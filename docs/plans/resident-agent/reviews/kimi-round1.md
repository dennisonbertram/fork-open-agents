  ## 1. Disposition audit

  The bulk of Fable's arbitration is right and I won't relitigate it: accepting finding 2 (credential possession vs. authority) is the correct structural fix; deciding one account-level endpoint (finding 4), redefining mid-turn kill as idempotent restart + truthful terminal states (finding 5), slimming M1 (finding 8), and reordering persistence before fault injection (finding 6) are all correct. Trims 1 (`create_workers` cut), 2 (`require_approval` schema-only), 3 (evidence core first), and 5 (10-tool spike surface) are the right scope calls for a validation spike. Disagreements only below.

  **(a) Accepted findings that are overbuilt for the spike**

  - **Finding 3 / founder-question 5, as decided, makes M4b a go-gate.** Codex's PRD §10 sets "Cloudflare go: M0–M4 pass," and the M4 row requires "minimal fan-out/status roll-up works." Fable ratified this ("primitives alone cannot decide build-vs-fork"). The account registry/read model legitimately enters spike scope — stories 16/21 need enumeration — but the *canonical-flow demo* (fan-out + roll-up + blocked state end to end) is product-surface completeness, not substrate validation. Coupling the build-vs-fork decision to it means a platform that passes every technical risk can be failed on demo polish. Registry yes; the fan-out demo should produce recorded evidence, not gate the decision.
  - **Codex's added story 30 (retention, redaction, export, PITR, archive, destruction "explicit for memory, logs, backups, OAuth data, and external-output records") was accepted without trimming.** Redaction + secret-canary scan is M0 core (Fable's trim 3 keeps it, correctly). Export/PITR/archive is compliance surface for a spike explicitly "thin enough to throw away" (spike-plan.md header), and the actual retention values are founder-TBD anyway. As written, story 30 invites an implementing agent to build retention machinery before validation. It should read: retention values TBD; redaction and canary scan only in spike.

  **(b) Trims that cut something load-bearing**

  - **Trim 4's new week-1 kill criterion is miscalibrated.** Fable replaced "M1–M3 by end of week one" with "M0 + M1 + M4a done by end of week 1 or stop and reassess." M4a is the most human-dependent milestone in the plan — it needs a domain decision, an IdP, a consent page, and a real Claude Code OAuth dance (research/mcp-client-landscape.md §1: one interactive terminal turn per server, even headless). A provisioning delay on any of those trips the kill switch and kills a healthy substrate spike for a staffing/logistics failure. The criterion should gate on M0 + M1 with M4a *attempted* and any blocker recorded as evidence. Note the spike-plan.md text itself still carries the old "~2 weeks / M1–M3" criterion — see §2, item 1.

  **(c) Decided items I would decide differently**

  - **Decision 12 (gate clients).** Fable gates on Claude Code (OAuth) + ChatGPT Developer Mode on web as OAuth client #2, with Codex CLI static-token as "the headless path." I would swap the second gate to Codex CLI static-token and demote ChatGPT to canary (joining mobile). Fable's register contradicts the PRD she adopted. Data jurisdiction has the same problem one milestone later: PRD §Security says "TBD before Worker creation" because DO placement is permanent; workers are created in M1.

  ## 2. Blind spots

  Ranked by build impact:

  1. **No document precedence, and Fable's trims were never propagated.** This is the highest-impact miss for an autonomous build. fable-round1.md amends Codex's PRD by narrative, but codex-round1.md still contains `create_workers` in the §7.3 tool table and §7.9, batch acceptance criteria in stories 19–20, the 16-tool surface, FTS5 in §7.7's "required logical schema," an un-split M2/M4, and spike-plan.md still says "~2 weeks" with the old week-1 kill criterion. Two implementing agents handed this package will build incompatible components — one following the PRD text, one following the arbitration. Nothing states which document wins. For a no-human build this is fatal and cheap to fix.
  2. **The autonomous-build trust topology and provisioning critical path are enumerated but never scheduled.** Codex's section C lists 20 human-provided items and gap #22 names the missing independent proof authority, but neither reviewer created a pre-M0 provisioning milestone or an owner for the M0 contract (gap #3: ledger schema, fault barriers, evaluator, fingerprints "must be defined before feature agents can implement"). As planned, the build halts in hour one waiting on a paid account and an IdP decision, and the founder's core rule — self-reports never trusted, evidence ledgers are — has no build-time mechanism: whoever writes the code also runs the tests and declares the verdict. The plan needs one paragraph saying the M0 evaluator is a separate, deterministic checker (or separately-agented) that implementing agents cannot edit.
  3. **The fixture and oracle spec is missing despite e2e-on-real-projects being the founder's hard requirement.** Codex flagged the contradictory "add a failing test" pass criterion (gap #15); nobody assigned the fix. No doc names the fixture repo, its commit pin, the expected patch/test outcome/final digest, or an oracle pre-change green run — the SWE-bench leakage/flakiness lesson in research/e2e-harness-prior-art.md stays unapplied. And the spike's "one repo fixture" is never reconciled with the founder's "real sample projects" (plural): the build-vs-fork decision could be reached without ever running the founder's actual acceptance condition.
  4. **MCP/OAuth spec-revision ambiguity.** research/testing-and-observability.md and e2e-harness-prior-art.md flag that the 2026-07-28 MCP spec deprecates DCR in favor of CIMD (removal ~2027), switches to stateless lifecycle with per-request `_meta`, and that RFC 8707 `resource` and `insufficient_scope` step-up exist only from dated revisions. mcp-client-landscape.md §1 gives the exact server metadata Claude Code requires to select CIMD, and the 5-minute idle timeout that makes MCP progress notifications a de facto server requirement. The PRD says "PKCE and DCR/CIMD support" and pins none of this. Two agents will serve different discovery documents and fail different clients. Relatedly, decision 1 committed to static bearer tokens, but no doc assigns who mints, scopes, stores, rotates, and revokes them (Codex gap C.7 raised this; it was never resolved).
  5. **Second-order platform traps present in research but absent from pass criteria.** (i) Backup GC: TTL is enforced only at restore time and expired squashfs objects linger and bill in R2 (research/sandbox-sdk.md §Lifecycle); no milestone owns a sweeper or even a lifecycle rule, and an autonomous multi-week spike will accumulate them. (ii) The `mksquashfs` permission trap — `0600`/`0700` tool dotfiles silently break backups — belongs in the M3 backup manifest tests alongside `.git`/untracked/session-state enumeration. (iii) OAuth revocation runs on eventually-consistent global KV (research/agents-sdk-and-mcp.md §OAuth), so the PRD's binary acceptance "revoke … subsequent calls fail through the deployed front door" will flake; it needs a measured-window criterion. (iv) The deterministic Workflow instance-ID scheme (`${workerId}-turn-${seq}`, ≤100 chars, duplicate-live-ID-throws = free idempotency, research/durable-objects-and-workflows.md §DO↔Workflow patterns) is exactly the kind of convention two agents invent differently, and the PRD never pins it.

  ## 3. Consensus verdict

  The package captures the important high-level items unusually well: the persona/trust model, the credential-authority split, the one-endpoint topology, the memory authority classes, the idempotency and evidence-ledger discipline, and the TBD-with-named-decider practice are all present and mostly consistent with the research. The low-level detail is also largely there — tool contracts, resource URIs, error taxonomy, lifecycle state machines, evidence bundle fields, per-milestone pass criteria. What is missing is not substance but *singular truth*: the arbitration layer exists only as deltas on documents that were never edited, two founder-required anchors (provisioning sequence, fixture/oracle spec) are unowned, and one protocol layer (MCP/OAuth revision + static-token design) is underpinned. For a human-led build these are friction; for the stated autonomous build they are divergence generators, and the founder's constraints make divergence the failure mode that matters. The gaps are all closable without new subsystems.

  5. Pin the MCP spec revision and discovery-document requirements (CIMD metadata, RFC 8707 resource, progress-notification cadence) and assign an owner for static-token issuance/scoping/revocation design before M4a.
