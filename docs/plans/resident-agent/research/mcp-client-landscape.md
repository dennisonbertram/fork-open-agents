# Remote MCP Client Landscape — August 2026

## TL;DR

Every major agent product researched now speaks remote MCP over Streamable HTTP, and OAuth 2.1 + PKCE has become the de facto authorization baseline across the ecosystem — but implementations diverge sharply on Dynamic Client Registration (DCR, RFC 7591) reliability, Client ID Metadata Document (CIMD) support, headless/no-browser auth, and the optional MCP client capabilities (elicitation, sampling, roots). Claude Code is the most complete and most explicitly documented remote-MCP client: it ships DCR and CIMD "out of the box," always sends PKCE, has a purpose-built static-header path for fully headless connections, and has unusually detailed, versioned documentation of long-tool-call and backgrounding behavior. Anthropic's own connector-auth docs (the server side) explicitly forbid pure machine-to-machine `client_credentials` grants — every connection requires a one-time human consent step, which matches this project's intended Cloudflare `workers-oauth-provider` design almost exactly. Codex CLI has the cleanest fully-headless static-token mechanism (`--bearer-token-env-var`) of any client researched, but its default per-tool-call timeout is a short 60 seconds and Codex Cloud (the web/background-task surface) does not read the CLI's MCP config at all — custom remote MCP in Codex Cloud is an unresolved community ask, not a confirmed shipped feature. ChatGPT's Developer Mode supports SSE and Streamable HTTP with CIMD and DCR, but Developer Mode can only be *enabled* on the web, and mobile use of an already-registered connector is community-reported (not officially confirmed) to be read-leaning with write actions frequently gated behind workspace tier and platform. Windsurf, as a distinct product, is functionally gone: `windsurf.com` now 308-redirects to `devin.ai/desktop`, and its own MCP docs page 307-redirects into Cognition's Devin documentation with a banner marking the old Cascade-agent MCP config "legacy."

## Per-client detail

### 1. Claude Code (CLI; Desktop app; Claude Code on the web/cloud sessions)

**Transport.** `claude mcp add --transport http <name> <url>` is the recommended path; `type: "streamable-http"` is accepted as an alias for `http` in JSON config. SSE (`--transport sse`) is explicitly marked deprecated in the docs. WebSocket (`type: "ws"`) is also supported but is header-auth-only — it does not support OAuth or the `--transport` flag. *Verified against `code.claude.com/docs/en/mcp`, official, fetched 2026-08-11.*

**OAuth / DCR / CIMD.** Claude includes a PKCE `code_challenge` with `S256` on every authorization request "regardless of which registration mechanism it uses." `oauth_dcr` and `oauth_cimd` are both "supported out of the box" server-side; Claude selects CIMD only when the auth server advertises both `client_id_metadata_document_supported: true` and `"none"` in `token_endpoint_auth_methods_supported`, otherwise falls back to DCR. Claude Code itself is a CIMD-identified native client: its own metadata document lives at `https://claude.ai/oauth/claude-code-client-metadata`, and it uses an RFC 8252 loopback redirect (`http://localhost:PORT/callback`, port varies per session — not the hosted `https://claude.ai/api/mcp/auth_callback` used by Claude.ai/Desktop/mobile). Pre-registered/static credentials are supported via `--client-id`/`--client-secret` (or `MCP_CLIENT_SECRET` env var for CI) and `--callback-port` for a fixed redirect port. *Verified against `claude.com/docs/connectors/building/authentication` (official) and `code.claude.com/docs/en/mcp` (official), both fetched 2026-08-11.*

**Headless / machine-to-machine.** Two independent paths: (1) fully headless static-token auth via `--header "Authorization: Bearer <token>"` — no browser ever required; (2) OAuth via `/mcp` or, since v2.1.186, `claude mcp login <name>` from a shell. As of v2.1.191 this command detects a browserless environment (SSH, headless Linux) and prints the authorization URL for the user to open elsewhere and paste the callback URL back — it still needs one interactive terminal turn; there is no fully unattended OAuth completion. Once authenticated, tokens are cached and refreshed automatically (reactive refresh on 401, proactive refresh up to 5 minutes before expiry), so later non-interactive runs (`claude -p`, Agent SDK, cloud sessions) reuse the cached token without a browser. If a configured server still needs auth during a non-interactive run, Claude Code (as of v2.1.196, with tool search on) tells the model the server's tools are unavailable pending sign-in rather than silently omitting them. *Verified against `code.claude.com/docs/en/mcp`, official, fetched 2026-08-11.*

**Elicitation / sampling / roots.** Elicitation is supported natively, both **form mode** (server-defined dialog fields) and **URL mode** (browser flow), with no client-side config required, plus an `Elicitation` hook for auto-response. **Roots** are supported: `roots/list` returns the launch directory plus any `--add-dir`-granted directories, and Claude Code sends `notifications/roots/list_changed` (both since v2.1.203). **Sampling is not supported** — `anthropics/claude-code#1785` ("Support for MCP Sampling to leverage Claude Max subscriptions") is open, filed 2025-06-08, confirmed still open 2026-08-11 (no merge/close comment found in this pass). *Verified against `code.claude.com/docs/en/mcp` (official) and the GitHub issue directly, both fetched 2026-08-11.*

**Wiring.** `claude mcp add`, `claude mcp add-json`, three scopes (`local` default in `~/.claude.json`, `project` shared via checked-in `.mcp.json`, `user` cross-project in `~/.claude.json`). Project-scoped servers require interactive approval the first time, except in `claude -p`, Agent SDK, and cloud sessions, which load them without prompting. **Skill/plugin-shaped wiring exists**: plugins can bundle `.mcp.json` at the plugin root or inline in `plugin.json`, and Anthropic ships an official `mcp-server-dev` plugin (`/plugin install mcp-server-dev@claude-plugins-official`, then `/mcp-server-dev:build-mcp-server`) that scaffolds a remote HTTP or local stdio server interactively — directly relevant to shipping the wiring as a skill. Claude Code on the web (cloud sessions) receives claude.ai connectors and other MCP config as explicit `--mcp-config` entries provisioned by the remote host rather than reading local `disabledMcpjsonServers`-style settings. *Verified against `code.claude.com/docs/en/mcp`, official, fetched 2026-08-11.*

**Long tool calls / timeouts / progress.** Unusually well documented: a per-server hard wall-clock `timeout` (config field, ms) or the `MCP_TOOL_TIMEOUT` env var, which **defaults to roughly 28 hours when unset**; a separate 60-second first-byte "per-request" timer for HTTP/SSE/connector servers (raised only by setting the per-server timeout or `MCP_TOOL_TIMEOUT` to ≥60s); an idle-timeout (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`) of 5 minutes (HTTP/SSE/WS) or 30 minutes (stdio) that fires only when the server sends **neither a response nor a progress notification** — meaning MCP progress notifications are honored and do extend the idle window even though they don't extend the hard wall-clock limit. As of v2.1.212, any main-conversation tool call still running after **2 minutes automatically backgrounds**: Claude gets a task ID immediately and keeps working, with the result delivered as a notification when the call finishes (visible/stoppable in `/tasks`). Automatic backgrounding does **not** apply to subagent calls, IDE-server calls, or non-interactive-mode calls (unless `CLAUDE_AUTO_BACKGROUND_TASKS=1`). *Verified against `code.claude.com/docs/en/mcp`, official, fetched 2026-08-11.*

**Mobile.** Claude Code itself has no mobile app; "Remote Control" lets a phone approve/deny individual permission prompts for a running session but is not an independent MCP client surface.

### 2. Claude.ai / Claude Desktop connectors (incl. Claude mobile)

Anthropic states the same auth infrastructure "backs Claude.ai, Claude Desktop, Claude mobile, Claude Code, and Cowork," but the hosted product and Claude Code are documented as **separate clients with separate OAuth identities**: hosted surfaces register a single shared callback, `https://claude.ai/api/mcp/auth_callback`, and directory connectors use **one shared OAuth application per connector** (no per-org client for the shared directory; custom connectors let an admin supply their own client ID/secret instead). *Verified against `claude.com/docs/connectors/building/authentication`, official, fetched 2026-08-11.*

Supported auth types for the hosted surfaces: `oauth_dcr`, `oauth_cimd` (both "out of the box"), `oauth_anthropic_creds` (Anthropic stores a vendor's OAuth client credentials and performs token exchange after a **mandatory** per-user consent screen — explicitly *not* a pure machine-to-machine grant), `custom_connection`, `static_headers` (**beta**: an org admin enters a fixed API key/bearer token once, shared org-wide), and `none` (authless). The doc is explicit and load-bearing: *"A pure machine-to-machine `client_credentials` grant—where a server-to-server token is issued with no user in the loop—is not supported. Every connection requires user consent."* This is a hard architectural constraint on any headless/no-human-in-loop design that routes through hosted Claude.ai/Desktop/mobile rather than through Claude Code CLI's own `--header` path.

Custom connectors (remote MCP by URL) are available on **Free, Pro, Max, Team, and Enterprise** plans (Free capped at one connector); Team/Enterprise admins add org-wide connectors under Organization settings, individuals add personal ones under Customize → Connectors. *Verified against `support.claude.com/en/articles/11175166`, official help-center, fetched 2026-08-11.* The same support article does not explicitly describe iOS/Android limitations; mobile MCP support (community-dated to 2025-07-26) is corroborated only by secondary/community sources found via search, not an official doc fetched directly in this pass — configuration happens only on the web/desktop UI and syncs to mobile, and mobile is remote-MCP-only since it cannot run local stdio servers.

Elicitation, sampling, and roots behavior for the **hosted UI specifically** (as opposed to the Claude Code CLI docs, which do cover these) was not found in the pages fetched — mark **UNVERIFIED**, not assumed identical to Claude Code just because the backend is shared.

### 3. ChatGPT (Developer Mode / connectors, incl. mobile)

**Transport / auth.** OpenAI's own docs state plainly: "Supported MCP protocols: SSE and streaming HTTP." Authentication types are OAuth, no-auth, and "Mixed Authentication." *Verified against `developers.openai.com/api/docs/guides/developer-mode`, official, fetched 2026-08-11.* The companion MCP guide recommends "OAuth with Client ID Metadata Documents for client registration when your authorization server supports CIMD," and documents both public-client (`none`) and signed-assertion (`private_key_jwt`) CIMD token-exchange flows; DCR "remains supported when configured" but CIMD is the stated preference. *Verified against `developers.openai.com/api/docs/mcp`, official, fetched 2026-08-11.* PKCE is not explicitly mentioned in either fetched page — treat as undocumented rather than absent.

**Headless / M2M.** Not documented as a supported path in either official page fetched. Developer Mode connector setup is UI-driven (per-search synthesis, the toggle and per-server registration live under Settings, with slightly conflicting community descriptions of the exact menu path — "Settings → Apps → Advanced settings" vs. "Settings → Security and login"); there is no documented equivalent to Claude Code's `--header` static-bearer flag or Codex's `--bearer-token-env-var`.

**Mobile.** The official Developer Mode page states availability is "Pro, Plus, Business, Enterprise, and Education accounts **on the web**" — i.e., **enabling** Developer Mode and registering a new custom connector is a web-only action per the primary source. Community sources describe mobile-app testing of already-built connectors ("Mobile layouts can be tested by invoking the app in the ChatGPT iOS or Android apps") but also report (OpenAI developer-community forum, GitHub issue on `openai/openai-apps-sdk-examples`, both community tier, dated across late 2025–2026) that **MCP write actions are frequently disabled on mobile** and that individual Plus/Pro accounts may be limited to read/fetch-only tool calls even with Developer Mode on, with full write access gated to Business/Enterprise/Edu workspaces after admin approval (Google/Microsoft write scopes reportedly rolled out 2026-06-15). None of this mobile-specific behavior is confirmed in an official OpenAI document fetched in this pass — treat the mobile write-gating claims as **community-sourced, moderate confidence**, and the read-path viability as **plausible but UNVERIFIED**.

**Elicitation / sampling / roots.** Not addressed in either official page fetched.

### 4. OpenAI Codex — CLI and Cloud

**CLI transport / config.** Two transports: local stdio and remote Streamable HTTP (SSE is not mentioned as a Codex CLI transport in the official doc). Config lives in `~/.codex/config.toml` (global) or a project's `.codex/config.toml`, under `[mcp_servers.<name>]` tables, shared between the CLI and the Codex IDE extension. Documented defaults: `startup_timeout_sec = 10`, `tool_timeout_sec = 60`. *Verified against `learn.chatgpt.com/docs/extend/mcp?surface=cli` (redirect target of `developers.openai.com/codex/mcp`), official, fetched 2026-08-11.* A **60-second default tool-call timeout is short** relative to Claude Code's ~28-hour default and is a concrete risk for any long-running "task a worker and wait" call unless raised explicitly in `config.toml`.

**Auth.** Four documented auth modes for HTTP servers: `bearer_token_env_var` (reads a token from an environment variable — no OAuth, no browser, cleanest headless path of any client researched), OAuth (the default, using "stored MCP OAuth credentials"), ChatGPT-session auth (reserved for "trusted first-party servers"), and static `http_headers`. `codex mcp add <name> --url <url> --bearer-token-env-var=<VAR>` is the exact documented headless pattern (also seen directly in the merged GitHub PR that introduced it, `openai/codex#4904`, which replaced plaintext bearer-token storage with env-var references). For OAuth servers, `codex mcp login <name>` runs a browser-based OAuth 2.1 + mandatory-PKCE flow using RFC 9728 protected-resource discovery and RFC 8707 resource indicators (community/code-derived sources — DeepWiki and a third-party Codex knowledge-base blog — moderate confidence, not independently re-derived from source in this pass). Community sources state headless environments without browser access must fall back to bearer-token auth or a pre-authenticated service account, since OAuth login has no non-interactive path. *Primary: `learn.chatgpt.com/docs/extend/mcp?surface=cli` and `github.com/openai/codex/pull/4904`, both fetched 2026-08-11. Secondary/community: DeepWiki `openai/codex` OAuth page, `codex.danielvaughan.com` posts — not independently verified.*

**Codex Cloud (web).** The same official doc states plainly: **"ChatGPT web doesn't read local Codex configuration."** Codex Cloud tasks reach external tools through ChatGPT's own Apps/plugins mechanism instead of the CLI's `config.toml`-based MCP client. A 2025-10 OpenAI developer-community thread ("Codex Cloud MCP Server support") requests direct custom-MCP support in Codex Cloud as a still-missing feature; this research pass could not confirm whether that gap has closed as of 2026-08-11 — **flagged as an open question**, not resolved either way.

**Elicitation / sampling / roots.** Not documented in any Codex source found (official or community).

**Mobile.** No evidence of Codex having its own mobile client; ChatGPT's mobile app can trigger Codex Cloud tasks through ChatGPT's own layer, which is governed by ChatGPT's Developer Mode/connector rules (see §3), not Codex's MCP client rules.

### 5. Cursor

**Transport.** stdio, SSE, and Streamable HTTP for remote, multi-user-capable servers. *Verified against `cursor.com/docs/context/mcp` (redirect target of `docs.cursor.com/context/mcp`), official, fetched 2026-08-11.*

**OAuth / DCR / CIMD.** The official doc confirms OAuth support ("Cursor supports OAuth for servers that require it") and a static-credential path (`mcp.json` `auth` object with `CLIENT_ID`, `CLIENT_SECRET`, `scopes`), with fixed redirect URLs: `https://www.cursor.com/agents/mcp/oauth/callback` (web/Agents) and `http://localhost:8787/callback` (Desktop — a fixed port, unlike Claude Code's ephemeral loopback port). PKCE and DCR are described only in secondary/community sources (a WorkOS-style guide and Cursor's own community forum), not stated explicitly in the official page text captured. The Cursor community forum itself (first-party forum, community-tier posts) documents real 2026 breakage: *"PKCE OAuth flow with custom MCP server failing Dynamic Client Registration on v3.3.30"* and *"Official Meta Ads MCP OAuth fails: Dynamic registration is not available for this client"* — evidence that DCR support is present but not reliable across servers in practice. CIMD support was not confirmed or denied in any source consulted — **UNVERIFIED**.

**Headless / M2M.** Not documented. Cursor also ships "Background Agents"/a Cursor CLI product surface; this research pass did not verify whether those surfaces have a distinct, more headless-friendly MCP auth path — **open question**.

**Elicitation / sampling / roots.** The official doc lists supported capabilities explicitly: *"Tools, Prompts, Resources, Roots, Elicitation, and Apps (extension)."* Sampling is conspicuously absent from that list — treated here as **not documented / likely unsupported**, not confirmed unsupported.

**Wiring.** `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global); also Settings → Tools & MCP UI, and one-click "Add to Cursor" buttons from Cursor's MCP marketplace listings.

**Long tool calls / timeouts.** Not documented in the fetched content — **UNVERIFIED**.

### 6. Devin (Cognition) — cloud sessions, Devin for Terminal, Devin Desktop

**Transport.** HTTP/Streamable HTTP (recommended for new integrations), SSE ("legacy protocol being phased out"), and stdio for local CLI-based servers. *Verified against `docs.devin.ai/work-with-devin/mcp`, official, fetched 2026-08-11.* (A separate page, `cli.devin.ai/docs/extensibility/mcp/overview`, covers Devin for Terminal specifically; details on that page came only from WebSearch synthesis, not a direct fetch, in this pass.)

**OAuth.** DCR, PKCE, a fixed callback URL (`https://api.devin.ai/mcp/oauth/callback`), and support for supplying pre-registered client credentials instead of DCR are all documented. CIMD support was not found either way — **UNVERIFIED**.

**Headless / M2M.** This is the most explicitly headless-friendly design found among the nine clients: static bearer tokens via an Authorization header, environment variables for API keys/credentials, and an explicit **organization-level "service account"** connection mode where "all members share one authenticated connection" — clearly designed for shared, non-interactive org use, distinct from the personal per-member OAuth mode also offered.

**Wiring.** Settings → Connections → MCP servers → "Add a custom MCP," specifying URL, auth method, and transport; a "Test listing tools" action spins up an isolated environment to validate connectivity before the server is live.

**Timeouts / elicitation / sampling / roots.** The doc documents a generic failure message — *"Server took too long to respond - check server status"* — with no specific duration given; the exact timeout value is **UNVERIFIED**. Elicitation, sampling, and roots support for Devin specifically were not confirmed in any Devin-specific source (search results returning generic MCP-spec explainer content were not treated as Devin-specific evidence) — **UNVERIFIED / undocumented**.

**Windsurf relationship.** See §9 — Windsurf is now folded into Devin Desktop, whose bundled default agent is "Devin Local," with the former Windsurf/Cascade agent retained as a labeled-legacy option.

### 7. Gemini CLI

**Transport.** stdio, SSE (`"url"` field), and Streamable HTTP (`"httpUrl"` field) are all documented as current, first-class options — notably, Google's docs do **not** carry the SSE-deprecation warning that Claude Code's docs do, an expectation gap worth flagging for anyone assuming SSE is uniformly dead across the ecosystem. *Verified against `github.com/google-gemini/gemini-cli/blob/main/docs/tools/mcp-server.md`, official, fetched 2026-08-11.*

**OAuth.** Three `authProviderType` values: `dynamic_discovery` (default; auto OAuth discovery/DCR-style flow, browser-based, redirect to `http://localhost:<random-port>/oauth/callback`), `google_credentials` (uses Google Application Default Credentials), and `service_account_impersonation` (impersonates a GCP service account). The doc is explicit and load-bearing: *"OAuth authentication requires that your local machine can open a web browser... This feature will not work in: Headless environments without browser access."* An **open, confirmed bug** (`google-gemini/gemini-cli#6639`) documents that when a Streamable HTTP server returns 401, Gemini CLI's MCP client does not correctly initiate the OAuth flow — a real reliability gap on the primary transport+auth combination.

**Headless / M2M.** `dynamic_discovery` explicitly does not work headless. Two headless-friendly alternatives are documented: static header tokens (`"headers": {"Authorization": "Bearer your-api-token"}`) and environment-variable expansion (`"API_KEY": "$MY_EXTERNAL_TOKEN"`); `google_credentials`/`service_account_impersonation` are also headless-capable but scoped to GCP-fronted servers.

**Elicitation / sampling / roots.** Elicitation support looks unreliable/in-progress: open issues include `#22249` ("Method not found" error using tools with elicitation support), `#7056` (feature request to support the elicitation/prompt workflow at all), and `#15613` (feature request for URL-mode elicitation specifically). Sampling and roots support specific to Gemini CLI were not confirmed in any source — **UNVERIFIED**, not to be conflated with the generic MCP-spec explainer content the search returned.

**Wiring.** `gemini mcp add [options] <name> <commandOrUrl> [args...]`, `gemini mcp list/remove/enable/disable`, config also settable directly in `settings.json` under `mcpServers`; `/mcp auth` runs the OAuth flow for a server that needs it from inside a session.

**Timeouts.** A per-server `"timeout": 30000` (ms) config field is documented, alongside a separately-described "default 10 minutes" for connection establishment — these two figures were not resolved to a single authoritative statement in this pass; flagged as a minor internal inconsistency in the sourced material rather than asserted as fact either way.

### 8. VS Code — GitHub Copilot agent mode

**Transport.** Local stdio and remote HTTP are shown in official examples (e.g., `"github": {"type": "http", "url": "https://api.githubcopilot.com/mcp"}`); SSE support was not confirmed or denied in the pages fetched. *Verified against `code.visualstudio.com/api/extension-guides/ai/mcp` and `docs.github.com` pages, official, fetched 2026-08-11.*

**OAuth / DCR.** VS Code "first starts with a Dynamic Client Registration (DCR) handshake and then falls back to a client-credentials workflow if the IdP does not support DCR," with fixed redirect endpoints `http://127.0.0.1:33418` and `https://vscode.dev/redirect`. GitHub and Microsoft Entra get first-party, built-in treatment via the Accounts menu ("Manage Trusted MCP Servers"), bypassing generic OAuth complexity for those two providers only. Real friction is documented in Microsoft's own issue tracker as of this research date: `microsoft/vscode#257415` (open — "No Option to disable Dynamic Client Registration and use custom(static) client information"), `#252892` (open feature request — let VS Code register a static clientId for MCP OAuth), and `#279955` (open — "Dynamic Client Registration(DCR) issues in MCP Servers"). Read together, these indicate DCR is the primary path and there is **no documented, shipped way to supply static/pre-registered OAuth client credentials as a first-class alternative**, unlike Claude Code (`--client-id`/`--client-secret`) or Cursor (`auth` object with `CLIENT_ID`/`CLIENT_SECRET`). CIMD support was not found either way — **UNVERIFIED**.

**Headless / M2M.** Not documented as a supported path in any source consulted.

**Elicitation / sampling / roots.** All three are explicitly documented as supported — the most complete set of the nine clients researched. Elicitation: *"request input from the user."* Sampling: MCP servers can perform "language model requests using the user's configured models and subscriptions," with the user prompted to authorize model access on first use and a `MCP: List Servers` → `Configure Model Access` command to restrict which models a server may use. Roots: VS Code supplies "the user's workspace root folder information" to the server.

**Wiring.** `.vscode/mcp.json` (workspace) or a user-profile location; Extensions view → search `@mcp` → "Install in Workspace" updates `.vscode/mcp.json`, with a trust-confirmation step before first startup. A community guide (not an official VS Code release note fetched in this pass) cites **VS Code 1.101** as the version baseline for remote MCP + OAuth — treat that specific version number as **UNVERIFIED against a primary source**. A separate community source (dev.to) claims that as of VS Code 1.113 (2026-03-25), configured MCP servers can bridge to Copilot CLI and Claude Code agent sessions — an interesting cross-tool config-sharing mechanism if true, but not independently confirmed here.

**Timeouts / long-running behavior.** Not documented in any source consulted — **UNVERIFIED**.

### 9. Windsurf (now redirects into Cognition's Devin Desktop)

Windsurf as an independently branded product no longer appears to exist as of this research date. Direct fetches performed today (2026-08-11) confirm: `https://windsurf.com` returns an HTTP 308 permanent redirect to `https://devin.ai/desktop`, and `https://docs.windsurf.com/windsurf/cascade/mcp` returns an HTTP 307 redirect to `https://docs.devin.ai/desktop/cascade/mcp`, where the page itself carries a banner stating *"The MCP configuration on this page applies to the legacy Cascade agent only,"* with "Devin Local agent" described as the new default. This is corroborated by press/community reporting (TechCrunch on the July 2025 acquisition; several third-party blogs describing a 2026-06-02 silent over-the-air rebrand of Windsurf into "Devin Desktop," with the bundled default agent renamed "Devin Local" and the original Windsurf agent kept as "legacy Cascade") — the exact rebrand date is community-sourced and not independently verified against a Cognition changelog in this pass.

**Legacy Cascade MCP support** (documented on the redirected page): stdio, Streamable HTTP, and SSE transports; remote HTTP servers configured via `mcp_config.json` using a `serverUrl` or `url` field; the page mentions "OAuth for each transport type" without PKCE/DCR/CIMD specifics. Headless/M2M auth, elicitation, sampling, roots, and tool-call timeout behavior were **not documented** on this page.

**Open question, not resolved in this pass:** whether "Devin Local" (the new default agent) has its own, possibly different, MCP-client implementation distinct from both legacy Cascade (documented above) and Devin's cloud-session MCP client (§6) — no separately-documented "Devin Local MCP client" page was found. Given the explicit "legacy" framing, any spike work should treat Windsurf-as-such as a shrinking target and verify current behavior directly against `devin.ai/desktop` rather than historical Windsurf material.

## Fit for resident agent service

**M4 milestone (external client self-registers via OAuth and tasks a worker) — lowest-risk pairing: Claude Code CLI as the orchestrating client.** Claude Code natively speaks exactly the stack this project's Cloudflare front door is being built around: OAuth 2.1, PKCE on every request, DCR out of the box, and CIMD out of the box with automatic auto-discovery/fallback logic that matches the semantics Anthropic documents for `@cloudflare/workers-oauth-provider`-style servers. It also has the most detailed documented behavior for exactly the shape of interaction this product needs — a tool call that can legitimately run for minutes to hours (default ~28-hour `MCP_TOOL_TIMEOUT`, automatic backgrounding of any call past 2 minutes so the orchestrating session "keeps working" while a worker grinds). The one real friction point: OAuth consent in Claude Code is documented as requiring one interactive turn per server (even over SSH it needs a paste-the-callback-URL step) — fully consistent with "closes the laptop *after* fanning work out," but not compatible with a design that expects zero human interaction ever. If flow (a) genuinely needs one MCP endpoint *per worker* (one per issue, per the product's "one worker per task" model), each new worker's first-ever OAuth handshake plausibly still needs either (i) a UX where the front door's own login session lets a second/third/Nth DCR-registered client skip the consent screen after the human has already authenticated once at the authorization server, or (ii) Claude Code reusing one already-authorized client registration across multiple resource URLs (RFC 8707 resource indicators) rather than registering fresh per worker — this is a server-design question outside this client-side research's scope, flagged here because it directly determines whether the skill-driven fan-out in flow (a) can complete unattended after the first worker.

**Flow (b), "ChatGPT on a phone for status" — works today only with real caveats, not a clean yes.** Developer Mode itself can only be *enabled*, and a new custom MCP connector can only be *registered*, on ChatGPT web (official doc: "Available to Pro, Plus, Business, Enterprise, and Education accounts on the web"). So the connector to this project's MCP backend has to be set up from a desktop/web ChatGPT session first; the phone can only use an already-registered connector, and even then, community reporting (not officially confirmed) suggests write actions are commonly gated or blocked on mobile, with full write access reserved for Business/Enterprise-tier workspaces after admin approval. A **status/read-only tool** (e.g., "list my running workers," "show worker X's latest event") is the more plausible mobile-safe design than a **write tool** (e.g., "tell worker X to retry") if targeting ChatGPT mobile specifically for this story. This should be verified with a live registration-and-mobile-use test before relying on it — it is currently an inference from community reports, not a confirmed capability.

**Flow (c), "tell Codex on another device to inspect and fix a stuck worker" — Codex CLI is workable, Codex Cloud is not confirmed.** Codex CLI has the single cleanest headless mechanism found in this survey (`--bearer-token-env-var`, zero browser interaction ever), which is attractive for a "device" that might be a CI runner or a script rather than an interactive terminal — but that mechanism bypasses the OAuth/DCR/PKCE flow this project's server is standardizing on, so using it would mean the server also needs to support a static-token auth mode (mirroring Anthropic's own `static_headers` beta pattern) for Codex-CLI-only users who want zero-interaction auth. If "Codex" in this flow means the ChatGPT-hosted Codex Cloud surface rather than the local CLI, remote custom MCP support there is **not confirmed** as of 2026-08-11 (the official doc states ChatGPT web doesn't read the CLI's MCP config, and a still-open 2025-10 community request asks for exactly this feature) — treat Codex Cloud as a blocker until independently reverified, and default to Codex CLI for this flow.

**Concrete blockers to track before building against this landscape:**
1. Codex Cloud custom-MCP support status is unconfirmed — verify directly before designing flow (c) around it.
2. ChatGPT Developer Mode enable/registration is web-only; mobile write-gating is community-sourced, not officially confirmed either way — verify with a live test.
3. Gemini CLI's `dynamic_discovery` OAuth mode explicitly refuses headless environments, and has an open bug where a 401 on Streamable HTTP doesn't correctly trigger re-auth (`#6639`) — if Gemini CLI is ever added as a client, budget for this.
4. VS Code has no documented static/pre-registered OAuth client path (four related issues open on Microsoft's tracker) — DCR-only is a real constraint if the front door ever needs to support a static-client fallback for VS Code users.
5. Windsurf-as-a-target is effectively deprecated; any work should target "Devin Desktop" / "Devin Local" and be re-verified against `devin.ai/desktop`, not historical Windsurf docs.
6. None of the nine clients confirmed to support MCP **sampling** except VS Code (Claude Code explicitly does not, via an open, unmerged 2025-06-08 issue) — if the product's "pluggable coding brain inside the sandbox" concept ever wants to let a lightweight worker borrow the orchestrating client's model via sampling, that is not broadly available today.

## Open questions

1. Does Codex Cloud (the ChatGPT-hosted web/background-task surface, as opposed to Codex CLI) support arbitrary custom remote MCP servers as of August 2026, or only vetted first-party Apps/plugins? A 2025-10 community request suggests it did not as of that date; not reconfirmed for 2026-08.
2. Does a ChatGPT Developer Mode custom connector, once registered on web/desktop under an account, remain usable — specifically for **read-only** status-check tool calls — from the ChatGPT mobile app today? Only community/forum evidence was found, no official confirmation either way, and none of it isolates read vs. write behavior cleanly.
3. What VS Code version actually shipped remote MCP + OAuth support? A community guide cites 1.101; this was not confirmed against an official VS Code release note in this pass.
4. Does Cursor support Client ID Metadata Documents (CIMD) at all? No source consulted confirmed or denied this.
5. What is Devin's actual tool-call timeout duration? Only a generic error message was documented, no number.
6. Does "Devin Local" (the new default agent bundled in what used to be Windsurf) have MCP-client behavior identical to, or different from, the documented "legacy Cascade" MCP client and the separately-documented Devin cloud-session MCP client? No page specifically documenting a "Devin Local" MCP client configuration was found.
7. Gemini CLI's documentation shows both a `"timeout": 30000` (30-second) example field and a separate reference to a "default 10 minutes" — these could not be reconciled to one authoritative statement in this pass.
8. Whether any of the nine clients support MCP sampling beyond VS Code was not exhaustively confirmed for every client (Cursor, Devin, Gemini CLI, Windsurf/Cascade specifically were absent from their own docs on this point rather than explicitly denying it) — treat "sampling unsupported" as confirmed only for Claude Code (open GitHub issue) and as "undocumented" (not "confirmed absent") for the rest.
9. Whether Claude.ai's `static_headers` (beta) auth type, or Claude Code's `--header` static-bearer path, would satisfy this project's OAuth-first design goal for headless workers, or whether the project intends OAuth end-to-end regardless of client — a product-design question, not a research gap, but worth resolving before M4 implementation.
