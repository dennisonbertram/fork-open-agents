# Prior Art & Competition: Taskable Cloud Coding Agents, Control Planes, and Agent-Interop Protocols

Research date: 2026-08-11. All time-sensitive claims are dated inline. Training-data knowledge is not trusted; every claim below traces to a fetched or searched source (see Sources).

## TL;DR

- Every major vendor (Cognition/Devin, Google/Jules, Anthropic, Cursor) now ships a **documented REST API** to create/steer/query a cloud coding-agent session. **OpenAI Codex Cloud is the one clear exception** — no public API for cloud task lifecycle exists as of 2026-08-11; this is confirmed by an open, unresolved GitHub issue on `openai/codex` (filed 2026-05-27) asking OpenAI to build exactly that.
- **None of the taskable products in category (A) expose themselves as an MCP server that a foreign agent can drive.** Devin, Jules, Cursor, GitHub Copilot, and Amp all *consume* MCP (client-side, to reach the user's tools); none *emit* an MCP front door to their own session-creation API. Claude Code's `claude mcp serve` is the closest analog, but it exposes the **local CLI's tools**, not a durable cloud session, and it's Anthropic/local-only.
- The most important new find: **Anthropic Claude Managed Agents** (`/v1/agents`, launched 2026-04-08, public beta) is a hosted, API-first "agent + environment + session" primitive with a persistent, separately-versioned **memory store** (`agent-memory-2026-07-22` beta). This is structurally the closest thing to "durable, addressable workers with memory, reachable over an API" that any vendor ships today — but it is Claude-model-only (not a pluggable coding brain), it is a plain REST/SDK API rather than an MCP front door, and building the OAuth/DCR/multi-client-neutral layer around it is left entirely to the developer.
- **Synthesis answer #1 (does "agent-neutral resident workers over MCP" already exist):** No vendor combines all three of (a) durable/addressable worker identity, (b) MCP as the actual front door (not just a tool the worker calls), and (c) explicit multi-vendor client neutrality. Open-source control planes (agentapi, cmux, vibe-kanban, claude-squad) get close to "any coding CLI, one control surface" but are local-machine tools, not durable cloud-resident workers with their own MCP-addressable identity. This confirms the 2026-08-11 prior finding: the combination remains open, with the caveat that Anthropic Managed Agents and Cursor's Cloud Agents API are the nearest adjacent moves and could add an MCP front door with a changelog entry, not a re-architecture.
- **Synthesis answer #2 (remote-brain delegation):** Devin, Jules, Cursor Cloud Agents, OpenHands Cloud, and Anthropic Managed Agents are all API-taskable today and could plausibly serve as a "remote brain" a worker delegates to instead of running a CLI in its own container. Codex Cloud cannot (no API). Each changes cost attribution (their metering, not the worker's), removes the need for the worker to hold a container for that turn, and shifts trust to "did the vendor's agent actually do what it reported" — none of them provide a verifiable, portable audit trail designed for a third-party orchestrator to check.
- **Synthesis answer #3 (moat):** If durable, MCP-addressable resident workers become table stakes, the moat is client-neutrality itself — being the one place *any* front-end agent (Claude Code, Codex, Devin's own UI, a human) can reach the *same* long-lived worker and its memory, rather than each vendor's worker being reachable only from that vendor's own surfaces. Every vendor surveyed here is building a walled cloud-agent product reachable primarily from its own chat/IDE/CLI; none is building a neutral front door other vendors' agents are expected to connect to.

## Fit for resident agent service

### 1. Does anything already ship "agent-neutral resident workers addressable over MCP" — i.e., our exact product?

No. Evidence assembled across every product researched:

- **No taskable cloud coding agent (Section A) exposes an MCP server as the way to reach its own session-creation/steering API.** Devin, Jules, Cursor, Copilot, and Amp all consume MCP servers as tools; none of them let an external MCP client connect and say "give me a session, remember my last conversation, let me ask it questions." (docs.devin.ai/work-with-devin/mcp; cursor.com/docs/cloud-agent/api/endpoints; docs.github.com Copilot cloud-agent page — all fetched 2026-08-11.)
- **Claude Code's `claude mcp serve`** is the one product-level feature that puts MCP directly in front of an agent's tools — but it fronts the **local CLI process on your own machine**, not a durable, cloud-resident, independently-addressable worker with its own lifecycle. It dies when you close the terminal.
- **Anthropic Claude Managed Agents** (new finding, launched 2026-04-08, still in public beta as of this research) is the closest structural match to "durable worker with memory, reachable over an API": it has agent/environment/session objects, a persistent cross-session memory store, and streaming event I/O. But (a) it's a plain REST/SDK surface, not MCP; (b) the agent is Claude-model-only, not a pluggable coding brain; (c) Anthropic frames it explicitly as infrastructure *you* build a product on top of, not a place other vendors' agents are expected to connect to.
- **Open-source control planes (Section B)** solve the "any coding CLI, one control surface" half of the pattern (agentapi, cmux, claude-squad, omnara) but are local-machine tools without durable server-side identity, cross-device OAuth-scoped addressability, or MCP as the front door to that identity.

This is consistent with — and specifically extends — the 2026-08-11 finding cited in the brief: the exact combination remains open territory. The qualification worth flagging: the gap between "open territory" and "a vendor ships this next quarter" is narrow for at least two players. Anthropic already has the memory/session primitives (Managed Agents) and could add an MCP front door as a changelog entry rather than a re-architecture. Cursor already has the most client-neutral REST API of the closed-source products and a documented per-agent persistent workspace. Neither has done it yet, as of 2026-08-11.

### 2. The "remote brain" variant — who could serve that role today, and what would it change?

Ranked by how cleanly they fit "worker keeps memory/verification, delegates execution via API instead of running a CLI in its own container":

| Candidate | API-taskable today? | Fit as remote brain | What changes |
|---|---|---|---|
| **Devin** | Yes, mature v1 REST API | Good fit — session creation accepts a `structured_output_schema` for verifiable output, `knowledge_ids`/`secret_ids` for scoped context injection, `snapshot_id` for resuming state | No local container needed for that turn; cost shifts to Cognition's ACU billing (opaque unit conversion, not $/token); trust model becomes "read Devin's session transcript/diff and re-verify," since Devin's own verification isn't portable to a third-party auditor |
| **Google Jules** | Yes, official `sessions.create` REST API | Good fit for GitHub-centric repos; `requirePlanApproval` gives a built-in human/agent-in-the-loop checkpoint before code changes land | Cost rides on Google AI Pro/Ultra subscription tiers rather than metered API billing, which complicates per-task cost attribution back to an end customer |
| **Cursor Cloud Agents** | Yes, documented REST + SSE streaming | Good fit — persistent per-agent workspace/conversation across runs, and the API already accepts MCP server configs so the delegated agent can reach the same tools the worker would have used locally | Billed at underlying model API pricing while in "Max Mode," so cost attribution is closer to normal token metering than Devin's ACU abstraction; still Cursor's own sandbox, so verification still means reading Cursor's transcript, not running your own checks |
| **OpenHands Cloud** | Yes, documented V1 REST API, model-agnostic | Good fit, notably **the only one of these that is also fully open-source and self-hostable**, so a worker could delegate to OpenHands Cloud for elastic capacity while still running the identical OSS agent in its own container when isolation/verification matters more than cost | Because the OSS and Cloud runtimes are the same code, this is the strongest candidate for *keeping* verifiability if the memory/verification-holding worker also controls the OpenHands agent's tool permissions |
| **Anthropic Claude Managed Agents** | Yes, REST + streaming events, plus a genuine cross-session memory primitive | Good fit if the worker is comfortable being Claude-only for that turn; the memory store means some of "the worker's own memory" work could even be offloaded to Anthropic's memory API rather than reimplemented | Locks the "remote brain" turn to Claude models specifically — loses the "pluggable coding brain" property for that turn; billing is transparent token + $/session-hour, easiest of all candidates to attribute cost cleanly |
| **OpenAI Codex Cloud** | **No** — no public API for cloud task lifecycle (confirmed via openai/codex#24777) | Not usable as a remote brain today without an official API; the only path is spawning `codex` CLI processes yourself (i.e., still running a container) | N/A until OpenAI ships the API the community is explicitly requesting |
| **Amp** | Partial (CLI/plugin programmability, no cloud task-creation REST API found) | Weak fit as a *remote* brain specifically — its execution model is CLI/editor-first, not "POST a task, get a session back" | Would still require running Amp's CLI in a container the worker controls, undermining the "no container needed" benefit |

Across the fits that work (Devin, Jules, Cursor, OpenHands, Managed Agents), the architectural shift is consistent: (a) the worker's own sandbox is no longer needed *for that turn* — it becomes a pure client of the vendor's session API; (b) cost attribution moves from the worker's own compute metering to the vendor's billing unit (ACU, Google AI subscription tier, Max-Mode token pricing, or $/session-hour — four different units, not directly comparable without conversion); (c) trust/verification degrades to "read what the vendor's agent reports and reproduce/spot-check it," because none of these vendors expose a portable, third-party-checkable proof of what actually happened in their sandbox — the worker's own verification layer would have to treat a delegated remote-brain turn as a *less-trusted* result than a turn it ran and audited itself in its own container.

### 3. Where is the moat if the big vendors each ship their own cloud workers?

The moat is not "having a resident worker with memory" — every vendor surveyed here is converging on that primitive (Devin sessions + knowledge, Jules sessions + sources, Cursor agents + persistent workspace, Anthropic Managed Agents + memory store). The moat is **being the one neutral place any of those agents — and any human-facing client — can reach the same worker**, instead of each vendor's worker being reachable only from that vendor's own chat UI, CLI, and first-party integrations. Every product in Section A is building a walled cloud-agent product:

- Devin's session API requires a Cognition API key and Cognition's own session/knowledge model.
- Codex Cloud has no external API at all.
- Claude Code cloud sessions require the `claude` CLI and a claude.ai account; the one HTTP endpoint (`/fire`) is explicitly scoped "to claude.ai users only."
- Cursor, Jules, and Copilot each require their own API key/account and drive their own model(s).
- None of them accept an inbound MCP connection from a *foreign* agent as the way to reach a durable worker.

If the product's differentiator is specifically "an MCP front door any agent — including a vendor's own coding CLI, running as someone else's client — can use to reach a worker that outlives any single session and remembers its own history," that combination is not something any single vendor is structurally incentivized to build for competitors' agents, because it would mean, e.g., letting Codex or Devin's own UI drive a worker whose brain happens to be Claude, or vice versa. The moat is the neutrality itself, and it survives exactly as long as none of the big vendors decide it's in their interest to let rival front-ends drive their workers — which, based on the walled designs observed here as of 2026-08-11, none currently do.
