# OpenAPI Contract System — Current State & iOS Extension Path

Research brief for the native iOS app plan. Sources: actual code in `apps/web` (read June 2026), docs under `docs/process/`, and GitHub issues #298/#302/#284 plus merged PR #303 on `dennisonbertram/fork-open-agents`.

## 1. The pipeline (how the spec is generated)

The spec is **NOT hand-authored JSON** and **NOT auto-derived from route files**. It is a hand-assembled OpenAPI document builder whose schemas come from the **same Zod v4 schemas the routes validate against**, serialized with Zod 4's native `z.toJSONSchema` — no third-party zod-to-openapi library.

```
route Zod schemas ─► lib/api/openapi-spec.ts ─► openapi.json ─► openapi-types.ts ─► lib/api/client.ts
 (source of truth)    (assembles the doc)       (artifact)      (openapi-typescript) (openapi-fetch)
```

Key files:

- `apps/web/lib/api/openapi-spec.ts` (259 lines) — `buildOpenApiDocument()` returns the full OpenAPI 3.0.3 doc as a plain object. The serialization helper is at `openapi-spec.ts:29-31`:
  ```ts
  function j(schema: z.ZodType, io: "input" | "output"): JsonSchema {
    return z.toJSONSchema(schema, { target: "openapi-3.0", io }) as JsonSchema;
  }
  ```
  Request bodies use `io: "input"` (pre-transform client shape), responses use `io: "output"` (`openapi-spec.ts:64-71`). This makes schemas with `.transform()` (e.g. `allowedTools` trimming in `lib/skills/skill-types.ts:54-58`) serialize cleanly.
- `apps/web/scripts/generate-openapi.ts` — writes `apps/web/openapi.json` (`JSON.stringify(..., null, 2) + "\n"`). Script: `bun run --cwd apps/web openapi:generate` (`apps/web/package.json:16`).
- `apps/web/scripts/check-openapi.ts` — drift guard; string-compares regenerated output vs committed file, exits 1 on mismatch. Script: `openapi:check` (`apps/web/package.json:18`).
- `apps/web/lib/api/openapi-types.ts` (911 lines, generated by `openapi-typescript ^7.13.0` via `openapi:types`, `apps/web/package.json:17`). Lint-ignored at `.oxlintrc.json:6` (`"apps/web/lib/api/openapi-types.ts"` in `ignorePatterns`).
- `apps/web/lib/api/client.ts` — `createOpenAgentsApiClient()`, a thin typed client over `openapi-fetch ^0.17.0` (`client.ts:26-33`); `baseUrl` defaults to `""` (same-origin), fetch injectable.
- `apps/web/openapi.json` (1545 lines) — the committed artifact. `info.version: "0.1.0"`, `servers: [{ "url": "/" }]` (relative — a native client must supply its own base URL).

Zod version: 4.3.6 (workspace catalog). `z.toJSONSchema` with `target: "openapi-3.0"` and the `io` option is a Zod 4 native feature; **no `@asteasolutions/zod-to-openapi`, `zod-openapi`, or similar package exists in the repo** (checked `package.json`s and `bun.lock`).

### Where request schemas live (true shared source)

- Git routes: `apps/web/lib/git/http-schemas.ts` — `createBranchRequestSchema` (:15), `commitChangesRequestSchema` (:26), `openPullRequestRequestSchema` (:40), `mergePrRequestSchema` (:51), plus **schemas that exist but are NOT yet in the spec**: `discardChangesRequestSchema` (:21), `generatePrContentRequestSchema` (:34), `deploymentUrlQuerySchema` (:60).
- Skills: `apps/web/lib/skills/skill-types.ts` — `createUserSkillInputSchema` (:62), `updateUserSkillInputSchema` (:73), `deleteUserSkillInputSchema` (:88).

Routes really do validate with these same schemas — e.g. `apps/web/app/api/sessions/[sessionId]/git/branch/route.ts` imports `createBranchRequestSchema` from `@/lib/git/http-schemas` and calls `.safeParse(await readJsonBody(req))`, returning `jsonError(...issues[0]?.message ?? "Invalid request", 400)` on failure.

### Caveat: response schemas are NOT shared with routes

Response shapes in `openapi-spec.ts` are **hand-declared Zod objects local to the spec file** (`userSkillSchema` at :35-48, `errorSchema` at :50, `gitStatusSchema` at :51-62, and inline `z.object(...)` per response). Only request bodies are truly "the same schema the route validates." Response drift is caught only by the runtime contract suite (section 4), and three mutation responses are typed as `z.record(z.string(), z.unknown())` → `additionalProperties: {}` (untyped): commit result (`openapi-spec.ts:188-191`), open-PR result (:226-229), merge result (:245-248). A Swift codegen of these yields untyped dictionaries — the iOS plan should tighten these first.

## 2. Covered surface: 6 paths, 10 operations

From `openapi.json` / `openapi-spec.ts:92-257`:

| Path | Methods → operationId |
|---|---|
| `/api/settings/skills` | GET `listSkills`, POST `createSkill`, PATCH `updateSkill`, DELETE `deleteSkill` |
| `/api/sessions/{sessionId}/git/status` | GET `getGitStatus` |
| `/api/sessions/{sessionId}/git/branch` | POST `createBranch` |
| `/api/sessions/{sessionId}/git/commit` | POST `commitChanges` |
| `/api/sessions/{sessionId}/git/pr` | GET `checkPullRequest`, POST `openPullRequest` |
| `/api/sessions/{sessionId}/git/pr/merge` | POST `mergePullRequest` |

Notable shape details for client codegen:

- `deleteSkill` sends its `{ id }` in a **DELETE request body** (`openapi-spec.ts:134-143`) — legal but awkward for some HTTP stacks; iOS plan should either keep URLSession (fine with DELETE bodies) or push the backend to a path param.
- All schemas are **inlined** — there is no `components.schemas` section at all (generated `openapi-types.ts` shows `components: { schemas: never; ... }`). The `{ error: string }` envelope is repeated ~30 times in `openapi.json`. Swift generators will produce anonymous nested types unless the spec adopts `components` + `$ref`.
- Nullable handling uses OpenAPI 3.0 `nullable: true` (e.g. git status response, `openapi.json:641`), produced by `target: "openapi-3.0"`.
- No `security`/`securitySchemes` declared anywhere — auth exists only as the prose sentence in `info.description` ("All endpoints require an authenticated session") plus documented 401 responses.
- No 5xx responses documented.

## 3. Conventions (enforced + implied) for adding a path

Documented in `docs/process/api-openapi-contract.md`; enforced by `apps/web/lib/api/openapi-spec.test.ts`:

1. **Error envelope**: every non-2xx is `{ error: string }` (`errorSchema`, `openapi-spec.ts:50`; helper `errorResponse` at :72-73). Routes produce it via `jsonError()` helpers.
2. **Unique `operationId` per operation** — test-enforced (`openapi-spec.test.ts:18-36` keys a `Set` and fails on duplicates).
3. **Every operation documents a 401** — test-enforced (`openapi-spec.test.ts:38-50`), reflecting "all endpoints require auth."
4. **Request schema must be the route's real Zod schema** imported from the domain lib (`lib/git/http-schemas`, `lib/skills/skill-types`); wrap with `jsonBody()` (input shape). Response: declare a Zod object mirroring the route's return, wrap with `jsonResponse()` (output shape).
5. **Path params** via the `sessionIdParam` const pattern (`openapi-spec.ts:75-80`).
6. **Regenerate + commit artifacts**: `bun run --cwd apps/web openapi:generate && bun run --cwd apps/web openapi:types`, commit `openapi.json` + `openapi-types.ts` with the spec change.
7. Status-code vocabulary in use: 200/201 success, 400 invalid payload, 401 unauth, 403 forbidden (session not owned), 404 not found, 409 conflict (duplicate skill name / "Sandbox not initialized").

## 4. CI gates and contract-test infrastructure

### Build-time drift gate (runs on every PR)

- `lib/api/openapi-spec.test.ts:52-59` re-builds the doc and `expect(committed).toEqual(doc)` against the committed `openapi.json` — so a forgotten regeneration fails `bun run test:isolated`, which runs inside `bun run ci` (root `package.json:25`) and in `.github/workflows/ci.yml` (Test step runs `bun run test:isolated`). `openapi:check` is the equivalent manual/standalone guard; it is **not** separately wired into the CI workflow (the unit test covers it).
- The same test file also smoke-tests the typed client with an injected fetch (`openapi-spec.test.ts:62-85`).

### Runtime contract suite (real HTTP, black-box)

Location `apps/web/tests/contract/`, runner `bun run test:contract` (root `package.json:28`), docs `docs/process/api-contract-tests.md`.

- Gated by `CONTRACT_BASE_URL`; suites `describe.skipIf(!contractEnabled)` skip when unset so `bun run ci` stays green (`tests/contract/_client.ts:15-19`).
- Auth: the `open_agents_test_user_id=dev-managed-runtime-user` cookie (`apps/web/lib/session/test-auth.ts:3-4`), honored when `NODE_ENV === "development"` or `OPEN_AGENTS_ENABLE_TEST_AUTH=1` (`test-auth.ts:6-11`). The test session impersonates a fixed demo user.
- Coverage today: `auth.test.ts` (10 protected endpoints must 401 unauthenticated, list at `auth.test.ts:9-20`), `reads.test.ts` (GET shape checks for `/api/models`, `/api/settings/preferences`, `/api/settings/skills`, `/api/inference-profiles`, `/api/sessions`, `/api/workflows/catalog`, `/api/usage`), `skills-crud.test.ts` (full round-trip incl. 409/400), `git-routes.test.ts` (401/404/400 and 200-or-409 on sandbox-less sessions; no real git mutations).
- Explicitly out of scope per docs: harness/SSE endpoints, chat streaming, OAuth callbacks, real git pushes.

### Issue #298 (OPEN): contract tests on preview deploys

`https://github.com/dennisonbertram/fork-open-agents/issues/298` — adds a non-required `.github/workflows/contract-tests.yml` triggered by `deployment_status` on preview deployments, pointing `test:contract` at the preview URL with the Vercel protection-bypass header (`x-vercel-protection-bypass`), an `authAvailable` preflight (skip authenticated suites when test-auth is off), and GET retry for transient preview-DB 5xx. **Not yet implemented** (no such workflow file exists; only `ci.yml` and `preview-smoke.yml`). Lineage: #284 created the git HTTP routes + schemas; #293/#295 the contract suite; #302 (closed, shipped as PR #303, merged) the OpenAPI contract + typed client; #298 is the remaining CI automation. #69 ("public API for cloud sandbox agent runs") is an open, broader API ambition.

## 5. Adoption status in the web app (important honesty check)

`createOpenAgentsApiClient` is referenced **only** by `lib/api/client.ts` itself and `lib/api/openapi-spec.test.ts`. **No web UI component or hook consumes the typed client yet** — PR #303 explicitly deferred "migrating existing frontend fetch calls" as a follow-up. The web UI mostly uses server actions and hand-written `fetch`. So the contract is real and gated, but the iOS app would be its **first serious consumer**, which means: (a) untyped response gaps (section 1 caveat) have had no consumer pressure yet, and (b) the iOS effort will surface contract bugs the web app never hits.

## 6. What full iOS-consumed coverage would require

The app has ~118 `route.ts` files under `apps/web/app/api/` (full enumerated list visible in `apps/web/.next/dev/types/routes.d.ts`). The spec covers 6 paths. Surfaces an iOS app needs, by bucket:

**REST-shaped, can be added to the spec with the existing pattern (route Zod schemas exist or are easy):**
- Sessions: `/api/sessions` (GET/POST), `/api/sessions/[sessionId]` (GET/PATCH/DELETE), `/chats`, `/chats/[chatId]`, `/chats/[chatId]/messages`
- Diff/files: `/api/sessions/[sessionId]/diff`, `/diff/cached`, `/diff/patch`, `/files`, `/files/content`
- Remaining git routes already schema'd in `lib/git/http-schemas.ts` but absent from the spec: `git/discard`, `git/pr/generate`, `git/deployment-url`, plus un-schema'd `git/pr/close`, `git/pr/readiness`, `generate-commit-message`
- Settings: `/api/settings/preferences`, `/agents`, `/model-variants`, `/runtime-profiles`, `/composio`; `/api/models`, `/api/inference-profiles`, `/api/usage`
- Repos/GitHub: `/api/github/installations`, `/installations/repos`, `/branches`, `/user`, `/connection-status`, `/api/repos/[owner]/[repo]/dashboard`
- Background agents: `/api/background-agents` CRUD, `/api/background-agent-runs`
- Sandbox status: `/api/sandbox/*`, `/api/sessions/[sessionId]/sandbox`

**NOT OpenAPI-friendly (need a separate iOS strategy, do not pretend the spec covers them):**
- `/api/chat` (POST) returns an AI SDK UI-message stream via `createUIMessageStreamResponse` (`apps/web/app/api/chat/route.ts:1,150,217,371`) — chunked SSE-style protocol; same for `/api/chat/[chatId]/stream` (resume). OpenAPI 3.0 can document the endpoint but not the chunk protocol; iOS needs a hand-built streaming decoder matching the AI SDK UI message chunk format.
- Auth: better-auth handlers at `/api/auth/[...all]` (cookie session, Vercel + GitHub OAuth) — flows, not REST resources.
- Harness SSE (`/api/harness/runs/[runId]/events`) and webhooks.

**Spec hygiene work full coverage forces:**
1. Add `components.schemas` + `$ref` (the builder currently inlines everything; trivial to extend since it's plain object assembly — register shared schemas once and reference them), otherwise Swift codegen produces hundreds of anonymous types.
2. Declare a `securitySchemes` entry (`type: apiKey, in: cookie` for the better-auth session cookie, or a bearer scheme if the iOS app gets token auth) and apply `security` globally — currently absent, and Apple's generator wants it for auth middleware.
3. Replace the three `additionalProperties: {}` mutation responses with real shapes.
4. Decide pagination/query-param conventions (none exist in the spec yet; only `deploymentUrlQuerySchema` shows the `z.coerce` query pattern).

## 7. Can schemas be derived from Zod automatically?

Yes — this already works and is the established mechanism: Zod 4's built-in `z.toJSONSchema(schema, { target: "openapi-3.0", io })`. No extra tooling present or needed for schema conversion. What is **manual** is the document assembly: paths, methods, operationIds, status codes, and response Zod objects are hand-written in `openapi-spec.ts`. There is no route-scanning or decorator system, and no framework (e.g. Hono/zod-openapi) to infer paths. Scaling to ~40-60 operations for iOS means either (a) keep the explicit builder and grow it (predictable, matches the drift gate, my read of repo conventions), or (b) introduce a registry helper so each route module exports its own path-item fragment colocated with the handler. Either way the drift gate (`openapi-spec.test.ts:52-59` + `openapi:check`) keeps working unchanged.

## 8. What Swift codegen can piggyback on

- **Input artifact**: `apps/web/openapi.json` is valid OpenAPI 3.0.3 and committed — Apple's `swift-openapi-generator` (supports 3.0.x/3.1) can consume it directly today; a build step in the iOS repo can vendor or fetch the file. There is **no runtime endpoint serving the spec** (no `/api/openapi` route; the `/openapi.json` string in `apps/web/app/api/harness/ready/route.test.ts:81` refers to the *external harness service's* spec, not this app's).
- **Drift protection**: any backend change to covered routes that touches the imported Zod schemas forces a regenerated `openapi.json` in the same PR (CI test fails otherwise), so the iOS build can treat the committed artifact as authoritative per commit. Consider a CI job in the iOS pipeline that re-runs Swift codegen against the latest `openapi.json` and fails on compile errors — the analog of `openapi-types.ts` for Swift.
- **Runtime verification**: the contract suite (`tests/contract/`) is the proof layer that the live server honors the documented shapes; #298's preview-deploy automation would give iOS continuous backend-contract signal without an iOS test rig. The test-auth cookie (`OPEN_AGENTS_ENABLE_TEST_AUTH=1` + `open_agents_test_user_id`) is the existing machine-auth path a contract/integration harness for iOS could reuse against previews — but it impersonates one fixed demo user and is dev/preview-only; **production iOS auth needs a real session story (cookie capture from a better-auth web flow, or new token auth), which the contract currently does not describe at all.**

## Uncertainties

- I did not find a written roadmap committing to extend OpenAPI coverage beyond "extend as routes adopt explicit schemas" (`openapi-spec.ts:17-18`, `docs/process/api-openapi-contract.md` Scope section); the pace/order of expansion is undecided.
- Whether better-auth can mint long-lived tokens suitable for a native app (vs cookie sessions) is outside this brief's scope — see the auth research brief; the contract-side fact is simply that no security scheme is declared.
- `git/pr/readiness` appears in the contract auth test (`auth.test.ts:19`) and route list but I did not read its handler; shape unknown.
