## Why this matters

The iOS app's single most important non-chat affordance is the one-tap **Resume** banner: when a session's sandbox has hibernated, every VM-touching call returns `409 {"error":"Sandbox is unavailable. Please resume sandbox."}` and the app must show Resume, which calls `PUT /api/sandbox/snapshot`. None of the 7 sandbox lifecycle paths exist in `apps/web/openapi.json` today (6 paths / 10 operations total, none sandbox). Without this batch the generated Swift client (`ios/Packages/OpenAgentsAPI`) cannot type `SandboxStatusResponse` or `SandboxReconnectResponse`, the Resume flow would be hand-rolled and drift-prone, and the epoch-milliseconds lifecycle countdown (sandbox expiry timer in the chat header) would be guesswork. This batch puts the whole sandbox lifecycle under the existing drift gates (`apps/web/scripts/check-openapi.ts` + `apps/web/lib/api/openapi-spec.test.ts`), and upgrades the manually-validated sandbox routes to shared Zod request schemas so the published contract is generated from the exact schemas the handlers enforce.

## User/operator path protected

An iOS (or any non-browser) client polls `GET /api/sandbox/status?sessionId=`, probes `GET /api/sandbox/reconnect?sessionId=`, and resumes a hibernated sandbox with `PUT /api/sandbox/snapshot` — all through generated, spec-checked types. The web app's existing sandbox controls (create, stop, extend, pause, resume, activity ping, attach-sandbox-to-plain-chat) keep byte-identical responses and error strings; the only behavior change is that malformed request bodies (non-string `sessionId`) now get a clean `400` instead of leaking into handler logic.

## Behavior contract

- **Given** a session with no sandbox, **when** the client sends `GET /api/sandbox/status?sessionId=<id>` with a valid session cookie or bearer token, **then** the server returns `200` with `{ status: "no_sandbox", hasSnapshot, lifecycleVersion, lifecycle: { serverTime, state, lastActivityAt, hibernateAfter, sandboxExpiresAt } }`, where every `lifecycle` number is Unix epoch milliseconds (or null) and the spec documents that unit in each field `description` — never `format: date-time`.
- **Given** a session whose sandbox runtime state is persisted, **when** the client sends `GET /api/sandbox/reconnect?sessionId=<id>`, **then** the response `status` is one of `"connected" | "expired" | "not_found" | "no_sandbox"`, `expiresAt` (epoch ms) is present only when connected, and the same `lifecycle` object shape is returned.
- **Given** a paused sandbox (`hasSnapshot: true`), **when** the client sends `PUT /api/sandbox/snapshot` with `{ "sessionId": "<id>" }`, **then** the server returns `200 { success: true, restoredFrom?, sandboxId?, alreadyRunning? }`, or `404 { "error": "No sandbox available for resume" }` when nothing is resumable, or `404 { "error": "Saved sandbox is no longer available. Create a new sandbox." }` when the saved handle is gone.
- **Given** any body-validated sandbox route (`POST /api/sandbox`, `DELETE /api/sandbox`, `POST /api/sandbox/extend`, `POST /api/sandbox/snapshot`, `PUT /api/sandbox/snapshot`, `POST /api/sandbox/activity`), **when** the body is not JSON, **then** `400 { "error": "Invalid JSON body" }`; **when** `sessionId` is missing, empty, or not a string (e.g. `{"sessionId": 123}`), **then** `400 { "error": "Missing sessionId" }`; **when** `POST /api/sandbox` gets `sandboxType` other than `"vercel"`, **then** `400 { "error": "Invalid sandbox type" }`. (The non-string case is the new behavior; today a truthy non-string slips past.)
- **Given** an unauthenticated request to any of the 9 operations, **then** `401 { "error": "Not authenticated" }`; **given** a session owned by another user, **then** `403`/`404` per the existing `requireOwnedSession` behavior — and every operation in the spec documents `401` (the spec unit test enforces this).
- **Given** the server later adds a field to any sandbox response, **when** the generated Swift client decodes it, **then** decoding succeeds because Batch A (M1-01) strips `additionalProperties: false` — this batch must not reintroduce closed objects.
- **Given** a VM-touching route (files/diff/git, documented in Batch D) hibernates mid-session, **when** it returns `409 { "error": "Sandbox is unavailable. Please resume sandbox." }`, **then** the spec's reusable `components.responses.SandboxUnavailable` documents that envelope and names `resumeSandbox` (`PUT /api/sandbox/snapshot`) as the recovery operation — defined in this batch, referenced by Batch D operations.
- **Given** an edit to `buildOpenApiDocument()` without regenerating, **when** CI runs, **then** `bun run --cwd apps/web openapi:check` and the drift test in `apps/web/lib/api/openapi-spec.test.ts` fail.

## Product and design spec

Server-only slice; no UI changes. The "product surface" is the contract itself:

- **Entry point:** `apps/web/openapi.json` (committed artifact) and `apps/web/lib/api/openapi-types.ts` (web typed client), consumed later by `ios/scripts/generate-openapi-client.sh`.
- **Primary flow:** implementer edits `apps/web/lib/api/openapi-spec.ts` plus the sandbox routes, regenerates both artifacts, and CI gates stay green.
- **States and copy:** every user-visible error string is frozen: `"Invalid JSON body"`, `"Missing sessionId"`, `"Invalid sandbox type"`, `"Sandbox not initialized"`, `"No sandbox available for resume"`, `"Saved sandbox is no longer available. Create a new sandbox."`, `"Too many requests"` (429 with `Retry-After`), `"Sandbox is unavailable. Please resume sandbox."` (409, defined for reuse). The web sandbox UI keys off these strings; do not reword them.
- **Permissions:** all 9 operations require an authenticated session and session ownership; none are public.
- **Error/empty/loading:** N/A beyond the envelopes above; `GET /api/sandbox/status` is class F (DB-only) and `GET /api/sandbox/reconnect` is class V (may take seconds while probing the VM) — record both latencies in operation `description`s so client timeout policy (`02-api-contract-and-networking.md` section 4) has a source.

**Component schemas registered via the M1-01 registry (stable names, exact source shapes):**

- `SandboxLifecycle` — from the `lifecycle` object both status and reconnect return (`apps/web/app/api/sandbox/status/route.ts` lines 17–28, `apps/web/app/api/sandbox/reconnect/route.ts` lines 26–38): `{ serverTime: z.number(), state: z.string().nullable(), lastActivityAt: z.number().nullable(), hibernateAfter: z.number().nullable(), sandboxExpiresAt: z.number().nullable() }`. Every number field gets `.describe(...)` containing the phrase `"Unix epoch milliseconds"` (for `serverTime`: `"Server clock at response time, Unix epoch milliseconds"`). **No `format: date-time` anywhere in this schema.**
- `SandboxCreateRequest` — `{ sessionId: z.string().min(1), repoUrl: z.string().optional(), branch: z.string().optional(), isNewBranch: z.boolean().optional(), sandboxType: z.literal("vercel").optional() }` (request `io: "input"`).
- `SandboxSessionRequest` — `{ sessionId: z.string().min(1) }` (shared body of stop/extend/pause/resume/activity).
- `SandboxCreateResponse` — `{ createdAt: z.number().describe("Unix epoch milliseconds when the sandbox became ready"), timeout: z.number().describe("Sandbox timeout duration in milliseconds"), currentBranch: z.string().optional(), mode: z.literal("vercel"), timing: z.object({ readyMs: z.number().describe("Milliseconds from request start to sandbox ready") }) }` (mirrors `apps/web/app/api/sandbox/route.ts` lines 291–297).
- `SandboxStopResponse` — `{ success: z.boolean(), alreadyStopped: z.boolean().optional() }`.
- `SandboxStatusResponse` — `{ status: enum ["active","no_sandbox"], hasSnapshot: boolean, lifecycleVersion: number, lifecycle: $ref SandboxLifecycle }`.
- `SandboxReconnectResponse` — `{ status: enum ["connected","expired","not_found","no_sandbox"], hasSnapshot: boolean, expiresAt?: number (epoch ms, only when connected), lifecycle: $ref SandboxLifecycle }`.
- `SandboxExtendResponse` — `{ success: z.boolean(), expiresAt: z.number().describe("Unix epoch milliseconds when the extended sandbox expires"), extendedBy: z.number().describe("Extension duration in milliseconds (EXTEND_TIMEOUT_DURATION_MS = 1200000)") }` (`apps/web/lib/sandbox/config.ts` line 28).
- `SandboxSnapshotResponse` — `{ snapshotId: z.string().nullable(), createdAt: z.number().describe("Unix epoch milliseconds when the pause completed") }`.
- `SandboxResumeResponse` — `{ success: z.boolean(), restoredFrom: z.string().optional(), sandboxId: z.string().optional(), alreadyRunning: z.boolean().optional() }`.
- `SandboxActivityResponse` — `{ success: z.boolean(), reason: z.string().optional().describe('Present when success is false; "not-active" means the lifecycle is not active so no timer was refreshed') }`.

**Nested `$ref` mechanics:** the M1-01 `ref(name, zodSchema, io)` helper registers whole Zod schemas; it cannot emit a `$ref` *inside* another schema. Add one sibling helper in `apps/web/lib/api/openapi-spec.ts` (skip if M1-02 already added it — check first):

```ts
function makeRawRef(registry: SchemaRegistry) {
  return function rawRef(name: string, schema: JsonSchema): JsonSchema {
    const existing = registry.get(name);
    if (existing && JSON.stringify(existing) !== JSON.stringify(schema)) {
      throw new Error(`OpenAPI schema name collision: ${name}`);
    }
    registry.set(name, schema);
    return { $ref: `#/components/schemas/${name}` };
  };
}
```

Build `SandboxStatusResponse` and `SandboxReconnectResponse` with `rawRef`, composing hand-written JSON Schema whose `lifecycle` property is the `$ref` returned by `ref("SandboxLifecycle", sandboxLifecycleSchema)`. All other sandbox schemas go through the normal Zod `ref(...)` path.

**Reusable 409 component:** add to the document's `components` (alongside `securitySchemes` and `schemas` from M1-01):

```ts
responses: {
  SandboxUnavailable: {
    description:
      'Sandbox is unavailable. Please resume sandbox. The body is the standard error envelope with error === "Sandbox is unavailable. Please resume sandbox." Clients should surface a Resume affordance that calls resumeSandbox (PUT /api/sandbox/snapshot).',
    content: {
      "application/json": {
```

## Observability and user feedback

This slice is contract + validation work in the `sandbox-lifecycle` route family; the rule is **preserve existing structured evidence exactly** and make the contract itself grep-able.

- Existing structured logs that must survive the refactor byte-for-byte (assert by inspection in review): `apps/web/app/api/sandbox/reconnect/route.ts` emits `[Reconnect] session=<sessionId> status=<connected|expired|no_sandbox> hasSnapshot=<bool>` at info (console.log) and `status=expired ... error=<message>` at error; `apps/web/app/api/sandbox/snapshot/route.ts` emits `[Snapshot Restore] session=<sessionId> success=<bool> ... restoredFrom=<handle>` at info/error; `apps/web/app/api/sessions/[sessionId]/sandbox/route.ts` persists the `session.sandbox.attached` event (source `sandbox`, status `info`) via `emitSessionEvent`.

The iOS client (later milestones) maps these envelopes to its typed `errorKind` values from `docs/plans/ios-app/07-observability.md` section 6: 409 envelope → `sandbox_unavailable`, 400 `"Sandbox not initialized"` → `server_reported`, 429 → `http_rate_limited`. The frozen error strings in this issue are that mapping's contract.

## Regression risks and concerns

- **Validation tightening:** non-string `sessionId` bodies now 400. Audit the web callers before merging (`grep -rn "api/sandbox" apps/web/app apps/web/lib --include="*.ts" --include="*.tsx"`) — they all send string IDs, but confirm; any caller relying on coercion is a pre-existing bug to fix in the same PR.
- **Error-string drift:** the web sandbox UI and the planned iOS errorKind mapping key off exact strings; the safeParse refactor must reproduce `"Missing sessionId"` / `"Invalid sandbox type"` byte-for-byte (unit tests pin this).
- **Lifecycle-timer semantics:** `POST /api/sandbox/activity` deliberately refreshes only `lastActivityAt`/`hibernateAfter`; the refactor must not touch `buildLifecycleActivityUpdate` usage or reorder the `lifecycleState !== "active"` early return.
- **Registry collisions:** if M1-02 named the session wrapper something other than `SessionResponse`, reuse its name — a divergent re-registration throws at build time (good) but blocks generation until resolved.
- **Artifact churn:** `openapi.json` and `openapi-types.ts` diffs are large but mechanical; reviewers should check the builder diff, not the artifacts. Never hand-edit `apps/web/openapi.json`.
- **DELETE-with-body codegen:** `stopSandbox` carries a JSON body on DELETE; `openapi-typescript` already handles this (`deleteSkill` precedent). Flag in the PR notes that the future Swift generator run must be verified against it in the M2 client milestone.
- **Reconnect latency in contract tests:** the suite only exercises the no-runtime-state path (DB-only, fast); do not add a live-VM reconnect assertion — that belongs to managed-runtime proof tooling, not this harness.

## Deploy or migration impact

None. No database schema change, no migration, no new env vars, no runtime infra. The spec is built at development time and committed; routes keep identical success responses. Preview and production deploys are unaffected beyond the stricter 400 on malformed sandbox bodies (no known caller). Both committed artifacts (`apps/web/openapi.json`, `apps/web/lib/api/openapi-types.ts`) must land in the same PR as the builder change or `openapi:check` blocks CI.
