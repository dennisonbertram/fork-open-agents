## Why this matters

The iOS app's generated Swift client (`ios/Packages/OpenAgentsAPI`) can only call what `apps/web/openapi.json` documents. Batch F is the final route-addition batch: GitHub connection and repo discovery (repo picker, onboarding), the Repo Dashboard, the Vercel project picker, the entire Background Agents surface, session observability/skills/runtime-profile reads, the public shared-chat status probe, and the native-auth bootstrap surface (`/api/auth/info` plus the `/api/native-auth/*` routes created in M0-01 and M0-03). After this issue merges, every generated-client endpoint the iOS app consumes in v1 is spec-documented and drift-gated, which closes the contract-expansion acceptance item in `docs/plans/ios-app/04-auth.md` section 12 and unblocks the iOS codegen milestone.

## User/operator path protected

Every generated-client endpoint the iOS app consumes is documented in `apps/web/openapi.json`, with the spec builder (`apps/web/lib/api/openapi-spec.ts`) and both committed artifacts (`apps/web/openapi.json`, `apps/web/lib/api/openapi-types.ts`) regenerated together in the same PR. Concretely: an iOS user picking a repo, opening the Repo Dashboard, managing background agents, watching a run detail, or opening a shared chat from a deep link relies on response shapes that can no longer silently drift, because `bun run --cwd apps/web openapi:check` and `apps/web/lib/api/openapi-spec.test.ts` fail on any divergence.

## Behavior contract

- Given the merged PR, when `bun run --cwd apps/web openapi:check` runs, then it exits 0 and prints `✓ openapi.json is in sync with openapi-spec.ts`, and `apps/web/openapi.json` contains all 23 Batch F paths / 25 operations listed in the Integration spec below, each with a unique `operationId`.
- Given the regenerated `apps/web/openapi.json`, when `grep -c '"additionalProperties": false' apps/web/openapi.json` runs, then it returns `0` (the M1-01 stripper applies to every new schema), and every new ISO timestamp field (`createdAt`, `updatedAt`, `startedAt`, `finishedAt`, `testedAt`, `lastActivityAt`) carries `"format": "date-time"`.
- Given an unauthenticated request, when `GET /api/shared/{shareId}/status` is called with a valid shareId, then the live route returns 200 `{ "isStreaming": boolean }` with no auth, and the spec documents the operation with `security: []`, a 200 `SharedChatStatusResponse`, a 404 `ErrorResponse`, and no 401 (allowed because `getSharedChatStatus` is in the test's public allowlist).
- Given an unauthenticated request, when `GET /api/auth/info` is called, then the live route returns HTTP 200 with `{ "user": undefined }` serialized as `{}` (verified in `apps/web/app/api/auth/info/route.ts` — it never returns 401), and the spec documents only a 200 `SessionUserInfo` response, with `getAuthInfo` added to the 401-omission allowlist in `apps/web/lib/api/openapi-spec.test.ts`.
- Given a bearer-authenticated `POST /api/native-auth/sign-out`, when the spec is consulted, then it documents 200 `{ success: boolean }` and 401 `ErrorResponse`, matching the route created in M0-03 (`apps/web/app/api/native-auth/sign-out/route.ts`).
- Given `GET /api/native-auth/complete` and `GET /api/native-auth/bridge`, when the spec is consulted, then `completeNativeAuth` documents only a 303 redirect response (Location header description: `openagents://auth?ott=...` or `openagents://auth?error=...`; this route never returns 401 — errors are redirects), and `bridgeNativeAuth` documents 303, 400 `ErrorResponse`, and 401 `ErrorResponse`.
- Given `GET /api/repos/{owner}/{repo}/dashboard` fails entirely, when the 500 response is documented, then its schema includes both `error: string` and `errorKind: string` (the route returns `{ error: "Dashboard data unavailable", errorKind: "unknown_dashboard_failure" }` — verified in `apps/web/app/api/repos/[owner]/[repo]/dashboard/route.ts`).
- Given two registered schemas with the same name but different shapes, when `buildOpenApiDocument()` runs, then it throws `OpenAPI schema name collision: <name>` (M1-01 registry behavior) and the unit test fails — no silent overwrite.
- Given `CONTRACT_BASE_URL` is set against a running server with `OPEN_AGENTS_ENABLE_TEST_AUTH=1`, when `bun run --cwd apps/web test:contract` runs, then the new Batch F contract tests pass; given `CONTRACT_BASE_URL` is unset, then they skip and `bun --bun run ci` stays green.
- Given a developer edits `apps/web/lib/api/openapi-spec.ts` without regenerating, when `bun run --cwd apps/web openapi:check` runs, then it exits 1 with the regenerate instruction, and the in-sync test in `apps/web/lib/api/openapi-spec.test.ts` fails.

## Product and design spec

This is a server-side contract slice; there is no new UI. The "product surface" is the committed `apps/web/openapi.json`, consumed later by `ios/scripts/generate-openapi-client.sh` (vendored copy, Swift codegen). The iOS screens that depend on these contracts (from `docs/plans/ios-app/02-api-contract-and-networking.md` section 1):

- Repo picker step 1/2 and branch picker: `listInstallations`, `listInstallationRepos`, `listBranches`.
- Onboarding and Settings > Connections: `getGitHubConnectionStatus` (polled after the GitHub App install round-trip), `getGitHubUser`, `getOrgsInstallStatus`.
- Repo Dashboard: `getRepoDashboard`.
- New Session Vercel project picker: `listVercelRepoProjects`.
- Background Agents list/editor/runs: the nine background-agent operations.
- Observability panel, composer slash-commands, runtime-mode selector: `getSessionObservability`, `listSessionSkills`, `listSessionRuntimeProfiles`.
- Shared-chat viewer deep link (public, signed-out): `getSharedChatStatus`.
- App-launch bootstrap and Settings: `getAuthInfo`, `signOutNative`; sign-in/bridge sheets: `completeNativeAuth`, `bridgeNativeAuth`.

Error/empty/loading behavior, copy, and accessibility for those screens are owned by the iOS milestone issues, not this one. Operator-facing behavior here: the two drift gates fail loudly with actionable messages (regenerate command in the output), and the contract suite gives a deployable smoke against previews.

Query/path parameters (declare inline as OpenAPI `parameters`):

- `listInstallationRepos`: `installation_id` (required), `query`, `limit` (1–100, default 50).
- `listBranches`: `owner` (required), `repo` (required), `limit`, `query`.
- `getRepoDashboard`: path params `owner`, `repo`.
- `listVercelRepoProjects`: `repoOwner` (required), `repoName` (required).
- `getBackgroundAgentReadiness`: `repoOwner`, `repoName`, `permission` (all optional; `repoOwner`/`repoName` must be both-or-neither — say so in the parameter descriptions).

- `getSessionObservability`: `chatId`, `limit` (1–500, default 150).
- `listSessionSkills`: `refresh` (optional, `"1"` forces a sandbox re-scan).
- `bridgeNativeAuth`: `ott` (required), `next` (optional, sanitized server-side).
- `completeNativeAuth`: `error` (optional, OAuth error passthrough).

Test allowlist changes in `apps/web/lib/api/openapi-spec.test.ts`: M1-01 added `publicOperationIds` containing `listModels` and `getSharedChatStatus`. Verify `getSharedChatStatus` is present (add if missing) and extend the allowlist with `getAuthInfo`, `completeNativeAuth`, and `bridgeNativeAuth`-style exceptions as required: `getAuthInfo` and `completeNativeAuth` never return 401 so they must be allowed to omit it; `bridgeNativeAuth` documents 401 normally. Data model: none. No schema or migration changes. All request validation stays as-is — Batch F is GET-heavy and the only request bodies (`createBackgroundAgent`, `updateBackgroundAgent`) already validate with Zod schemas in `apps/web/lib/background-agents/types.ts`; no `http-schemas.ts` extraction is needed in this batch. Note in the spec descriptions that the background-agent create/update schemas are strict server-side (unknown keys rejected) even though the published schema is open after M1-01 stripping.

Compatibility: regenerating `apps/web/lib/api/openapi-types.ts` may surface type errors in web consumers of `createOpenAgentsApiClient` (`apps/web/lib/api/client.ts`) — fix forward in the same PR. The native-auth and shared-status operations are documented for contract completeness; the iOS generation script's hand-rolled exclusion list (`docs/plans/ios-app/02-api-contract-and-networking.md` section 3.3) is unaffected.

## Observability and user feedback

This slice changes contract artifacts and tests, not runtime behavior; observability is about the gates and the already-instrumented routes the spec now documents.

- Named module: the spec builder `apps/web/lib/api/openapi-spec.ts`. Its registry throws `OpenAPI schema name collision: <name>` at build/test time (error, surfaced by `bun test` and `openapi:check`) — never a silent overwrite. `apps/web/scripts/check-openapi.ts` prints `✓ openapi.json is in sync with openapi-spec.ts` on success and the exact regenerate command on drift (exit 1).
- Existing structured events this batch makes contractual: the `repo-dashboard` service (in `apps/web/app/api/repos/[owner]/[repo]/dashboard/route.ts`) emits `repo-dashboard.fetch.completed` at info with `{ service, userId, repoOwner, repoName, requestId, latencyMs, partialFailureCount }` and `repo-dashboard.fetch.failed` at error with `{ ..., errorKind }`. Typed errorKind values documented in the 500 schema: `unknown_dashboard_failure`; per-window `errorKind: "provider_unavailable"` rides inside 200 bodies. Correlation ID: `requestId` (the route honors inbound `x-request-id`).
- Redaction rules: `apps/web/openapi.json` is a committed public artifact — no real tokens, shareIds, OTT values, user IDs, or example bearer headers in `description`/`example` fields. The `completeNativeAuth`/`bridgeNativeAuth` descriptions must reference the OTT parameter by name only, never a sample value. ## Regression risks and concerns

- Mis-transcribed response shapes become contractual lies that break Swift decodes later. Mitigation: every schema is written from the route source (files named above), not from memory; contract tests assert live shapes for the four named surfaces.
- The top-level-array responses (`listInstallations`, `listInstallationRepos`) and bare-object `getGitHubUser` are easy to wrongly wrap in envelopes — the coverage test cannot catch this; the contract tests and reviewer must.
- Allowlist amendments touch a shared test that M1-02..M1-05 also rely on; a careless edit could let a future operation skip its 401 documentation. Keep the allowlist literal and minimal (exactly the operations named here).
- Regenerated `openapi-types.ts` can break web consumers of `apps/web/lib/api/client.ts`; `turbo typecheck --filter=web` is in the checklist.
- Merge-order hazard: this issue races siblings M1-02..M1-05 in `openapi-spec.ts` and `openapi.json`; after any rebase/merge of `origin/develop`, re-run the regeneration pair and `openapi:check` before pushing.
- If M0-01/M0-03 have not merged, the native-auth operations would document nonexistent routes — verify `apps/web/app/api/native-auth/complete/route.ts`, `apps/web/app/api/native-auth/sign-out/route.ts`, and `apps/web/app/api/native-auth/bridge/route.ts` exist in the checkout before starting; stop and report if they do not.
- The background-agent contract round-trip writes real rows for the test-auth user; it must delete the agent it creates even on assertion failure (use try/finally) to keep preview databases clean.
