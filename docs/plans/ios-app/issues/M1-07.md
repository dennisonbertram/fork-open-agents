## Why this matters

Vercel BotID gates nine production API routes with `checkBotProtection()` (`apps/web/lib/botid.ts`). The web client passes because `apps/web/instrumentation-client.ts` registers BotID client protection, which transparently attaches browser challenge headers. A native iOS client has no browser JS runtime and cannot produce those headers, so in production every BotID-gated call from the app — most critically `POST /api/chat`, the core chat-send path — is expected to return `403 {"error":"Access denied"}`. Until this is resolved, the iOS app cannot send a single chat message against production. Separately, `usage_events.source` only admits `"web"` (`apps/web/lib/db/schema.ts` line 1809, `apps/web/lib/db/usage.ts` line 8), so native-originated assistant turns would be misattributed as web traffic on the Usage screen and in operator analytics. This issue resolves both server enablers and records the resulting contract so the iOS `APIError.forbidden` / BotID-signature mapping (`02-api-contract-and-networking.md` section 4.2) is grounded in verified behavior, not guesswork.

## User/operator path protected

Chat send from a bearer-authenticated native client is never blocked by bot protection in production: an iOS user who signed in via the M0-01 deep-link handoff can `POST /api/chat` (and hit every other BotID-gated route) with `Authorization: Bearer <token>` and no cookies, and receive the normal route response instead of `403 Access denied`. Secondary operator path: the Usage screen and `usage_events` queries attribute native turns to `source = "ios"` instead of silently folding them into `"web"`.

## Behavior contract

- **Given** a request to a BotID-gated route in production carrying a valid `Authorization: Bearer <token>` header (session resolves via the better-auth bearer plugin from M0-01) and no BotID browser challenge headers, **when** the route reaches `checkBotProtection()`, **then** the bot check is bypassed (`{ isBot: false, bypassed: true }`), the route proceeds normally, and a `bearer-exemption-applied` event is logged.
- **Given** a browser request authenticated by the better-auth session cookie (no `Authorization` header), **when** the route reaches `checkBotProtection()`, **then** `checkBotId(botIdConfig)` runs exactly as today — web behavior is unchanged.
- **Given** a scripted request with a stolen/copied session cookie, no `Authorization` header, and no browser challenge headers, **when** BotID classifies it as a bot, **then** the route still returns `403 {"error":"Access denied"}` — the exemption never weakens the cookie path.
- **Given** an unauthenticated request (no valid cookie, no valid bearer token) to any gated route, **when** the route runs, **then** it returns `401` from the auth check *before* `checkBotProtection()` is ever consulted — the exemption can never open an unauthenticated path because every gated route validates the session first.
- **Given** a request with a non-bearer `Authorization` header (for example `Authorization: Basic ...`) or a malformed value (`Bearer` with no token), **when** `checkBotProtection()` runs in production, **then** no exemption applies and `checkBotId(botIdConfig)` runs.
- **Given** `NODE_ENV !== "production"` or test auth enabled (`OPEN_AGENTS_ENABLE_TEST_AUTH=1`), **when** `checkBotProtection()` runs, **then** the existing dev/test bypass behavior is byte-identical to today.
- **Given** a chat turn started by `POST /api/chat` with a bearer-authenticated request, **when** the workflow finishes and `recordWorkflowUsage` runs, **then** the inserted `usage_events` rows (main agent and aggregated subagent rows) carry `source: "ios"`; a cookie-authenticated turn carries `source: "web"`; an absent `clientSource` defaults to `"web"`.
- **Edge — BotID 403 contract for iOS:** when a future regression or a non-exempt path does return the BotID block, the response stays exactly `403` with body `{"error":"Access denied"}` — this string is the stable signature the iOS `APIErrorMapper` keys on; do not change it.

## Product and design spec

This is a server-only slice; there is no new web UI.

- **Entry point:** any native (non-browser) HTTP request to the BotID-gated routes: `POST /api/chat`, `POST /api/sessions`, `POST /api/sandbox`, `DELETE /api/sandbox`, `POST /api/sandbox/extend`, `POST /api/generate-title`, `POST /api/generate-pr`, `POST /api/transcribe`, `POST /api/sessions/{sessionId}/generate-commit-message`, `POST /api/settings/skills/generate`.
- **Primary flow:** authenticated bearer request → bot check bypassed → normal route behavior (stream, JSON, rate limits, ownership checks all unchanged).
- **States:** (1) bearer bypass (new), (2) dev/test bypass (existing, unchanged), (3) BotID verdict pass (existing), (4) BotID verdict block → `403 {"error":"Access denied"}` (existing, body frozen as contract).
- **Copy:** the 403 body string `"Access denied"` is contractual; iOS surfaces its own user-facing message ("This network request was blocked. Update the app or try again.") keyed off that signature — server copy must not change.
- **Permissions:** the exemption applies only after the route has already validated a session; it grants no access of its own. Residual risk (an authenticated user scripting the API with their own bearer token) is accepted and bounded by the existing per-user rate limits (sessions 10/min, sandbox create 20/min, sandbox delete 10/min, extend 3/min, generate-title 10/min, transcribe 5/min, generate-pr 5/min, generate-commit-message 10/min, skills/generate 10/min) and by chat ownership + duplicate-workflow 409 guards.
- **Error/empty/loading behavior:** unchanged for web. Accessibility: not applicable (no UI).

## Integration spec

- **Routes touched (read + ordering audit only, no logic edits):** the nine gated route files listed below under the todo checklist. Logic changes are centralized in `apps/web/lib/botid.ts`, so all call sites inherit the exemption without per-route edits.
- **`apps/web/lib/botid.ts`:** `checkBotProtection()` gains a bearer pass-through. It reads request headers via `headers()` from `next/headers` (already the pattern in `apps/web/lib/session/get-server-session.ts`), checks `authorization` against `/^Bearer .+$/`, and returns the bypass object when matched. Add a doc comment stating the call-order contract: *callers must validate the session before calling `checkBotProtection()`*.
- **New helper:** `apps/web/lib/auth/bearer-detection.ts` exporting `isBearerAuthenticatedRequest(headers: Headers): boolean` (pure, testable), shared by `lib/botid.ts` (with `await headers()`) and `app/api/chat/route.ts` (with `req.headers`) so the BotID exemption and the usage attribution can never disagree on what "bearer" means.
- **Data model:** `apps/web/lib/db/schema.ts` `usageEvents.source` enum becomes `["web", "ios"]`; `apps/web/lib/db/usage.ts` `UsageSource` becomes `"web" | "ios"`. - **Attribution wiring:** `POST /api/chat` (`apps/web/app/api/chat/route.ts`, `start(runAgentWorkflow, [...])` call around line 307) passes `clientSource: isBearerAuthenticatedRequest(req.headers) ? "web"` for both the main-agent and subagent `recordUsage` calls.
- **Events/services/observability:** see Observability and user feedback.
- **API surfaces:** no OpenAPI spec change (that is M1-01..M1-06 territory). No response-shape change anywhere.
- **Compatibility:** web cookie flow untouched; usage queries (`apps/web/lib/db/usage.ts` `getUsageHistory`, `apps/web/lib/usage/compute-insights.ts`) group by `source` generically and need no changes — new `"ios"` rows surface additively.

## Observability and user feedback

- **Module:** `botid` — structured single-line JSON on stdout from `apps/web/lib/botid.ts`, shape `{ service: "botid", event, ...fields }`.
- **Events:**
  - `bearer-exemption-applied` — level info — fields `{ requestId }` (read from the `x-request-id` request header; `null` when absent). Emitted once per exempted call.
  - `blocked` — level warn — fields `{ requestId, errorKind: "bot_detected", isVerifiedBot }`. Emitted whenever `checkBotId` returns `isBot: true` (the request the route will 403).
- **Typed error kinds:** server-side log `errorKind` value `bot_detected`. Client-facing contract: HTTP `403` with body exactly `{"error":"Access denied"}` — the iOS `APIErrorMapper` maps this to `APIError.forbidden` with the BotID signature and logs `errorKind: http_forbidden` under OSLog category `api` (subsystem `com.openagents.ios`, taxonomy in `docs/plans/ios-app/07-observability.md`); this issue freezes the server side of that pair.
- **Correlation IDs:** `requestId` only. The iOS client sends `x-request-id: ios-<uuid>` on every request (`02-api-contract-and-networking.md` section 4.1), so exemption events from native traffic are recognizable by the `ios-` prefix. Do not log `userId`, `sessionId`, or `chatId` from `lib/botid.ts` — they are not in scope at that layer.
- **Redaction rules:** never log the `Authorization` header value, any token, the `Cookie` header, or request bodies. The `bearer-exemption-applied` event carries only `requestId`. Existing BotID verdict internals from `checkBotId` are not logged beyond `isVerifiedBot`.
- **Usage attribution evidence:** `usage_events.source` is queryable directly; no new events needed.
- **Debug recipes:**
  - Native exemptions in the last hour: `vercel logs <prod-deployment-url> | grep '"service":"botid"' | grep '"event":"bearer-exemption-applied"' | grep '"requestId":"ios-'`
  - Blocked requests during an incident: `vercel logs <prod-deployment-url> | grep '"service":"botid"' | grep '"errorKind":"bot_detected"'`
  - Attribution check (Neon SQL console): `select source, count(*), max(created_at) from usage_events where created_at > now() - interval '1 day' group by source;`
  - One request end-to-end: take the `x-request-id` from the iOS log archive, then `vercel logs <url> | grep '<request-id>'`.

## Regression risks and concerns

- **Widening the bypass too far:** a bug that matches any `Authorization` header (not strictly `Bearer <token>`) or that skips `checkBotId` for cookie traffic would gut bot protection for the web app. Mitigated by the truth-table unit tests and the pinned cookie-path test.
- **Ordering inversion:** if a future route calls `checkBotProtection()` before session validation, the exemption would apply to unauthenticated traffic carrying a junk bearer header. BotID is then skipped for a request that will still 401 — low impact, but the doc comment plus the ordering audit keep this visible.
- **Abuse via self-owned tokens:** authenticated users can now script gated routes without browser challenges. Accepted: per-user rate limits cover every gated route except `POST /api/chat`, which is bounded by session/chat ownership and the duplicate-workflow 409 guard. Flag any observed abuse via the `bearer-exemption-applied` log volume.
- **Usage misattribution:** if `clientSource` defaults wrongly, web turns could show as `ios` (or vice versa). Pinned by the default-`"web"` test; the bearer detector is shared with the BotID path so the two cannot diverge.
