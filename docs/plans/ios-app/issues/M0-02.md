## Why this matters

App Store guideline 4.8 ("Login Services") requires that an app whose primary account setup uses a third-party login service offer an equivalent privacy-preserving option. The iOS app's primary identity is Vercel OAuth, which qualifies as third-party, so the app must ship Sign in with Apple in v1 or risk rejection at review (the "client for a specific third-party service" exemption is a reviewer-dependent gamble the plan explicitly does not take — `docs/plans/ios-app/04-auth.md` section 3.4 and section 13). The native Apple flow is idToken-based: the device mints an identity token via `ASAuthorizationAppleIDProvider`, and the server verifies it against Apple's JWKS in a single `POST /api/auth/sign-in/social` call — no browser, no deep link, no OTT. This slice makes `apps/web` able to accept that call. It is a server-only PR; no Swift work can build the Apple sign-in screen until it lands in `develop`.

## User/operator path protected

A native client POSTs `/api/auth/sign-in/social` with body `{"provider":"apple","idToken":{"token":"<Apple identity token>","nonce":"<raw nonce string>"}}` and receives an HTTP 200 session response plus a `set-auth-token` response header (the signed bearer token from M0-01's `bearer()` plugin), establishing a fully working bearer session for every subsequent API call. This is the server half of iOS protected path P1 in `docs/plans/ios-app/06-testing-strategy.md` section 2 ("A user can sign in with Vercel OAuth (or Sign in with Apple) and the session survives app relaunch"). Web sign-in (Vercel OAuth, GitHub linking, cookies) must not change.

## Behavior contract

- **Happy path (native Apple sign-in).** Given the `apple` social provider is configured with `APPLE_APP_BUNDLE_IDENTIFIER=com.openagents.ios`, and a client holds a genuine Apple identity token whose `aud` claim is `com.openagents.ios` and whose `nonce` claim is the string `n1`, when the client sends `POST /api/auth/sign-in/social` with `{"provider":"apple","idToken":{"token":"<jwt>","nonce":"n1"}}` and header `Origin: openagents://`, then the response is HTTP 200 with user + session JSON, the response carries a `set-auth-token` header (per `docs/plans/ios-app/04-auth.md` section 3.9, row "`POST /api/auth/sign-in/social` with `idToken`"), a `users` row exists with `username` derived by `deriveAuthUsername`, and an `accounts` row exists with `providerId = "apple"`.
- **Invalid token.** Given the provider is configured, when the client sends the same request with `idToken.token` set to a string that is not a valid Apple-signed JWT (malformed, expired beyond 1 h `maxTokenAge`, wrong issuer, or tampered signature), then the response is HTTP 401 with better-auth error code `INVALID_TOKEN`, and no user or session row is created.
- **Nonce mismatch.** Given a structurally valid Apple identity token whose `nonce` claim is `n1`, when the request body carries `idToken.nonce: "n2"`, then verification fails and the response is HTTP 401 `INVALID_TOKEN`. Comparison is **verbatim string equality** (`jwtClaims.nonce !== nonce` in the better-auth Apple provider) — the server must never hash the incoming nonce, and the config must not introduce any hashing layer.
- **Audience mismatch.** Given a token whose `aud` claim is not `APPLE_APP_BUNDLE_IDENTIFIER`, then verification fails with HTTP 401 `INVALID_TOKEN`. (better-auth validates the audience as `audience ?? appBundleIdentifier ?? clientId`; `appBundleIdentifier` is load-bearing because device-minted tokens carry `aud = <bundle id>`, not the Services ID.)
- **Unconfigured deployment.** Given the three `APPLE_*` env vars are unset (provider registered with empty strings), when an Apple sign-in request arrives, then it fails with HTTP 401 `INVALID_TOKEN` (no Apple-signed token has an empty-string audience). It never returns a 500, and Vercel/GitHub sign-in is unaffected.
- **Subsequent sign-ins (sparse profile).** Given Apple sends `email` and `name` only on the first authorization, when a returning user's token carries only the stable `sub`, then the existing user row is matched via the `accounts` row and sign-in succeeds; `mapAppleProfileToUser` must tolerate absent `email`/`name` (username derivation falls back to `user-<first 12 chars of sub>` per `apps/web/lib/auth/username.ts`).
- **Account linking.** Given `accountLinking.trustedProviders` now includes `"apple"`, when an Apple sign-in carries an email matching an existing user, then better-auth links the Apple account to that user instead of failing (existing `allowDifferentEmails: true` behavior unchanged for Vercel/GitHub).
- **Secret generation script.** Given `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (PKCS8 `.p8` contents), and `APPLE_CLIENT_ID` env vars, when the operator runs `bun run apps/web/scripts/generate-apple-client-secret.ts`, then stdout is a single ES256 JWT with header `{alg: "ES256", kid: <APPLE_KEY_ID>}` and claims `iss = <APPLE_TEAM_ID>`, `sub = <APPLE_CLIENT_ID>`, `aud = "https://appleid.apple.com"`, `exp - iat` = 179 days (Apple max is 180). When any env var is missing, the script prints the list of required vars to stderr and exits 1.
- **Web regression guard.** Given this PR, when the existing test suite and `bun --bun run ci` run, then all pre-existing auth behavior (Vercel sign-in, GitHub linking, M0-01 bearer/OTT tests) stays green.

## Product and design spec

This is a server-only slice; there is no UI change in `apps/web`. The "product surface" is the API contract and the operator experience:

- **Entry point:** `POST /api/auth/sign-in/social` served by the existing better-auth catch-all `apps/web/app/api/auth/[...all]/route.ts` (no route file changes — the provider registration in config is the entire wiring).
- **Primary flow:** native client flow per `docs/plans/ios-app/04-auth.md` section 5 (the exact 5-step chain). The iOS `SignInWithAppleButton` rendering with equal prominence to the Vercel button is a downstream iOS issue and explicitly not here.
- **States/errors:** success = 200 + session JSON + `set-auth-token` header; failure = 401 `INVALID_TOKEN` or 404 `PROVIDER_NOT_FOUND`/`ID_TOKEN_NOT_SUPPORTED` JSON envelopes (better-auth-owned copy; do not customize messages in this slice). No loading/empty states server-side.
- **Permissions:** the endpoint is public (it IS sign-in). No session required. Origin validation is skipped for cookie-less requests and `openagents://` is a trusted origin after M0-01.
- **Operator-facing copy:** `apps/web/.env.example` comments for the three new env vars (exact text in the checklist below) and the script usage comment block. The PR description documents the Apple Developer portal prerequisites (section 3.4.1 of the auth plan): App ID `com.openagents.ios` with the Sign in with Apple capability, a `.p8` Sign in with Apple key with recorded Key ID and Team ID, and the note that a Services ID is only needed if the web app later adds an Apple button.
- **Accessibility:** n/a (no UI).

- **Dependencies:** `jose` is already a direct dependency of `apps/web` (`"jose": "^6.1.3"` in `apps/web/package.json`) — do not add anything. `better-auth` stays at `^1.6.5`.
- **Data model:** no schema change, no migration. Apple users land in the existing `users`, `accounts` (with `providerId = "apple"`), and `auth_sessions` tables.
- **Verified library behavior (pinned facts, better-auth 1.6.5 dist):** the sign-in handler at `apps/web/node_modules/better-auth/dist/api/routes/sign-in.mjs` resolves the provider (404 `PROVIDER_NOT_FOUND` if absent), then for `idToken` bodies calls `provider.verifyIdToken(token, nonce)` and throws 401 `INVALID_TOKEN` on false. The Apple provider (`@better-auth/core` dist, `social-providers/apple.mjs`) verifies against Apple's remote JWKS with `issuer: "https://appleid.apple.com"`, `maxTokenAge: "1h"`, `audience: options.audience?.length ? options.audience : options.appBundleIdentifier ? options.appBundleIdentifier : options.clientId`, and compares `if (nonce && jwtClaims.nonce !== nonce) return false`. A malformed token fails in `decodeProtectedHeader` **before any network call** — this is what makes the 401 route test deterministic and offline.
- **Compatibility:** purely additive. The `set-auth-token` header on the idToken sign-in response is produced by M0-01's bearer plugin after-hook (this issue adds no header logic). OpenAPI: `/api/auth/sign-in/social` is better-auth-owned and stays outside `apps/web/openapi.json`; the auth-surface contract work is M1-06, not here.

## Observability and user feedback

- **User-visible status:** a native client observes success as HTTP 200 + `set-auth-token` header on `POST /api/auth/sign-in/social`, and failure as a 401/404 JSON envelope. The iOS app (downstream issue) maps these to the `auth_signin_succeeded` / `auth_signin_failed { flow: "apple", error_kind }` OSLog events defined in `docs/plans/ios-app/07-observability.md` section 4.1; this server slice is what makes those client events meaningful.
- **Named module:** `better-auth` (the library's context logger inside the catch-all `apps/web/app/api/auth/[...all]/route.ts`) is the structured-event source for this slice. No new server logging code is in scope — the scope boundary is config + script only.
- **Events (existing, verified in `apps/web/node_modules/better-auth/dist/api/routes/sign-in.mjs`):**
  - `Provider not found. Make sure to add the provider in your auth config` at **error** level with `{ provider: "apple" }` — fires only on misconfigured deployments (regression signal that the provider was dropped from config).
  - `Invalid id token` at **error** level with `{ provider: "apple" }` — fires on every failed verification (bad signature, audience mismatch, nonce mismatch, expired token).
  - Both reach stdout and therefore Vercel runtime logs.
- **Typed error kinds:** the stable better-auth response `code` values are the error taxonomy for this surface: `PROVIDER_NOT_FOUND` (404), `ID_TOKEN_NOT_SUPPORTED` (404), `INVALID_TOKEN` (401). The iOS client maps the 401 to `error_kind=http_unauthorized` and passes the server code through as `server_error_kind` per `docs/plans/ios-app/07-observability.md` section 6 — never rename these codes server-side.
- **Correlation IDs:** honest limitation — the better-auth pipeline does not echo `x-request-id` (the harness `getRequestId` helper only covers app routes). Correlation for failed Apple sign-ins = Vercel's per-request log id + timestamp + the `provider: "apple"` field. The iOS client still sends `x-request-id: ios.<uuid>` on the request (visible in access logs even though unechoed). Do not add new headers in this slice.
- **Redaction rules:** never log the identity token, the nonce value, `APPLE_CLIENT_SECRET`, or `APPLE_PRIVATE_KEY` (`docs/plans/ios-app/04-auth.md` section 11.1 and `docs/process/observability-discipline.md`). The script writes the JWT to stdout only (the operator handles it as a secret; it is never written to disk or committed). The only permitted script output besides the JWT is the missing-env message, which names variables but never values. The PR attaches the section 11.7 grep proof.
- **Debug recipes:**
  - Local reproduce (expects 401 + `INVALID_TOKEN` once configured; 404 + `PROVIDER_NOT_FOUND` proves the provider is missing):

    ```bash
    curl -i -X POST http://localhost:3000/api/auth/sign-in/social \
      -H "content-type: application/json" -H "origin: openagents://" \
      -d '{"provider":"apple","idToken":{"token":"not-a-jwt","nonce":"probe"}}'
    ```

  - Production triage for a user who cannot sign in with Apple: `vercel logs <deployment-url> | grep "Invalid id token"` (audience mismatch from a wrong `APPLE_APP_BUNDLE_IDENTIFIER` is the most likely cause) and `vercel logs <deployment-url> | grep "Provider not found"` (env/config regression).

## Regression risks and concerns

- **Breaking existing sign-in:** any typo in `socialProviders` could break Vercel/GitHub auth. Mitigation: the change is additive (new key + one array element), the wiring test asserts all three providers, and the full suite runs in CI.
- **Account-linking semantics change:** trusting `"apple"` means an Apple sign-in with a matching email links to an existing user. This is the intended design (one human, one account), but it widens the linking surface; `allowDifferentEmails: true` is pre-existing and unchanged. Apple private-relay emails make accidental collisions effectively impossible.
- **Nonce hashing trap:** Firebase-style flows SHA-256 the nonce before putting it in the request; better-auth compares **verbatim**. Add a one-line comment above the `apple` config block ("nonce is compared verbatim — never hash across the client/server boundary") so a future "hardening" change does not silently break every native sign-in.
- **Audience misconfiguration:** setting `APPLE_APP_BUNDLE_IDENTIFIER` to anything other than the iOS bundle id (`com.openagents.ios`, pinned in the plan) makes all native sign-ins 401. The `.env.example` comment and the debug recipe cover diagnosis.
- **Client-secret expiry (≤180 days):** native idToken verification uses Apple's JWKS only — it does **not** consume `APPLE_CLIENT_SECRET` — so native sign-in survives secret expiry; only a future web-side Apple button would break. The rotation duty still lands in the release checklist (`docs/plans/ios-app/08-ci-cd-release.md`).
- **Secret leakage via the script:** the script must never read the `.p8` from a hardcoded path or write any file; env-in, stdout-out only. The security grep in the checklist is the gate.
- **`authProvider` cosmetic gap:** Apple-only users report `authProvider: "vercel"` from `GET /api/auth/info`. Known, accepted, and explicitly deferred to the follow-up issue; the iOS app is forbidden from branching on this field.
