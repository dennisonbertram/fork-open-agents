## Why this matters

Every live chat experience in the iOS app — watching a run stream (U3), resuming after backgrounding (U4), stopping a runaway agent — rides on one transport object: the connection between `URLSession` and the chunk decoder. M7-01 delivered the parser and the lenient `UIMessageChunk` decoder, and M3-01 delivered authorized request construction, but nothing yet opens the socket, asserts the protocol, classifies failures, or distinguishes "user pressed stop" from "user swiped back". This slice is that object: a `ChatStreamClient` actor that owns `POST /api/chat`, `GET /api/chat/{chatId}/stream` (including the 204 no-active-stream answer), and `POST /api/chat/{chatId}/stop`, enforcing the `x-vercel-ai-ui-message-stream: v1` assertion, mapping every HTTP/transport failure into the typed `ChatStreamError` taxonomy, and implementing the web client's hard-won stop semantics: instant local cancel, fire-and-forget snapshot persistence, and the `userStopped` flag that fixes the iOS-Safari "tap stop 3 times" reconnect race natively. M7-04 (send flow), M7-05 (reconnect policy), and M7-06 (run-watching UI) all consume this actor; getting the boundaries wrong here forks the error taxonomy and re-introduces the duplicate-content bugs the milestone exists to prevent.

## User/operator path protected

Protected path (T3/U3 transport leg, plus the stop invariant named by the milestone): a user taps Stop during a streaming turn — the UI halts instantly (local cancel never waits on the network), the partial assistant output is preserved (the in-flight snapshot rides the stop POST body byte-verbatim so the server persists it before cancelling the workflow), and no automatic reconnect fires until the user sends again (`userStopped` suppression). The dual invariant: navigating away from a chat cancels only the local connection and **never** stops the server run — the durable workflow keeps generating, matching web behavior.

## Behavior contract

- Given `StubURLProtocol` replays fixture `01-plain-text-turn.sse.txt` in chunked slices with status 200 and headers `content-type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`, `x-workflow-run-id: wf_test_1`, `x-request-id: req_echo_1`, When `postTurn(sessionId:chatId:bodyJSON:)` is awaited, Then the outgoing request is `POST {baseURL}/api/chat` with `content-type: application/json`, an `x-request-id` matching `^ios\.[0-9a-f-]{36}$`, an `Authorization: Bearer` header from the M3-01 builder, and a body byte-identical to `bodyJSON`; and the returned `Connection` has `workflowRunId == "wf_test_1"`, `requestId == "req_echo_1"`, and yields every fixture chunk in arrival order, finishing at EOF.
- Given a 200 response **without** the `x-vercel-ai-ui-message-stream: v1` header, When `postTurn` or `resume` runs, Then `ChatStreamError.protocolViolation` is thrown before any chunk is yielded and `stream_protocol_violation` is logged with `reason=missing_v1_header`.
- Given the stream body contains `data: [DONE]` followed by more bytes before EOF, When consumed, Then `[DONE]` is treated as advisory — the chunk stream finishes only at EOF (per `05-streaming-chat-engine.md` §1.2).
- Given a 200 + v1 SSE response on `GET /api/chat/{chatId}/stream`, When `resume(chatId:)` runs, Then it returns `.stream(Connection)` with `workflowRunId == nil` when the header is absent, and the full replay chunks are yielded in order (rebuild-from-scratch is M7-05's job; this actor only delivers the chunks).
- Given a `204 No Content` on the resume GET, Then `resume` returns `.noActiveStream` without throwing and without yielding chunks.
- Given a `401` on the resume GET whose body is the **plain text** `Unauthorized` (not JSON, per `apps/web/app/api/chat/[chatId]/stream/route.ts`), Then `resume` throws `.notAuthenticated` — the mapper must not require a JSON envelope.
- Given non-2xx responses on either endpoint, When mapped, Then the §3.5 taxonomy holds exactly: 400 `{"error":"Session is archived"}` → `.sessionArchived`; other 400 → `.badRequest(message:)`; 401 → `.notAuthenticated`; 403 → `.forbidden(message:)`; 404 → `.notFound`; 409 → `.conflict`; 422 with `fieldErrors` → `.workflowInputInvalid(fieldErrors:)`; 502 → `.verifiedBuildUnavailable(requestId:)` (requestId from the body's `requestId` else the echoed header); other 5xx → `.serverError(status:)`.
- Given an active connection mid-stream (stub delivering with 10 ms inter-chunk delay), When `stop(chatId:stopBodyJSON:)` is called, Then it returns without awaiting the stop POST (assert return in < 100 ms while the stub holds the stop response ≥ 1 s), the chunk stream terminates promptly with `.cancelled` (silent — never surfaced as an error), the request to `POST /api/chat/{chatId}/stop` carries a body byte-identical to `stopBodyJSON`, and `isUserStopped` becomes `true`.
- Given `isUserStopped == true`, When `resume(chatId:)` is called, Then it returns `.suppressedByUserStop` and `StubURLProtocol` records **zero** network requests for that call.
- Given `isUserStopped == true`, When `postTurn` is invoked (the next send), Then the flag resets to `false` before the request fires; `clearUserStopped()` also resets it (the explicit-retry path for M7-05/M7-06).
- Given an active connection, When `cancelActiveConnection()` is called (navigation away), Then the local stream ends with `.cancelled`, **no** request to `/api/chat/{chatId}/stop` is ever issued, and `isUserStopped` remains `false` — a subsequent `resume` proceeds normally.
- Given the stub fails the connection with `URLError(.networkConnectionLost)` after N chunks, Then the N already-yielded chunks were delivered and the stream throws `.transport(URLError)`; `CancellationError`/`URLError(.cancelled)` map to `.cancelled` instead.
- Given fixture `14-unknown-chunk-types.sse.txt` (malformed JSON line + unknown types), When streamed through the client, Then decode failures are skipped with a logged event and the stream continues to EOF (leniency lives in the M7-01 decoder; this proves the loop never aborts on it).

## Product and design spec

This slice ships **no screens**. The product surface is the `ChatStreamClient` actor API that M7-04 (send flow), M7-05 (reconnect), and M7-06 (stop button, status strip) consume, plus the typed `ChatStreamError` values whose UI handling matrix (`05-streaming-chat-engine.md` §3.5) those siblings render with `status.stream.*` / `error.*` copy keys owned by `docs/plans/ios-app/01-product-and-ux.md`.

- Entry points: `postTurn(sessionId:chatId:bodyJSON:)`, `resume(chatId:)`, `stop(chatId:stopBodyJSON:)`, `cancelActiveConnection()`, `clearUserStopped()`, `isUserStopped`.
- States: connecting (request in flight), streaming (chunks yielding), terminated-clean (EOF), terminated-failed (typed throw), suppressed (`.suppressedByUserStop`). No spinners, banners, or copy are rendered here; errors are thrown values.
- The stop affordance contract this actor guarantees to the eventual UI: tap-to-halt is instantaneous and idempotent (a second `stop` while already stopped is a no-op that fires no duplicate POST).
- Accessibility, copy, permissions: none — library code only.
- Error/empty/loading behavior: encoded in the `ChatStreamError` taxonomy and its classification helpers (Integration spec); `cancelled` is the one error consumers must treat as silent.

## Integration spec

New/edited files (all paths exact):

- `ios/Packages/StreamEngine/Sources/StreamEngine/ChatStreamClient.swift` — the actor:

  ```swift
  public actor ChatStreamClient {
    public struct Connection: Sendable {
      public let workflowRunId: String?      // x-workflow-run-id (POST; rarely on GET)
      public let requestId: String?          // echoed x-request-id, else the generated one
      public let verifiedBuildRunId: String? // x-verified-build-run-id when present
      public let chunks: AsyncThrowingStream<UIMessageChunk, Error>
    }
    public enum StartResult: Sendable {
      case stream(Connection)
      case noActiveStream          // GET 204
      case suppressedByUserStop    // resume called while userStopped; zero network
    }
    public init(requestBuilder: any AuthorizedRequestBuilding, logger: any StreamEventLogging)
    public var isUserStopped: Bool { get }
    public func postTurn(sessionId: String, chatId: String, bodyJSON: Data) async throws -> Connection
    public func resume(chatId: String) async throws -> StartResult
    public func stop(chatId: String, stopBodyJSON: Data)   // instant; fire-and-forget POST; sets userStopped
    public func cancelActiveConnection()                   // local only; never stops the server run
    public func clearUserStopped()
  }
  ```

  Consumption loop per `05-streaming-chat-engine.md` §3.2: `requestBuilder.streamingSession.bytes(for:)` → status switch (200 asserts the v1 header; 204 on GET only; default drains ≤ 64 KiB of body and calls `ChatStreamError.map(status:headers:body:)`) → `for try await line in bytes.lines` → M7-01 `parseSSELine` → M7-01 `UIMessageChunk(lenientlyDecoding:)` → `continuation.yield`. Decode failure: log + skip, never abort. EOF → `continuation.finish()` (clean/dirty determination is M7-04/M7-05's). Exactly one connection task at a time; starting a new one cancels the previous. `stop` order (replicates web exactly, §3.3): set `userStopped = true` → cancel the connection task → launch an unstructured `Task` for the POST (never awaited by the caller) → log. `bodyJSON`/`stopBodyJSON` are complete request payloads — `{"sessionId":…,"chatId":…,"messages":[…]}` and `{"assistantMessage":…}` respectively — encoded by the caller (M7-04 or tests) and sent byte-verbatim.

- `stream_event` (debug): `chat_id`, `part_type`, `bytes` — never the payload.
- `stream_protocol_violation` (error): `request_id`, `chat_id`, `reason=missing_v1_header` | `bad_json_line`, `error_kind`.
- `stream_disconnected` (notice): `chat_id`, `reason` (`server_close` on EOF | `user_cancel` on stop/cancel | `network_lost` on `URLError(.networkConnectionLost)`), `duration_ms`, `events_total`.
- `stream_resume_result` (notice): `chat_id`, `outcome` (`replayed` | `no_active_stream_204` | `failed`), `error_kind` only when `failed`.
- The fire-and-forget stop POST logs `api_request_finished`/`api_request_failed` (category `stream`, since it bypasses the generated client) with `request_id`, `path=/api/chat/{chatId}/stop`, `status`, `duration_ms`.

Typed `error_kind` values (taxonomy in `07-observability.md` §6 — no new kinds needed): `notAuthenticated`→`http_unauthorized`, `forbidden`→`http_forbidden`, `notFound`→`http_not_found`, `conflict`→`http_conflict`, `serverError`/`verifiedBuildUnavailable`→`http_server_error`, `badRequest`/`sessionArchived`/`workflowInputInvalid`→`server_reported` (server `errorKind` such as `workflow_input_invalid` passes through verbatim as `server_error_kind`), `protocolViolation`→`contract_missing_header`, `transport`→`network_offline`/`network_timeout`/`network_connection_lost` by URLError code (`network_connection_lost` is notice-level expected churn, never error), `cancelled`→`cancelled` (never error-level).

Correlation: every event carries `chat_id` and the `ios.<uuid>` `request_id`; `workflow_run_id` is attached from `stream_connected` onward; `session_id` on postTurn events. Joining contract: client `request_id` ↔ server `session_events.request_id` and the `x-request-id` response header; `workflow_run_id` ↔ `workflow_runs.id`.

Redaction (binding, `07-observability.md` §7.3): chunk payloads, message text, deltas, tool inputs/outputs, `bodyJSON`, `stopBodyJSON`, and the `Authorization` header are **never** interpolated into any log at any level — only `part_type`, byte counts, ids, statuses, durations. The grep proof in the checklist is attached to the PR.

User-visible status: none rendered in this slice; the typed errors plus `Connection` attribution fields (`workflowRunId`, `requestId`) are the contract M7-06 renders as the `status.stream.*` strip and the tap-to-reveal attribution row.

Debug recipes:

- Live-tail the engine on a booted simulator: `xcrun simctl spawn booted log stream --level debug --style compact --predicate 'subsystem == "com.openagents.app" AND category == "stream"'`.
- Post-hoc, one stop investigated: `xcrun simctl spawn booted log show --last 30m --style compact --predicate 'category == "stream"' | grep -E 'stream_disconnected|user_cancel'`.
- Server join for one turn: take `request_id=ios.<uuid>` from `stream_connect_started`, then `vercel logs <deployment-url> | grep 'ios.<uuid>'` and `SELECT event_name, status FROM session_events WHERE request_id = 'ios.<uuid>' ORDER BY created_at;`.

## Regression risks and concerns

- **Stop/cancel conflation** is the highest-value bug class this slice exists to prevent: if `cancelActiveConnection` ever POSTs stop, navigating away kills server runs; if `stop` ever skips the flag, the reconnect race returns. The two operations must stay separate code paths (file 4 pins both directions).
- **Awaiting the stop POST** anywhere in the `stop` call path silently reintroduces sluggish stop on bad networks — the unstructured `Task` must not be joined; the < 100 ms assertion guards it.
- **Snapshot fidelity**: re-encoding the stop body through a typed model here would break byte-verbatim round-trip of parts the app does not understand; `Data`-through is deliberate. Do not "improve" it.
- **Single error mapper**: M7-04/M7-06 will switch over `ChatStreamError`; a second ad-hoc mapping (e.g. inline status checks in M7-05) forks the taxonomy — keep `map` the only entry point and keep the classification helpers exhaustive (`switch` without `default` so new cases fail compilation).
- **Plain-text auth errors on the resume route**: a JSON-only decoder crashes or mis-maps the 401; the plain-text fallback test pins it.
- **Unbounded error-body drain**: reading a stream body to EOF on a non-2xx could hang on a misbehaving proxy; the 64 KiB cap is load-bearing.
- **`StubURLProtocol` chunk coalescing**: if the M7-01/M3-01-era spike test (`06-testing-strategy.md` §5.2) revealed coalescing on the current SDK, these tests must use the FlyingFox tier instead — check `docs/agents/lessons-learned.md` before assuming the stub tier works.
- **Strict-concurrency traps**: `AsyncThrowingStream.Continuation` is `Sendable` but the connection task must be owned by the actor; no `@unchecked Sendable`. `URLSession.AsyncBytes` iteration throwing on cancellation must map to `.cancelled`, not surface as `.transport`.
- **M3-01/M7-01 drift**: if the `AuthorizedRequestBuilding` method names or fixture paths differ from this plan, adapt to what shipped (discovery step) rather than duplicating a request-building path — two auth-header code paths would be a custody regression.
