## Why this matters

Resume-replay semantics times iOS backgrounding is risk #4 in `docs/plans/ios-app/00-overview.md` §"top risks": the server replays the active stream **from chunk 0** on every `GET /api/chat/{chatId}/stream` 200, iOS kills the socket shortly after every suspension, and a naive client that appends replayed chunks onto its existing partial state duplicates every text and reasoning block — the exact "jank" the web client's resume hook documents avoiding. Backgrounding makes this the *common* case on mobile, not an edge case. M7-03 gave us the transport (`ChatStreamClient.resume(chatId:)` returning `.stream` or `.noActiveStream`) and M7-04 gave us `ChatRuntime` with the send flow, but nothing yet decides *when* to reconnect, *how* to rebuild state without duplication, or *what* to do on `204`. This slice lands that policy layer — the rebuild-from-scratch rule, the 204 refetch-and-reconcile path, the full reconnect trigger table, and the backgrounding drain — plus the named U4 deterministic regression that pins it forever. Without it, M7-06's run-watching UI would render duplicated or vanishing content the first time a user switches apps mid-run.

## User/operator path protected

U4 (`docs/plans/ios-app/00-overview.md` §protected paths): "Backgrounding the app mid-stream and foregrounding it resumes the stream (or refetches persisted messages on 204) with zero duplicated or lost text." This is P4 in `docs/plans/ios-app/06-testing-strategy.md` §2: "A stream interrupted by backgrounding/network loss resumes and replays without duplicated or lost parts," proven by SSE fixture replay (disconnect fixtures) plus an integration test. Secondary invariant protected: the client never re-POSTs `/api/chat` as a reconnect strategy (a re-POST can 409 and re-sends the entire message history; GET is the contract).

## Behavior contract

- Given a turn streaming in `ChatRuntime`, When the app enters the background (scene-phase hook fires), Then within a ≤ 5 s drain budget already-buffered chunks are applied to the turn state, the in-flight assistant message snapshot is upserted to GRDB with `sync_state = 'partial_stream'`, the local stream task is cancelled (no stop POST — the server workflow keeps running), and `stream_disconnected` is logged with `reason=backgrounded`.
- Given a backgrounded turn that was in flight, When the app returns to the foreground, Then `ChatRuntime.resumeIfNeeded()` issues `GET /api/chat/{chatId}/stream` immediately; on `200` (with `x-vercel-ai-ui-message-stream: v1`) the engine creates a **fresh `ChatTurnState` seeded with persisted history up to, but not including, the in-flight assistant message**, applies the full replay to that fresh state, and on the first UI flush after the `start` chunk replaces the last local assistant message wholesale when `start.messageId` matches its id (appends the rebuilt message otherwise). The previous partial in-memory state is discarded entirely. The final transcript is byte-identical (canonical JSON) to applying the same replay to a clean seeded state — zero duplicated and zero lost parts.
- Given any resume, When replayed chunks arrive, Then they are **never appended onto existing partial state** — rebuild is the only code path, regardless of how many reconnects occur in one turn.
- Given `GET /api/chat/{chatId}/stream` returns `204`, When the runtime handles it, Then it fetches `GET /api/sessions/{sessionId}/chats/{chatId}` (`ChatRefreshResponse { chat, isStreaming, messages }`); if `isStreaming == false` it replaces `ChatRuntime.messages` with the canonical `messages` and reconciles GRDB in one transaction (delete all `synced`/`partial_stream` rows for the chat, insert server messages as `synced` with fresh `position`, **keep `pending_send`/`failed_send` rows whose ids are absent from the server set** — the outbox survives); if `isStreaming == true` it goes back to the GET-stream path (alternating stream-GET/refetch at the dirty-EOF backoff cadence until a `200` attaches or `isStreaming` goes false — never a tight loop, never a POST).
- Given the network path becomes satisfied after being unsatisfied (`NWPathMonitor` seam), When a turn is in flight, Then the runtime reconnects via GET resume.
- Given a mid-stream EOF without a `finish` chunk and `userStopped == false`, When the stream loop ends dirty (or `URLError` is thrown from `AsyncBytes`), Then the runtime schedules backoff reconnects at `0.5 s → 1 s → 2 s → 4 s → 8 s → 15 s` (cap), each with ±20 % jitter, and the attempt counter resets after any connection that stays alive > 60 s.
- Given the user tapped stop (`userStopped == true`, set by M7-03), When EOF-without-`finish` or any reconnect trigger fires, Then **no** auto-reconnect happens until the next send clears the flag (web's iOS-Safari "tap stop 3 times" fix, inherited natively).
- Given a chat mounts whose last message has `role == "user"` and no active stream is known locally, When the runtime activates, Then it probes `GET /api/chat/{chatId}/stream` on the schedule **0 s, 1 s, 2.5 s, 5.5 s, 10 s**, attaching to the first `200`; if all five return `204`, the chat-snapshot refetch reconciles state and status returns to ready.
- Given a connected stream receives no chunk for 300 s, When the watchdog fires, Then it probes server `isStreaming` (via `GET /api/sessions/{sessionId}/chats`); `true` → keep waiting and re-arm the watchdog (long sandbox tool runs are legitimate; there are no server heartbeats); `false` → treat as the `204` path (refetch + reconcile).
- Given an in-band `{"type":"error"}` chunk followed by EOF, When the turn ends, Then no auto-reconnect fires; the error banner's Retry action performs a GET resume (`clearError` + resume), never a re-POST.
- Given any reconnect scenario in this issue, When the transport records all requests, Then **zero `POST /api/chat` requests** were issued by resume/reconnect logic (asserted in every engine test in this slice).
- Given a `200` replay whose `start.messageId` does **not** equal the last local assistant message id, When the first flush happens, Then the rebuilt message is appended (not replaced) and no existing message is mutated.
- Given resume GETs keep failing with transport errors, When the backoff budget continues, Then attempts continue at the 15 s cap with jitter, `stream_resume_attempt`/`stream_resume_result outcome=failed` are logged per attempt, and the runtime exposes the reconnecting state for the UI (rendering is M7-06).

## Product and design spec

This slice ships **no new screens** — it is the policy layer behind the chat screen M7-06 renders. Its product surface is state correctness and the `StreamState` transitions other slices bind to:

- Entry points: app lifecycle (scene-phase hooks shipped by M5-02 in `ios/Packages/AppShell`), network-path changes, chat mount (`ChatRuntime` activation from M7-04), and stream EOF events.
- States driven here (copy keys per `docs/plans/ios-app/07-observability.md` §12.2; wording owned by `01-product-and-ux.md`, rendered by M7-06): `.reconnecting` (`status.stream.reconnecting`, "Connection lost. Reconnecting…"), `.waiting` (`status.stream.waiting`, "Agent is still working…" — watchdog/stall), `.failed(errorKind)` (`status.stream.failed`) when the resume budget is exhausted, `.streaming`/`.finished` on successful attach/finish.
- A `partial_stream` GRDB row renders with a "resuming…" affordance on cold launch (M7-06/M6 transcript rendering) and is always replaced by the next resume rebuild or refetch.
- Accessibility: no new UI; state changes surface through M7-06's status strip which owns announcements.
- Permissions: none. No new entitlements, background modes, or Info.plist keys (the ≤ 5 s drain uses the standard `UIApplication.beginBackgroundTask` grace, not BGTaskScheduler).
- Error/empty/loading behavior: silent recovery is the default; the user sees at most the reconnecting indicator. Typed errors flow through the M7-03 `ChatStreamError` taxonomy; nothing new is invented.

## In scope

- Rebuild-from-scratch resume on every `200` replay: fresh `ChatTurnState` seeded with persisted history (excluding the in-flight assistant message), replace-by-`messageId` on first flush, previous partial state discarded; never append across reconnects.
- The `204` path: `ChatRefreshResponse` refetch, message replacement when `isStreaming == false`, GRDB reconcile transaction preserving the `pending_send`/`failed_send` outbox, loop-back to GET-stream when `isStreaming == true` at backoff cadence.
- The complete §2.3 reconnect trigger table: foreground, network regain, dirty-EOF/transport-error backoff (`0.5→1→2→4→8→15 s` cap, ±20 % jitter, >60 s-alive reset), `userStopped` suppression until next send, the `0/1/2.5/5.5/10 s` mount probe schedule, and the 300 s watchdog probing `isStreaming` (plus 60 s `stream_idle` ticks).
- Backgrounding: ≤ 5 s drain budget, `partial_stream` GRDB snapshot, stream-task cancel, AppShell `beginBackgroundTask` wiring, foreground resume wiring.
- The structural never-re-POST guarantee, asserted in every test in this slice.
- The named U4 deterministic regression (`ResumeRebuildTests`, runnable via `swift test --package-path ios/Packages/StreamEngine --filter ResumeRebuild` — the exact command in the M7 verification checkpoint).

7. `ios/Packages/PersistenceKit/Tests/PersistenceKitTests/TranscriptReconcileTests.swift` — in-memory `AppDatabase`: seed 3 `synced` + 1 `partial_stream` + 1 `pending_send` + 1 `failed_send` rows; reconcile with a 4-message server array that contains none of the outbox ids → result is exactly 4 `synced` rows with `position` 0–3 plus the untouched `pending_send` and `failed_send` rows; a server array that **does** contain an outbox id replaces that row with the server copy as `synced`. (If discovery finds M7-04 already shipped this method with tests, extend the existing suite with the missing cases instead of duplicating.)

## Observability and user feedback

Named module: `StreamEngine`, logging through the minimal `Log.stream` facade (`ios/Packages/Observability`, subsystem `com.openagents.app`, category `stream`); AppShell lifecycle events through `Log.bg` (category `bg`, added in this slice if absent). Event names, levels, and snake_case fields verbatim from `docs/plans/ios-app/07-observability.md` §4.3/§4.6 so the later structured-emitter migration is mechanical:

- `stream_resume_attempt` (notice): `chat_id`, `attempt`, `backoff_ms` — emitted before every GET resume, including each mount-probe step.
- `stream_resume_result` (notice): `chat_id`, `outcome` ∈ `replayed | no_active_stream_204 | failed`, `error_kind` only when `failed`.
- `stream_disconnected` (notice — never error): `chat_id`, `reason` ∈ `server_close | network_lost | backgrounded | stalled | user_cancel`, `duration_ms`, `events_total`.
- `stream_idle` (info): `chat_id`, `idle_ms` — 60 s chunk-free ticks while connected (no server heartbeats exist; long tool runs are normal).
- `stream_stalled` (notice): `chat_id`, `idle_ms`, `threshold_ms` — the 300 s watchdog fired (UI flips to `status.stream.waiting`).
- `bg_app_backgrounded` (info): `streams_active`; `bg_app_foregrounded` (info): `background_s` — from the AppShell hook.

Typed `error_kind` values produced (taxonomy `07-observability.md` §6, no new kinds): `network_connection_lost` (expected mobile churn — notice, counted separately, never error-level), `network_offline`, `network_timeout`, `stream_resume_failed` (resume GET non-OK after the backoff budget), `stream_stalled` (watchdog fired and the probe also failed), `cancelled` (local suspend/cancel — never error-level), `http_unauthorized` (handed to the auth layer).

Correlation: every event carries `chat_id` and `session_id`; `request_id` (`ios.<lowercase-uuidv4>`, set by the M7-03 client on the stream GET) and `workflow_run_id` (from `x-workflow-run-id`, present on POST-origin connections) are attached whenever in scope. These join server-side to `session_events.request_id` and `workflow_runs.id`.

Redaction: no message text, prompt content, tool output, or replay payload is ever logged at any level — only counts (`events_total`), durations, reasons, and ids. `path` fields are route templates (`/api/chat/{chatId}/stream`), never concrete URLs with query strings. OSLog interpolations follow `07-observability.md` §7.2 (ids and enum-ish strings `.public`, everything else default-private).

Debug recipes:

- Live-tail resume behavior on a booted simulator: `xcrun simctl spawn booted log stream --level debug --style compact --predicate 'category == "stream"' | grep -E "stream_resume|stream_disconnected|stream_stalled"`.
- Post-hoc U4 verification after a background/foreground cycle: `xcrun simctl spawn booted log show --last 30m --style compact --predicate 'category == "stream" OR category == "bg"' | grep -E "bg_app_|stream_resume_result"` — expect `bg_app_backgrounded` → `bg_app_foregrounded` → `stream_resume_attempt` → `stream_resume_result outcome=replayed`.
- Server join: take `request_id=ios.<uuid>` from `stream_resume_attempt`, then `vercel logs <deployment-url> | grep 'ios.<uuid>'` and `SELECT event_name, status FROM session_events WHERE request_id = 'ios.<uuid>' ORDER BY created_at;`.

## Regression harness plan

- **Continuous, deterministic, PR-blocking**: test files 1–7 run on every `ios/**` PR via `./ios/Scripts/ci.sh` (host-runnable `swift test` for StreamEngine and PersistenceKit). `ResumeRebuildTests` is the **named U4 regression** the milestone exit criteria call out — it fails if anyone ever appends replayed chunks, drops the seeding rule, breaks replace-by-messageId, or re-POSTs on reconnect. Fail-before/pass-after is the recorded red→green pair (the suite cannot compile before implementation).
- The never-re-POST assertion is embedded in every reconnect test, so a future "helpful" re-POST fallback fails seven suites at once.

## Regression risks and concerns

- **Append-on-resume is the catastrophic failure mode** this slice exists to prevent — any future refactor that reuses the live `ChatTurnState` across a reconnect reintroduces duplicated text. The byte-equal golden comparison in test 1 (including the double-cycle variant) is the tripwire; reviewers must reject any change that makes resume mutate existing state.
- **Outbox loss**: a careless reconcile (delete-all + insert) would destroy queued/failed user messages on every `204`. Tests 2 and 7 pin the preserve rule; never "simplify" the transaction.
- **Reconnect storms**: jitterless backoff or a missing `userStopped` guard can hammer the server (and resurrect the web's "tap stop 3 times" bug). The policy is pure and table-tested (test 3); keep all trigger handling routed through `ReconnectPolicy.decide` — no ad-hoc `resume()` calls elsewhere.
- **409 risk via re-POST**: re-POSTing `/api/chat` on reconnect can 409 (`Another workflow is already running`) and re-sends the whole history. The structural guarantee is that resume code paths only hold a reference to `ChatStreamClient.resume`, never `postTurn`; the recorded-request assertions enforce it.
- **Watchdog vs. long tool runs**: the server emits no heartbeats and multi-minute idle gaps are legitimate. Treating idle as dead (or skipping the `isStreaming` probe) would kill healthy runs; test 5's probe-true-re-arms case pins this.
- **Drain budget overrun**: an unbounded drain in `suspendForBackground()` risks a watchdog termination (`0x8badf00d`). The 5 s budget with the injected clock (test 6) plus keeping UIKit's background-task bracketing in AppShell bounds it.
- **Host-runnability**: importing SwiftUI/UIKit into StreamEngine (e.g. for `scenePhase` or `UIApplication`) would break macOS `swift test` and the fast inner loop — lifecycle enters via the seams only.
- **M7-04 drift**: if shipped seam names differ (snapshot fetcher, `isStreaming` source, write-point methods), adapt to what merged (discovery step) rather than adding parallel paths — two reconcile implementations would themselves be a duplication bug.
- **Strict concurrency**: `ChatRuntime` is `@MainActor`, the engine/reducer are actors, `StreamWatchdog` is an actor with an injected clock — keep `Sendable` honest, zero `@unchecked Sendable` (repo expectation).

## Deploy or migration impact

None server-side: zero `apps/web` changes, no DB migration, no env vars, no OpenAPI regeneration (every consumed endpoint is hand-rolled per `02-api-contract-and-networking.md` §0.4 and already exists). iOS-side: no GRDB schema change (reuses `chat_message.sync_state` from M6), no new entitlements, background modes, Info.plist keys, or third-party dependencies (`Network.framework` is a system framework). Ships as library + AppShell wiring gated by the iOS CI workflow; no app has shipped yet, so there is no field-compatibility concern. Rollback is a plain revert; `partial_stream` rows written by a reverted build are self-healing (always replaced by the next resume rebuild or refetch).
