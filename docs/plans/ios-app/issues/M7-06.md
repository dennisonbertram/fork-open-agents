## Why this matters

The streamed agent run is the product's best-loved surface, and M7-01..05 made it deterministic under the hood — but nothing renders live yet. This issue is where the engine becomes visible: the shimmer placeholder before the first token, a block caret that lives in an overlay (never inside `Text`, so Markdown reflow can't tear it), the frozen-block/live-tail strategy that keeps Markdown re-parse cost constant as messages grow, scroll anchoring that never fights the user's thumb, an instant stop on the app's only tinted glass capsule, the S4 completion fold-in with exactly one haptic, and the S2 heartbeat strip that follows a live run across tabs. The pillar at stake is P2 ("the stream is sacred"): coalesced updates, one alive indicator, zero per-token animation. The slice also lands the milestone's perf gate — the XCTest `measure` throughput check on fixture 04 and a manual Instruments hang pass — so 60 fps is proven, not asserted.

## User/operator path protected

U3 — a user sends a message (via the SCR-11 first-message handoff, now wired to the real engine) and watches the reply stream: every chunk-driven update is visible within 200 ms of arrival at a sustained 60 fps, with no duplicated, lost, or visually jumping content; the user can scroll up without being yanked back, jump back to live with one tap, stop the run instantly, and see the run's completion fold in with one success/error haptic — and from any other tab, the S2 strip shows the run is still alive.

## Behavior contract

- Given a chat whose turn was just submitted (engine status `.submitted`), when no assistant chunk has arrived yet, then a shimmer placeholder row (rounded rect, `TimelineView` gradient sweep, 1.2 s period) renders where the assistant message will appear, and crossfades to content on the first chunk. Under Reduce Motion the shimmer is a static fill.
- Given text is streaming, when the live tail renders, then a block caret (~2×17 pt `Rectangle`, `AccentPrimary`, opacity autoreversing 0.6 s) appears as an overlay anchored to the end of the last laid-out line — never as a character inside the `Text` — and disappears on `text-end`/finish.
- Given a reasoning or tool phase is running (no text streaming), then the caret is absent and the active tool row's spinner (from M6-06) is the only alive indicator. At no instant are two alive indicators (shimmer, caret, tool spinner) visible in the transcript.
- Given an in-flight assistant message, when a coalesced flush (75 ms cadence from M7-04) arrives, then only frozen-block boundaries are recomputed: completed Markdown blocks render from cached `AttributedString`s and are never re-parsed; the live tail renders as plain `Text(verbatim:)` with no Markdown parse; a block freezes on a blank-line boundary, a closed code fence, `text-end`, or `finish-step`, and syntax highlighting runs once, on freeze, off-main (CodeUI's `SyntaxHighlighter`).
- Given an unclosed ``` fence in the live tail, then a code-block shell renders immediately (language label from the fence info string, copy button disabled, plain monospaced text, no highlighting); highlight applies when the fence closes or the message ends.
- Given the transcript with `followsLive == true` (the initial state), when flushes arrive, then the view stays pinned to the bottom via `.defaultScrollAnchor(.bottom)` + `scrollPosition(id:)` without a programmatic scroll per flush, and earlier rows never change height mid-stream.
- Given streaming, when the user drags upward ≥ 24 pt from the bottom edge (detected with `.onScrollGeometryChange`), then `followsLive` becomes `false`, auto-pinning stops, and the S5 jump-to-now glass pill (`chevron.down` + **"Live"**, `.interactive()`) appears floating above the composer area with a `.snappy(duration: 0.2)` scale 0.9→1.0 entrance; a drag of < 24 pt does not unfollow.
- Given `followsLive == false`, when the run completes, then the pill label changes to **"{N} new"** (N accumulates per completed run/message; this supersedes the "1 new message" wording in `01-product-and-ux.md` section 5.3 rule 5 — section 9 S5 is the binding spec) and the transcript is never force-scrolled.
- Given the pill is visible, when the user taps it, then the transcript scrolls to the bottom with `.smooth(duration: 0.3)` (unanimated under Reduce Motion), `followsLive` re-arms, the pill dissolves, and `ui_action action=jump_to_now` is logged.
- Given a streaming run, then a run-status line renders between the transcript and the composer area: the StreamState copy ("Working…", key `status.stream.streaming`) plus an elapsed timer in `m:ss` format with `.monospacedDigit()`, anchored to the last user message's timestamp so it is honest across relaunch/resume (e.g. backgrounding 30 s into a run and foregrounding shows ≥ 0:30, never 0:00). The timer text appears within the first second of submit and ticks every second. This line is text-only — no spinner — so the one-alive-indicator rule holds.
- Given a streaming run, then the stop button (`stop.fill` on a `StatusError`-tinted glass capsule — the app's only tinted glass, per the section 3.5 glass map) is visible in the interim composer bar with `.keyboardShortcut(".", modifiers: .command)`; tapping it fires `.stop` sensory feedback, calls `ChatRuntime.stop()` (instant local cancel + fire-and-forget snapshot POST, already built in M7-03/M7-04), freezes the partial output, appends the `Type.timestamp` footnote row **"Stopped by you."**, re-enables send immediately, and logs `ui_action action=stream_cancel`.
- Given a turn reaches a clean `finish`, then the S4 completion fold runs as one `.smooth(duration: 0.3)` grouped settle (fade only under Reduce Motion): the caret disappears, a tool-summary header folds in beneath the response (**"Ran {n} tools · {e} edits · +{added} −{removed}"**, omitting zero segments), the M6-06 duration/cost/model footer badges fade in, action chips **"View diff"** / **"Open PR"** appear when a resolved `data-commit`/`data-pr` part exists, and `.success` sensory feedback fires exactly once for the whole run (never per tool, never on repeated snapshot flushes).
- Given a turn ends with an in-band `error` chunk or terminal failure, then an error row renders (`xmark.circle.fill` in `StatusError` + **"The run failed: {server message}"** + **"Retry"** button that calls the engine's GET-resume retry), `.error` fires exactly once, and `ui_error_presented { error_kind: "stream_server_error_part", copy_key: "status.stream.failed" }` is logged.
- Given any chat is streaming while the user is on another tab or another chat, then the S2 heartbeat strip renders as a 48 pt `TabViewBottomAccessory` above the tab bar: a 6 pt leading dot in `StatusRunning` pulsing opacity 1.0↔0.4 at 0.8 Hz (static under Reduce Motion), label **"{session title} · running · 0:42"** with `.monospacedDigit()`. Tapping deep-links to that chat with `followsLive` armed and logs `ui_action action=status_strip_open`. When the run completes untapped, the dot swaps to the success/error glyph and the strip auto-dismisses after 4 s. The strip fires no haptics. When multiple chats stream, the strip shows the most recently started run.
- Given the user is viewing the streaming chat itself, then the strip is hidden (it appears only when the user is "elsewhere").
- Given Dynamic Type at AX sizes, then the pill, run-status line, strip, and fold rows reflow without truncation (no fixed heights on text-bearing views); and given VoiceOver, the streaming message exposes one status element ("Assistant is responding") with `.accessibilityAddTraits(.updatesFrequently)`, completion posts exactly one announcement (**"Agent finished: {e} files edited, {c} commands run."**, failure: **"Run failed."**), and the strip is a button labeled "{session}, running, {seconds} seconds, double-tap to open". Tokens are never announced individually.

## Product and design spec

- **Entry point:** SCR-12 Chat Workspace (existing `ChatScreen` from M6-05/M6-06), now bound to the live `ChatRuntime` instead of cache-only history. Cross-tab entry: the S2 strip.
- **Send path for this milestone:** AppShell's `FirstMessageSending` implementation is swapped from M6-03's draft stash to the real engine (`ChatRuntime.send`), so creating a session starts a watchable run. A minimal **interim composer bar** (plain `TextField` + send button + the stop capsule; no glass anatomy, no attachments/mic/drafts) ships so follow-up sends and the stop control have a home; M8-01 replaces it wholesale. The stop capsule is built as a standalone reusable component so M8-01 embeds it unchanged.
- **Motion (exhaustive for this slice, from section 3.8):** shimmer 1.2 s `TimelineView` sweep; caret 0.6 s autoreversing opacity (allowed under Reduce Motion); S4 fold `.smooth(0.3)` single settle; S5 pill `.snappy(0.2)` scale+opacity; pill scroll `.smooth(0.3)`; strip pulse `easeInOut` 0.8 Hz; **streaming text append: no animation, ever** (P2). Anything not listed gets system defaults.
- **Haptics (exhaustive for this slice, from section 3.7):** run success `.success` once; run failure `.error` once; stop engaged `.stop`. Implemented exclusively via `.sensoryFeedback(_:trigger:)` with a per-turn terminal token as the trigger value. No haptics on pill, strip, tool transitions, or scroll.
- **Glass (section 3.5 map):** jump pill = glass capsule `.interactive()`; stop = glass capsule with `StatusError` tint (the only tinted glass in the app); strip = system `TabViewBottomAccessory` styling. Transcript content stays opaque. Never glass over glass; the pill floats over the opaque transcript, not over the composer's glass.
- **States:** streaming (shimmer → caret/tool-spinner → fold); stopped ("Stopped by you." footnote); failed (error row + Retry); unfollowed (pill "Live" / "{N} new"); completed-while-away (strip glyph swap + 4 s dismiss). Loading/empty/offline states of the chat shell are unchanged from M6-05.
- **Copy (binding):** "Live" · "{N} new" · "Stopped by you." · "The run failed: {server message}" · "Retry" · "Working…" (`status.stream.streaming`) · strip label "{session title} · running · {m:ss}" · summary "Ran {n} tools · {e} edits · +{a} −{r}".
- **Accessibility:** section 7.2 rules in full (one `.updatesFrequently` status element, single completion announcement, combined message-row elements untouched from M6-05/06); `accessibilityDifferentiateWithoutColor` is already satisfied because every status is glyph + word + color.

## Regression risks and concerns

- **P2 violations are silent and easy:** an implicit `withAnimation` or observable-driven transition around the transcript can animate text appends; snapshots can't catch motion. Reviewers must check every state change feeding `StreamingMessageView` is animation-free, and the Instruments pass is the backstop.
- **Scroll fighting:** `scrollPosition(id:)` + `.defaultScrollAnchor(.bottom)` interacting with `LazyVStack` re-layout is the highest-flake area; keep all policy in the pure `TranscriptFollowState` so the view layer only obeys it, and never issue programmatic scrolls while unfollowed.
- **Haptic duplication:** repeated coalesced snapshots of a finished turn must not re-trigger `.success` — the trigger token test (file 4) is the guard; the same applies to the VoiceOver completion announcement.
- **Registry surface creep:** adding `streamingRuntimes` to `ChatRuntimeRegistry` must not retain runtimes that `releaseIdleRuntimes()` would evict (M7-04 memory semantics); re-run the M7-04 registry tests.
- **`FirstMessageSending` swap:** the protocol signature is the M6-03 contract — wire the new sender without touching the protocol, and re-run `SessionsFeatureTests` to prove SCR-11 still works; the draft-stash rows already written by M6-03 must not double-send (the runtime sender supersedes, it does not replay stashed drafts).
- **`TabViewBottomAccessory` API risk:** flagged open item; the fallback overlay is specified in Research and context sources so the milestone cannot stall on an SDK rename.
- **Frozen-block cache invalidation:** a Dynamic Type or color-scheme change may legitimately re-parse frozen blocks once; ensure it cannot happen per flush (cache keyed on content + trait inputs), or the perf budget quietly dies on AX sizes.
- **Throughput test flakiness on shared CI hardware:** the 5,000 chunks/s floor has headroom (budget math in 05 section 7.1 implies ~10× margin in release builds); if CI proves noisy, fix the environment (release config, single iteration warm-up) — never lower the floor without a PR amending `05-streaming-chat-engine.md`.
