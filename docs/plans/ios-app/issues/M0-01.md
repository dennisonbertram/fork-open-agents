## Why this matters

The iOS app cannot exist until `apps/web` accepts a credential that is not a browser cookie. Today better-auth `1.6.5` (pinned `^1.6.5` in `apps/web/package.json`) runs cookie-only: no `plugins:` key, no `trustedOrigins` key in `apps/web/lib/auth/config.ts`. This slice turns the server into a bearer-token multi-client auth platform with one config change plus two small routes: the `bearer()` plugin upgrades every session-gated API (JSON, RSC, and SSE) at once because all ~30 route files resolve sessions through exactly two helpers (`apps/web/lib/session/server.ts` and `apps/web/lib/session/get-server-session.ts`), both of which pass full request headers into `auth.api.getSession({ headers })`. The `oneTimeToken()` plugin plus the two new `native-auth` routes give the iOS app a hardened browser-to-app sign-in handoff (single-use, 3-minute, hashed-at-rest OTT — the session token never appears in any URL) and the reverse bridge for cookie-bound web flows (GitHub App install, Composio connect). Every other iOS milestone depends on this landing first (risk #1 in `docs/plans/ios-app/00-overview.md` §9).

## User/operator path protected

A native client signs in via browser handoff (OAuth in `ASWebAuthenticationSession` → `GET /api/native-auth/complete` → `openagents://auth?ott=…` → `POST /api/auth/one-time-token/verify` → `set-auth-token` header) and then calls every session-gated API — including SSE (`GET /api/chat/{chatId}/stream`) — with `Authorization: Bearer <token>.<sig>` and no cookies. Simultaneously protected: the existing web cookie path must not change in any observable way.

## Behavior contract

- Given a user with a valid better-auth session whose signed token is `<token>.<sig>`, When a request carries `Authorization: Bearer <token>.<sig>` and no `Cookie` header, Then `getSessionFromReq` resolves the session and session-gated routes (e.g. `GET /api/sessions`) return 200 with that user's data.
- Given an active chat run, When `GET /api/chat/{chatId}/stream` is requested with only the bearer header, Then the response is 200 with `x-vercel-ai-ui-message-stream: v1` and `data:` SSE lines (204 when no stream is active — both prove auth passed; 401 would mean it failed).
- Given a bearer value with a tampered signature, When any session-gated route is called, Then the session does not resolve (401 from the route; `getSessionFromReq` returns `undefined`).
- Given a raw unsigned session token (the `auth_sessions.token` column value without `.<sig>`), When used as a bearer, Then it is rejected (`requireSignature: true`).
- Given a browser request to `GET /api/native-auth/complete` carrying a fresh session cookie, When the route runs, Then it responds 303 with `Location: openagents://auth?ott=<one-time-token>`.
- Given `GET /api/native-auth/complete?error=access_denied` (better-auth forwarded an OAuth error via `errorCallbackURL`), Then it responds 303 to `openagents://auth?error=access_denied` without minting an OTT.
- Given `GET /api/native-auth/complete` with no session cookie (cancelled/expired dance), Then it responds 303 to `openagents://auth?error=sign_in_failed`.
- Given a freshly minted OTT, When `POST /api/auth/one-time-token/verify` receives `{ "token": "<ott>" }` with no cookies and no `Authorization`, Then it returns 200 with the session JSON and a `set-auth-token: <token>.<sig>` response header.
- Given an already-verified OTT, When verified a second time, Then the response is 400 (single-use).
- Given a valid OTT, When `GET /api/native-auth/bridge?ott=<ott>&next=/api/github/app/install` runs, Then it responds 303 with `Location: /api/github/app/install` and a `Set-Cookie` header establishing the session (`better-auth.session_token`).
- Given `next=https://evil.example/phish` (or any external/absolute origin), When the bridge runs with a valid OTT, Then the redirect target falls back to `/sessions` (via `sanitizeInternalRedirect`).
- Given a missing `ott` query param, Then the bridge returns 400 `{ "error": "Missing ott" }`; given an invalid or expired OTT, Then 401 `{ "error": "Invalid or expired token" }`.
- Given the existing web app, When a user signs in with cookies and uses every page, Then nothing observable changes (the plugins are additive; cookie CSRF/origin validation behavior is untouched; the only delta is a harmless extra `set-auth-token` response header on better-auth endpoints that set the session cookie).

## Product and design spec

This is a server-only slice; the "UI" is the HTTP surface consumed by the in-app browser and the future iOS client.

- Entry points: (1) `GET /api/native-auth/complete` — terminal hop of the OAuth dance inside `ASWebAuthenticationSession`, reached via better-auth `callbackURL`/`errorCallbackURL` values of `/api/native-auth/complete`; (2) `GET /api/native-auth/bridge?ott=…&next=…` — opened by the app to hand its bearer session to a browser sheet for cookie-bound web flows.
- States: success (303 to `openagents://auth?ott=…` / 303 to internal `next` path with session cookie), provider error (303 to `openagents://auth?error=<provider code>`), no-session (303 to `openagents://auth?error=sign_in_failed`), bad request (bridge 400), rejected token (bridge 401). No HTML is rendered by either route; `ASWebAuthenticationSession` intercepts the `Location` header for the custom scheme.
- Copy: error codes are machine-readable query values (`sign_in_failed`, provider codes like `access_denied`); the iOS client owns human copy. Bridge JSON errors use the repo's existing `{ "error": "…" }` shape.
- Permissions: `/api/native-auth/complete` requires a cookie session only for the success path (no session → error redirect, never a 500); `POST /api/auth/one-time-token/verify` is public by design (single-use, 3-minute TTL, SHA-256-hashed at rest in the existing `verification` table); `GET /api/auth/one-time-token/generate` is session-gated by the plugin.
- Routes live under `app/api/native-auth/` — never under `app/api/auth/`, which belongs to the better-auth catch-all `apps/web/app/api/auth/[...all]/route.ts`.
- Accessibility / loading / empty: not applicable (no rendered UI); web pages are untouched.

## Observability and user feedback

Named module: `apps/web/lib/auth/native-auth-log.ts`, service value `native-auth`, emitting single-line JSON via `console.log`/`console.warn` (matching the structured-object convention used in `apps/web/app/api/github/app/install/route.ts`). `requestId` is `req.headers.get("x-vercel-id") ?? crypto.randomUUID()`.

Events:

- `complete-redirect` (info): `{ service: "native-auth", event: "complete-redirect", outcome: "ott_issued" | "oauth_error" | "no_session", providerError?: string, requestId }`. `providerError` is the non-secret OAuth error code (e.g. `access_denied`); never the OTT.
- `bridge-redirect` (info): `{ service: "native-auth", event: "bridge-redirect", next: string, requestId }` — `next` is the already-sanitized internal path, safe to log.
- `bridge-rejected` (warn): `{ service: "native-auth", event: "bridge-rejected", errorKind: "missing_ott" | "invalid_or_expired_ott", requestId }`.

Typed error kinds (stable values): `no_session`, `oauth_error`, `missing_ott`, `invalid_or_expired_ott`.

Redaction rules (binding, per `docs/plans/ios-app/04-auth.md` §11 and `docs/process/observability-discipline.md`): never log the OTT value, any `Authorization` header, any `set-auth-token` value, any `Cookie`/`Set-Cookie` value, or `req.url`/raw query strings (the OTT rides in the query). The only URL-ish logged field is the sanitized `next` path. No `userId` is logged by these routes (no session is parsed in the bridge success path).

User-visible status: failures surface to the native client as `openagents://auth?error=<code>` deep links and JSON `{ "error": … }` bodies — machine-readable, no secrets.

Debug recipes:

- Local: `bun run web 2>&1 | grep '"service":"native-auth"'`
- Production/preview: `vercel logs <deployment-url> | grep '"service":"native-auth"'`
- Incident triage for failed handoffs: `grep '"errorKind":"invalid_or_expired_ott"'` over the above; correlate with `requestId`.

SSE bearer evidence procedure (attach raw output to the PR — §3.8 row 6):

1. `bun run web`; sign in at `http://localhost:3000` in a browser; copy the `better-auth.session_token` cookie value from devtools.
2. `curl -s -o /dev/null -D - -H "Cookie: better-auth.session_token=<cookie value>" http://localhost:3000/api/native-auth/complete` → record `location: openagents://auth?ott=<ott>` (redact the OTT in the PR).
3. `curl -s -D - -H "Content-Type: application/json" -H "Origin: openagents://" -d '{"token":"<ott>"}' http://localhost:3000/api/auth/one-time-token/verify` → record the `set-auth-token` header (redact its value).
4. Start a chat run from the web UI (long prompt so it streams); get the `chatId` from `GET /api/sessions/<sessionId>/chats` using the bearer, then while streaming: `curl -N -D - -H "Authorization: Bearer <set-auth-token value>" "http://localhost:3000/api/chat/<chatId>/stream"` → record `HTTP/1.1 200` + `x-vercel-ai-ui-message-stream: v1` + the first few `data:` lines (redact content). A 204 (idle) run additionally proves auth; the PR must include the 200 capture.

## Regression risks and concerns

- **Auth surface widening.** The catch-all now exposes `one-time-token/generate` (session-gated) and `one-time-token/verify` (public). Bounded by design: single-use, 3-minute TTL (`expiresIn: 3`), SHA-256-hashed at rest (`storeToken: "hashed"`). The verify endpoint must never 500 on garbage input (contract test asserts 4xx).
- **Bearer forgery.** `requireSignature: true` means only HMAC-signed values verify against `BETTER_AUTH_SECRET`; the tampered/raw-token tests pin this. Do not weaken to `requireSignature: false` for any reason.
- **Open-redirect risk on the two new routes.** `complete` redirects only to the constant `openagents://auth`; `bridge` only through `sanitizeInternalRedirect` (same-origin path) — tests (b)/(c) in file 5 pin it. `trustedOrigins` prefix-matching whitelists every `openagents://…` URL; acceptable per plan (scheme-hijack exposure is bounded to the OTT, `docs/plans/ios-app/04-auth.md` §11.5).
- **Web cookie behavior drift.** The bearer after-hook adds a `set-auth-token` header to better-auth responses that set the session cookie — header-only, additive; the cookie itself, CSRF origin-check, and the test-auth cookie precedence in `getSessionFromReq` are unchanged. The Authenticated Local UI Smoke in the checklist guards this.
- **better-auth minor drift.** The pin is `^1.6.5`; the behaviors used are public documented APIs, and `apps/web/lib/auth/config.test.ts` + the route tests catch regressions on upgrade (plan risk table, §13).
- **Logging leak risk.** New log lines near credentials. Mitigated by the redaction rules above and the PR redaction grep in the checklist.

## Deploy or migration impact
