## Why this matters

Every REST call the iOS app will ever make — from M3-02/M3-03 facades through every feature screen — flows through the networking core this issue builds in `ios/Packages/APIClient`. It is the single place where bearer tokens are injected and rotated, where `x-request-id` correlation is stamped, where HTTP failures become the one `APIError` taxonomy every caller switches over, where per-class retry/backoff is decided, and where production/preview/localhost environments are switched. If two callers map errors differently, or one path misses a `set-auth-token` rotation, the app gets unexplainable sign-outs and inconsistent error UX that no later layer can fix. Building it once, middleware-driven and table-tested, is what makes the rest of the epic mechanical.

## User/operator path protected

P11 (new row added to the `docs/plans/ios-app/06-testing-strategy.md` section 2 catalog in this PR): **every API call shares one error taxonomy, one request-id/auth/rotation behavior, and one environment configuration — whether it goes through the generated client or the hand-rolled `RawHTTPClient`.** Concretely: a `set-auth-token` rotation observed on any response is persisted before the caller sees the response; a 401 anywhere signals the auth layer exactly once; a 409 "Sandbox is unavailable" maps to `.conflict(kind: .sandboxUnavailable)` everywhere so the global Resume affordance (M9-01) has one trigger.

## Behavior contract

- Given a token store holding `tok-1`, when any request is sent through the standard middleware chain, then the request carries `Authorization: Bearer tok-1` and `x-request-id: ios.<lowercase-uuidv4>` (format from `RequestID.generate()` in the `Observability` package, matching the server pattern in `apps/web/lib/harness/request-id.ts`).
- Given a 200 response carrying header `set-auth-token: tok-2`, when the middleware chain returns, then `tokenStore.update(token: "tok-2")` has already been awaited (rotation persists before the caller can act on the response), and the response body is still fully readable downstream.
- Given a 401 response (JSON `{"error":"Not authenticated"}` or the stream route's plain-text body), when it passes through `AuthMiddleware`, then the injected `onAuthFailure` callback is invoked exactly once for that response (never per retry attempt — 401 is never retried), and the mapped error is `APIError.notAuthenticated`.
- Given a GET that fails with 503 twice then succeeds, when sent through `RetryMiddleware` with a pinned jitter source and a recording delayer, then exactly 3 requests are made and the recorded base delays are 0.5 s then 1.0 s plus full jitter (`Double.random(in: 0...delay)` added).
- Given a POST to a non-allowlisted mutation that returns 503, when sent through the chain, then no retry happens and the caller gets `APIError.server(status: 503, ...)`. Given the same POST failing with `URLError(.cannotConnectToHost)` (provably pre-send), then exactly one retry happens. Given it fails with `URLError(.networkConnectionLost)` (bytes may have been sent), then no retry happens and the error maps to `.offline`.
- Given a 409 response with body `{"error":"Sandbox is unavailable. Please resume sandbox."}`, when mapped, then the result is `.conflict(kind: .sandboxUnavailable, message: ...)` and it is never retried regardless of method or class.
- Given a 429 with header `Retry-After: 7` on a retryable GET, when retried, then the delay is exactly 7.0 s with no jitter, and the mapper produces `.rateLimited(retryAfter: 7)`; with the header absent, `retryAfter` is `nil`.
- Given the environment is switched to `.preview` with a bypass secret set (DEBUG build), when any request is sent, then it carries `x-vercel-protection-bypass: <secret>`; in `.production` and `.localhost` the header is never present. Given a Release build, then the environment is always `.production` regardless of any persisted override (the override read is compiled out).
- Given `NetworkingContainer.setEnvironment(.localhost)`, when the next request is sent, then it targets `http://localhost:3000`, the previous `URLSession`s have been invalidated, and `configuration.keychainTokenAccount` now reads `session-token.localhost.localhost` (the per-environment token namespacing hook M4-01 consumes).
- Given a class-L operation (long-running client), when its request fails, then it is never retried automatically — the long-running client's chain contains middlewares 1–4 only.
- Given a `RawHTTPClient` GET to a `text/plain` endpoint, when sent, then middlewares 1–4 are applied (request id, bearer, env header, logging) and `RetryMiddleware` is not; a `set-auth-token` on its response is persisted identically to the generated-client path.

## Product and design spec

Developer-facing infrastructure; no end-user UI ships in this slice.

- Entry points: the `APIClient` package's public API (`NetworkingContainer`, `RawHTTPClient`, `APIError`, `AppEnvironment`, `EnvironmentStore`) consumed by M3-02/M3-03 facades, M4 AuthKit wiring, and M7 StreamEngine.
- Environment switching states: `.production` (default, the only state in Release), `.preview` (base URL + bypass secret from `UserDefaults`), `.localhost` (`http://localhost:3000`, served by `bun run web`). The Settings > Developer picker UI that renders this is later Settings-feature scope; this issue ships the complete DEBUG-gated backing store (`EnvironmentStore`) and the rebuild behavior, so the picker becomes a three-row form over an existing API.
- Error "copy": `APIError` preserves server `error` strings verbatim in associated values; user-facing copy keys are `07-observability.md` section 12 / feature scope. Nothing in this layer invents user-facing strings.
- Loading/empty/error behavior, accessibility: not applicable (no UI). The observable "UX" of this slice is log lines (section below) and thrown `APIError` values.
- Permissions: none. No new entitlements, no Info.plist changes.

- `api_request_finished` — notice — `request_id` (the **echoed** `x-request-id` when present, else ours), `method`, `operation_id`/`path`, `status`, `duration_ms`.
- `api_request_failed` — error — same fields plus `status` (0 if no response) and `error_kind` (section 6 registry via `APIError.errorKind`).
- `api_retry_scheduled` — notice — `request_id`, `attempt`, `delay_ms`, `error_kind` (per-attempt visibility; `started`/`finished` bracket the whole logical call because Retry is innermost).
- `api_rate_limited` — notice — `request_id`, `path`, `retry_after_s`.
- `api_botid_blocked` — notice — `request_id`, `path` (new registry row added by this PR; gives the M1-07 server exemption real-world signal).

## Regression risks and concerns

- **`AppEnvironment` name collision**: AppShell's M2-01 placeholder DI class shares the name. Different modules, so it compiles; AppShell must module-qualify (`APIClient.AppEnvironment`) until M5-02 renames its container. Flagged in the PR body and `docs/agents/lessons-learned.md` if it bites.
- **Middleware array ordering** is an swift-openapi-runtime implementation contract (index 0 outermost). `MiddlewareOrderTests` pins it; if a runtime bump flips it, fix `MiddlewareChain` only.
- **HTTPBody is a one-shot stream**: `AuthMiddleware`'s 401 body buffering must re-wrap the body for downstream or every 401 handler upstream sees an empty body. Covered by `plainText401AlsoSignals` + the end-to-end test asserting bodies remain decodable after the chain.
- **Retry-attempt interpretation**: the source doc's "up to 3 attempts" with three backoff values is internally ambiguous; this issue pins 3 retries / 4 total requests consuming delays 0.5/1.0/2.0 s. If review prefers 3 total, change `RetryPolicy.maxRetries` and the two affected test rows — one constant, one table.
- **401 signaling relaxation** (any 401, not only the JSON body) could over-signal on odd endpoints; M4-03's single confirmation probe before sign-out is the designed guard. Do not add dedupe state here — exactly-once is per response by construction.
- **Idempotent allowlist strings** (`createChat`, `markChatRead`, `pingSandboxActivity`) reference operations that enter the spec in M1-02/M1-03; they are plain strings here. M3-02/M3-03 must keep the allowlist in sync when facades land — noted in their scopes' source doc (section 4.4).
- **Determinism**: any `Task.sleep`, `Date()`, or live `Double.random` in tests is a defect (06-doc flake policy); the delayer/jitter/clock are always injected. `UserDefaults`-touching suites are `.serialized` with scratch suites.
- **Strict concurrency**: APIClient is nonisolated-default; `NetworkingContainer` is explicitly `@MainActor`. If generated-client construction or `@Observable` produces Swift 6.2 diagnostics under the Template-B flags, record the exact diagnostic in `docs/agents/lessons-learned.md` and adjust only this package's `swiftSettings` with a comment.
