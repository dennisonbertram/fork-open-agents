## Why this matters

Vercel OAuth (M4-01) is a third-party login service, so App Store guideline 4.8 requires an equivalent privacy-preserving alternative — without Sign in with Apple the app is rejected at review and nothing else in the epic ships. SIWA is also the only sign-in that needs no browser, no deep link, and no one-time token: `ASAuthorizationAppleIDProvider` mints an identity token on-device, one `POST /api/auth/sign-in/social` exchanges it, and the `set-auth-token` response header is the bearer token (per `docs/plans/ios-app/04-auth.md` §3.9 this is one of exactly two responses that carry it). This slice completes the M4 goal for users who have no Vercel account at all.

## User/operator path protected

A signed-out user on SCR-01 taps the system "Sign in with Apple" button, completes Face ID / Touch ID in the native sheet, and reaches the signed-in state with a working bearer token: the `set-auth-token` value is persisted through the M4-01 token store, `GET /api/auth/info` with `Authorization: Bearer <token>` returns their user, and no token material, identity token, or nonce ever appears in any log. Cancelling the Apple sheet returns silently to SCR-01 with no error shown.

## Behavior contract

- Given a signed-out user on the sign-in surface, When they tap `SignInWithAppleButton(.signIn)` and complete the native Apple sheet, Then `AppleSignInCoordinator` extracts `identityToken` from the `ASAuthorizationAppleIDCredential`, sends `POST {baseURL}/api/auth/sign-in/social` with body `{"provider":"apple","idToken":{"token":"<identityToken UTF-8>","nonce":"<nonce>"}}` where `nonce` is byte-for-byte the same string set on `ASAuthorizationAppleIDRequest.nonce`, And on a 200 response stores the `set-auth-token` header value via the M4-01 token store, And the sign-in flow reports success.
- Given the coordinator prepares a request, When `configure(_:)` runs, Then it sets `requestedScopes = [.fullName, .email]` and a fresh nonce (32 random bytes, lowercase hex, 64 characters) — never SHA-256-hashed across the client/server boundary (better-auth compares the claim verbatim, `docs/plans/ios-app/04-auth.md` §3.4.3).
- Given the user dismisses the Apple sheet, When the completion delivers `ASAuthorizationError.canceled`, Then the flow ends silently: no error UI, no error-level log, one `auth_signin_cancelled` notice event, and the sign-in surface is unchanged (SCR-01 copy rule: "cancel produces no error").
- Given the token exchange returns a non-200 status (e.g. 401 from a nonce or audience mismatch), When the coordinator inspects the response, Then it throws `AuthError.tokenExchangeFailed(status:)`, emits `auth_signin_failed` with the mapped `error_kind`, and the standard sign-in error state shows "Sign-in didn't finish. Try again." (SCR-01 footnote copy).
- Given the exchange returns 200 but no `set-auth-token` header (edge case), When the coordinator validates the response, Then it throws `AuthError.tokenExchangeFailed` with `error_kind=contract_missing_header` — a 200 without the token must never be treated as signed in.
- Given Apple returns a credential with a missing or non-UTF-8 `identityToken`, or `handle` is invoked with no stored nonce (edge case), When the coordinator validates inputs, Then it throws `AuthError.appleCredentialIncomplete` and emits `auth_signin_failed` with `error_kind=auth_apple_credential_invalid`.
- Given the Keychain write fails after a successful exchange (edge case), When the token-store update throws, Then the coordinator emits `auth_token_persist_failed` at fault with the `keychain_status` and surfaces the standard sign-in error state (a token that will not survive relaunch is a failed sign-in).
- Given a returning Apple user (subsequent authorization), When Apple omits email and name (it sends them only on first authorization), Then sign-in still succeeds — the server keys on the stable `sub` claim.
- Given an Apple-only account, When the app later fetches `GET /api/auth/info`, Then `hasGitHub == false` and the account has no Vercel connection; the app never branches on `authProvider` (the server hardcodes `"vercel"` — known cosmetic gap, `docs/plans/ios-app/04-auth.md` §3.4.3). The gating consequences are recorded for onboarding (see Integration spec) but the gated UI itself is M5-03 scope.
- Given each new sign-in attempt, When `configure(_:)` runs again, Then a new nonce replaces the previous one — a stale nonce from an abandoned attempt can never validate a later credential.

## Product and design spec

- **Entry point:** the sign-in surface (SCR-01 Welcome in `docs/plans/ios-app/01-product-and-ux.md`). This issue ships the reusable button component and coordinator; M5-03 composes the final Welcome screen and owns its snapshots.
- **Button:** SwiftUI `SignInWithAppleButton(.signIn)` (system control — exact Apple-mandated artwork), `.signInWithAppleButtonStyle(.black)` in light mode and `.white` in dark mode, rendered at the same width and height as the "Continue with Vercel" `.glassProminent` button, stacked above it. Guideline 4.8 requires the alternative be "equivalent" — equal prominence is a review requirement, not a styling preference.
- **Primary flow:** tap → native Apple sheet (no browser, no SCR-02 web handoff) → on credential return, the in-progress state shows the labeled spinner "Signing you in…" (SCR-02 treatment) for the duration of the token exchange → signed-in.
- **States:** cancel → silent return, no footnote. Exchange failure → SCR-01 inline footnote under the buttons: **"Sign-in didn't finish. Try again."** Offline → the button is disabled with footnote **"You're offline. Connect to sign in."** (offline detection wiring is the sign-in surface's concern; the coordinator maps `NSURLErrorNotConnectedToInternet` to `error_kind=network_offline`).
- **Accessibility:** the system button carries its own localized label; the in-progress state has `accessibilityLabel("Signing you in")` per the SCR-01/02 accessibility table.
- **Permissions/copy:** no permission prompts. All copy verbatim from SCR-01/SCR-02 — do not invent new strings.

## Integration spec

- **Package:** `ios/Packages/AuthKit` (the `04-auth.md` package name `OpenAgentsAuth` is normalized to `AuthKit` per the `docs/plans/ios-app/03-architecture.md` naming-normalization rule; M2-01 created the package: Template A, MainActor-default, iOS-only, deps `OpenAgentsCore` + `Observability`, deliberately **not** `APIClient`).
- **New files:**
  - `ios/Packages/AuthKit/Sources/AuthKit/AppleSignInCoordinator.swift` — `@MainActor final class`; `configure(_ request: ASAuthorizationAppleIDRequest)` (sets scopes + fresh nonce, stores `currentNonce`), `handle(result: Result<ASAuthorization, any Error>) async` (maps the credential to a payload and runs the exchange), and a nonisolated `static func randomNonce() -> String` using `SecRandomCopyBytes` (32 bytes → 64-char lowercase hex).
  - `ios/Packages/AuthKit/Sources/AuthKit/AppleIDCredentialPayload.swift` — `struct AppleIDCredentialPayload: Sendable, Equatable { let identityToken: Data? }` plus an extension mapping `ASAuthorizationAppleIDCredential` → payload. This seam exists because `ASAuthorizationAppleIDCredential` has no public initializer and cannot be constructed in tests; all exchange logic takes the payload.
  - `ios/Packages/AuthKit/Sources/AuthKit/AppleSignInButton.swift` — SwiftUI view wrapping `SignInWithAppleButton(.signIn)` with `onRequest: coordinator.configure` and `onCompletion` dispatching to `handle(result:)`; exposes a completion callback for the host screen.
- **Server surface (already shipped by M0-02; verify deployed before starting):** `POST {baseURL}/api/auth/sign-in/social`, headers `Content-Type: application/json`, `Origin: openagents://`, `x-request-id: ios.<uuid>`; body `{"provider":"apple","idToken":{"token":"<jwt>","nonce":"<nonce>"}}`; success = 200 with a non-empty `set-auth-token` response header (decode the JSON body leniently — `{"user":...,"session":...}` or `{"token":...,"user":...}` shapes both occur; the header is the source of truth). No cookies, no `Authorization` header on this request.
- **Reused from M4-01 (do not duplicate; discovery task in the checklist):** the `AuthTokenStore` protocol from `OpenAgentsCore` (`currentToken()/update(token:)/clear()` — the coordinator depends on the protocol so tests inject an in-memory fake; production injects `KeychainTokenStore`), AuthKit's raw URLSession POST helper (ephemeral, cookie-free configuration per `04-auth.md` §8.2), the `AuthError` enum (extend with `.appleCredentialIncomplete` if M4-01 did not add it), and the `redactedForLogging` URL helper.
- **Bundle-id coordination (load-bearing):** the identity token's `aud` claim equals the built app's bundle identifier, and the server validates it against `APPLE_APP_BUNDLE_IDENTIFIER`. `docs/plans/ios-app/03-architecture.md` pins `PRODUCT_BUNDLE_IDENTIFIER: com.openagents.app` while `docs/plans/ios-app/04-auth.md` examples use `com.openagents.ios`. The app's `ios/App/project.yml` value is authoritative — verify the deployed server env matches it and correct the **server env var** (never the bundle id) on mismatch. The Apple Developer App ID with the Sign in with Apple capability must be registered for that same bundle id; the `com.apple.developer.applesignin: [Default]` entitlement already exists in `ios/App/project.yml` (M2-01).
- **Events/observability:** per the Observability section below; emitted through the `EventLogging` facade on the `auth` OSLog category.
- **Onboarding gating record:** the Apple-only user has no Vercel OAuth token (workspace/sandbox creation runs on the user's Vercel account) and no GitHub connection (`hasGitHub == false` from `GET /api/auth/info`). Record this in `docs/plans/ios-app/01-product-and-ux.md` (Onboarding group): if the section already covers the GitHub-less state via SCR-03 but lacks the missing-Vercel-connection gate, append a short "Apple-only accounts" note naming both gates and the bridge-route connect flows (`04-auth.md` §3.7) as the remedies, marked as M5-03 input.
- **Compatibility:** no web routes, schema, or env-var code changes in this slice. No new third-party dependencies. `AuthenticationServices` is already importable (AuthKit is iOS-only).

## Regression risks and concerns

- **Nonce hashing trap:** copying the widespread Firebase SIWA sample (SHA-256 the nonce before `request.nonce`) breaks every sign-in with a server-side nonce mismatch. `configureSetsScopesAndVerbatimNonce` plus `exchangeSendsVerbatimNonceAndProviderApple` pin the verbatim contract.
- **Audience mismatch:** if `APPLE_APP_BUNDLE_IDENTIFIER` on the server differs from the app's real bundle id (the docs currently disagree: `com.openagents.app` vs `com.openagents.ios`), every native sign-in fails JWT audience validation with a non-obvious 401. The checklist's grep + env verification step is the guard; report the mismatch rather than silently "fixing" either side.
- **Cancel treated as error:** surfacing `ASAuthorizationError.canceled` as a failure produces a noisy, review-flaggable UX. The events test pins silence.
- **Token leakage:** a stray `Logger` interpolation of the JWT or header value is unrecoverable once shipped. Double guard: the `noTokenMaterialInAnyEventField` test and the §11.7 grep proof.
- **First-authorization-only email/name:** testing repeatedly against one Apple ID hides the returning-user path. Use Settings → Apple Account → Sign-In & Security → Sign in with Apple → delete the app association to re-test the "first" flow; verify both.
- **M4-01 API drift:** if M4-01's helper/`AuthError` names differ from the sketches, blindly following `04-auth.md` §8.6 creates duplicates. The discovery checklist item exists for this; reconcile toward M4-01's shipped names.
- **Sibling overlap:** do not implement `signInWithApple()` on `AuthController` (M4-03) or compose SCR-01 (M5-03); keep this slice's public surface to the coordinator + button so the siblings consume it.
