## Why this matters

App Store guideline 5.1.1(v) requires that an app supporting account creation lets users initiate account deletion inside the app. The repo has no deletion path today (verified: no `delete-user` or `deleteAccount` route exists anywhere under `apps/web/app/api`). Without this slice the iOS app cannot pass App Review.

Sign-out has a parity gap: the only sign-out path that revokes the user's Vercel OAuth token is the web server action in `apps/web/lib/auth/actions.ts`, and native clients cannot call server actions. The better-auth built-in `POST /api/auth/sign-out` kills the session row but leaves the Vercel OAuth token alive. This slice gives native clients a single bearer-authenticated route with full parity, and enables better-auth's `delete-user` endpoint with a `beforeDelete` revocation hook.

This is the last M0 auth enabler: after M0-01 (bearer + OTT + handoff routes), M0-02 (Sign in with Apple), and this issue, `apps/web` is a complete auth platform for native clients.

## User/operator path protected

A bearer-authenticated native client can sign out (better-auth session row destroyed and the Vercel OAuth token revoked, best-effort) and can delete its account entirely in-app (`users` row plus every cascading table gone in one transaction). Web cookie sign-out via the `signOut` server action keeps working unchanged.

This is protected path P8 ("A user can delete their account from the app — App Store guideline 5.1.1(v)") from `docs/plans/ios-app/06-testing-strategy.md` section 2, and it extends P1 (session lifecycle).

## Behavior contract

- Given a valid signed bearer token for an existing session, when the client sends `POST /api/native-auth/sign-out` with `Authorization: Bearer <token>.<sig>` and no cookies, then the response is `200 {"success":true}`, the `auth_sessions` row for that token is deleted (a subsequent `getSessionFromReq` with the same bearer returns `undefined`), and the user's Vercel OAuth token was submitted to `https://api.vercel.com/login/oauth/token/revoke` before the session was destroyed.
- Given no `Authorization` header and no session cookie, when the client sends `POST /api/native-auth/sign-out`, then the response is `401 {"error":"Not authenticated"}` and no sign-out or revocation side effect occurs.
- Given the Vercel revocation fetch throws or the env vars `NEXT_PUBLIC_VERCEL_APP_CLIENT_ID` / `VERCEL_APP_CLIENT_SECRET` are unset, when a bearer-authenticated client signs out, then revocation is skipped or swallowed (logged at warn), the session is still destroyed, and the response is still `200 {"success":true}` — revocation is best-effort and never blocks sign-out.
- Given a user with no Vercel account row (e.g. an Apple-only user from M0-02), when they sign out, then `getRevocableVercelToken` returns `null`, no revoke call is made, and sign-out succeeds.
- Given a bearer session created less than 24 hours ago (better-auth `freshAge` default), when the client sends `POST /api/auth/delete-user` with body `{}` (empty JSON object, no `password` field), then the response is `200 {"success":true,"message":"User deleted"}`, the `users` row is deleted, all `auth_sessions` rows for the user are deleted, and every FK-cascading row (app `sessions`, chats, preferences, agents, usage events, Composio profiles — all 33 `users.id` references in `apps/web/lib/db/schema.ts` declare `onDelete: "cascade"`) is gone.
- Given a bearer session whose `createdAt` is 25 hours old, when the client sends `POST /api/auth/delete-user` with `{}`, then the response is `400` with better-auth `SESSION_EXPIRED` semantics and the `users` row survives (iOS handles this with a re-auth-then-retry flow per `docs/plans/ios-app/04-auth.md` section 8.9 — not built here).
- Given an OAuth-only user sends `{"password":"anything"}` instead of `{}`, when they call `POST /api/auth/delete-user`, then the response is `400` `CREDENTIAL_ACCOUNT_NOT_FOUND` (these users have no credential account) — this is why the documented client body is exactly `{}`.
- Given the `beforeDelete` revocation hook fails internally (token lookup or revoke fetch throws), when a fresh-session user deletes their account, then deletion still completes — the hook swallows all of its own errors. (Load-bearing: better-auth `await`s `beforeDelete` and an unhandled throw would block deletion; verified in `apps/web/node_modules/better-auth/dist/api/routes/update-user.mjs`.)
- Given the web app, when a signed-in browser user triggers the existing `signOut` server action, then behavior is byte-identical to today (the action now imports the moved helpers from `apps/web/lib/auth/revoke-vercel-token.ts`).

## Product and design spec

This is a server-only slice. There is no web UI change and no iOS code in this issue (the iOS sign-out and deletion screens are specified in `docs/plans/ios-app/04-auth.md` sections 8.8-8.9 and built in a later milestone). The "product surface" is two HTTP contracts:

| Surface | Method | Auth | Request body | Success | Errors |
|---|---|---|---|---|---|
| `/api/native-auth/sign-out` | POST | bearer or cookie session | none | `200 {"success":true}` | `401 {"error":"Not authenticated"}` |
| `/api/auth/delete-user` (better-auth catch-all; no new file) | POST | bearer or cookie session, fresh (< 24 h old) | `{}` | `200 {"success":true,"message":"User deleted"}` | `401` no session; `400` `SESSION_EXPIRED` stale session; `400` `CREDENTIAL_ACCOUNT_NOT_FOUND` if `password` sent |

Permissions: any valid better-auth session for the calling user; both endpoints only ever act on the caller's own account. Loading/empty states are client concerns. Accessibility: not applicable server-side.

Copy deliverable — App Review notes text (paste into the PR description verbatim; the iOS submission issue will lift it from there):

> Account deletion (`POST /api/auth/delete-user`) deletes the user row and all server-side data transactionally (sessions, chats, preferences, agents, background agents, usage events, Composio profiles — every foreign key cascades). Two external artifacts survive: (1) the GitHub App installation on the user's GitHub account/org is a GitHub-side object; the user uninstalls it via GitHub Settings → Applications; (2) any live Vercel sandboxes expire on their own timeout. With Sign in with Apple's idToken-only flow the server holds no Apple refresh/access token, so there is nothing to revoke at `appleid.apple.com/auth/revoke`.

## Integration spec

- New route: `apps/web/app/api/native-auth/sign-out/route.ts` — exactly the snippet in `docs/plans/ios-app/04-auth.md` section 3.5 plus the structured logging below. It uses `getSessionFromReq` (`apps/web/lib/session/server.ts`) and `auth.api.signOut({ headers: req.headers })`; both pass full request headers through the M0-01 bearer plugin, so the route works with `Authorization: Bearer` and zero cookies.
- Newly enabled endpoint: `POST /api/auth/delete-user`, served by the existing catch-all `apps/web/app/api/auth/[...all]/route.ts` once `user.deleteUser.enabled: true` lands in `apps/web/lib/auth/config.ts`. Do not create a route file for it. Do not configure `sendDeleteAccountVerification` (it would change the success response to "Verification email sent"). Do not change `freshAge`.
- New module: `apps/web/lib/auth/revoke-vercel-token.ts` — `revokeVercelToken` and `getRevocableVercelToken` moved **verbatim** from `apps/web/lib/auth/actions.ts` (including the `VERCEL_REVOKE_URL` constant), both exported. `actions.ts` keeps only the `signOut` server action, importing the helpers. Per the repo file-organization rule, do not append the route logic to `actions.ts`.
- New module: `apps/web/lib/auth/native-auth-log.ts` — the `native-auth` structured-event emitter (see Observability). If M0-01 already landed a `native-auth` logging helper for the complete/bridge routes, extend that file instead of creating a duplicate.
- Edited: `apps/web/lib/auth/config.ts` — extend the existing `user` block with the `deleteUser` config from `docs/plans/ios-app/04-auth.md` section 3.6. **Import-cycle warning (verified):** `apps/web/lib/vercel/token.ts` imports `auth` from `@/lib/auth/config`, so a static import of the revocation helpers inside `config.ts` creates the cycle config → revoke-vercel-token → vercel/token → config. Use a dynamic import inside the hook:

```ts
    deleteUser: {
      enabled: true,
      beforeDelete: async (user) => {
        try {
          const clientId = process.env.NEXT_PUBLIC_VERCEL_APP_CLIENT_ID;
          const clientSecret = process.env.VERCEL_APP_CLIENT_SECRET;
          if (clientId && clientSecret) {
            const { getRevocableVercelToken, revokeVercelToken } = await import(
              "@/lib/auth/revoke-vercel-token"
            );
            const token = await getRevocableVercelToken(user.id);
            if (token) {
              await revokeVercelToken({ token, clientId, clientSecret });
            }
          }
        } catch {
          // never block deletion on revocation failure (better-auth awaits this hook)
        }
      },
    },
```

- Data model: no schema change, no migration. Deletion relies entirely on the existing `onDelete: "cascade"` declarations in `apps/web/lib/db/schema.ts`.
- Config/env: reuses existing `NEXT_PUBLIC_VERCEL_APP_CLIENT_ID` and `VERCEL_APP_CLIENT_SECRET`; when absent, revocation is skipped silently (both code paths already guard on them).
- Compatibility: purely additive. Web cookie flows are untouched. `apps/web/openapi.json` is untouched (documenting `/api/native-auth/sign-out` belongs to the M1 contract-expansion milestone), so `bun run --cwd apps/web openapi:check` stays green with no action.
- Depends on M0-01: the bearer plugin must already be in `apps/web/lib/auth/config.ts` or the bearer round-trip tests cannot pass.

## Observability and user feedback

User-visible status: the HTTP responses themselves (`{"success":true}` / `{"error":"Not authenticated"}` / better-auth's 400 bodies) — the iOS client maps them to the section 8.8/8.9 UX and logs the paired client events `auth_signout` and `auth_account_deletion_started|succeeded|failed` (`docs/plans/ios-app/07-observability.md` section 4.1), joinable on the same `x-request-id`.

Named module: `apps/web/lib/auth/native-auth-log.ts`, service `native-auth`. `logNativeAuthEvent(level, event)` emits one single-line JSON object per event to `console.info`/`console.warn`/`console.error`: `{ "service": "native-auth", "timestamp": <ISO8601>, "event": ..., ...fields }`. The helper's field type accepts only strings, numbers, and booleans — it has no parameter that could carry a token.

Events (all fields snake-free camelCase to match the repo's JSON logging):

| Event | Level | Fields |
|---|---|---|
| `sign_out_succeeded` | info | `requestId`, `userId`, `vercelTokenRevoked` (boolean), `durationMs` |
| `sign_out_unauthenticated` | warn | `requestId`, `errorKind: "not_authenticated"` |
| `vercel_token_revocation_failed` | warn | `requestId` (sign-out only), `userId`, `context` (`"sign_out"` \| `"delete_user"`), `errorKind: "revocation_failed"` |
| `delete_user_before_delete` | info | `userId`, `vercelTokenRevoked` (boolean) |

Typed error kinds: `not_authenticated`, `revocation_failed`. (`getRevocableVercelToken` swallows lookup errors and returns `null` by design; that surfaces as `vercelTokenRevoked: false`, not an error event.)

Correlation IDs: `requestId` comes from `getRequestId(req.headers)` in `apps/web/lib/harness/request-id.ts`, which honors the iOS client's `x-request-id: ios.<uuid>` header (07-observability section 5.2); `userId` is the better-auth id on every event that has a session. No `sessionId`/`chatId` — these routes are not chat-scoped.

Redaction rules: never log the bearer token, the `Authorization` or `set-auth-token` header values, the Vercel OAuth token, or `VERCEL_APP_CLIENT_SECRET` — only booleans, ids, durations, and stable enum strings. The PR attaches the grep proof required by `docs/plans/ios-app/04-auth.md` section 11.7 (command in the checklist).

Debug recipes:

```bash
# Local dev server
bun run web 2>&1 | grep '"service":"native-auth"'

# Production / preview
vercel logs <deployment-url> | grep '"service":"native-auth"' | grep '"event":"sign_out_succeeded"'

# Did sign-out actually kill the session? (expect 0 rows)
psql "$POSTGRES_URL" -c "SELECT count(*) FROM auth_sessions WHERE user_id = '<userId>';"

# Did deletion actually cascade? (expect 0 rows each)
psql "$POSTGRES_URL" -c "SELECT count(*) FROM users WHERE id = '<userId>';"
psql "$POSTGRES_URL" -c "SELECT count(*) FROM sessions WHERE user_id = '<userId>';"
```

## Regression risks and concerns

- Web sign-out regression: the server action in `apps/web/lib/auth/actions.ts` has no test of its own; the helper move must be verbatim, with `turbo typecheck --filter=web` (inside `bun --bun run ci`) as the wiring gate. Do not change its behavior or signatures.
- `beforeDelete` blocking deletion: better-auth `await`s the hook with no internal try/catch — all error handling must live inside the hook body (covered by test 4c).
- Import cycle: a static import of the revocation helpers in `config.ts` creates config → revoke-vercel-token → vercel/token → config. The dynamic import in the hook is mandatory, not stylistic.
- Destructive endpoint exposure: enabling `deleteUser` exposes self-serve deletion to all clients including the web origin. That is intended (session-gated, freshness-gated, self-only), but the PR description must state it explicitly. Deleted accounts are unrecoverable.
- `next/headers` in `getUserVercelToken`: it calls `await headers()`, which throws outside a Next request scope; the function swallows this and returns `null`, so direct-handler tests must mock `@/lib/auth/revoke-vercel-token` (as specified) rather than relying on the real lookup.
- Dev-only quirk: a request authenticated solely by the test-auth cookie (`apps/web/lib/session/test-auth.ts`) passes `getSessionFromReq` but has no real better-auth session, so `auth.api.signOut` will throw → 500. Document it in the PR if observed; do not add fallback logic in this slice (production native clients always carry real bearer sessions).
- Config hygiene: do not set `freshAge: 0` (disables freshness globally) and do not add `sendDeleteAccountVerification` (changes the success response shape the iOS client depends on).
- Test-data hygiene: DB-backed tests must create and clean up their own `nanoid()`-keyed users; reusing shared fixtures would make `delete-user` tests destroy state other suites rely on.

## Deploy or migration impact

- No schema change, no migration, no new env vars. The slice is config + two new lib files + one new route file.
- Effective immediately on deploy: previews (isolated Neon branches — safe for contract testing) and production both gain `POST /api/native-auth/sign-out` and an enabled `POST /api/auth/delete-user`.
- Vercel revocation already works in production (same env vars the web sign-out action uses); if they are ever absent, both paths degrade to session-only sign-out/deletion without erroring.
- Rollback: revert the PR. Reverting disables the deletion endpoint again (404) and removes the route; already-deleted accounts cannot be restored — state this in the PR's deploy notes.
