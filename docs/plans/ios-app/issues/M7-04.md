## Why this matters

This issue is where the streaming engine becomes a product: M7-01 gave us bytes-to-chunks, M7-02 gave us chunks-to-messages, M7-03 gave us a connection — but nothing yet sends a message, survives a failed send, or shows a pixel. `ChatRuntime` is the iOS equivalent of the web's `useChat` + chat-instance-manager pair: it owns one chat's turn lifecycle, blends local stream state with server `isStreaming` truth, coalesces reducer snapshots onto the main actor at 75 ms so the transcript renders at 60 fps, and writes to GRDB only at turn boundaries so streaming never causes disk I/O per token. The rollback matrix encodes the single most important product promise of the slice: a user's typed message is never silently lost — every failure lands the text either in a retryable failed message or back in the composer. The registry gives the app web parity for navigation: walking away from a streaming chat never kills the run or the local accumulation, and coming back shows the live turn without a refetch. M7-05 (resume/reconnect) and M7-06 (run-watching UI) both build directly on the APIs fixed here.

## User/operator path protected

P3 (`docs/plans/ios-app/06-testing-strategy.md` section 2): a user sends a chat message and watches the assistant reply stream token-by-token — and never loses typed content on failure. Concretely: tap send → optimistic user bubble + `pending_send` outbox row → POST `/api/chat` via the M7-03 `ChatStreamClient` → `start` chunk flips the row to `synced` → coalesced 75 ms flushes update the transcript → `finish` persists the assistant message. Every failure branch (transport error, 4xx/5xx, 409 active-run conflict, archived session) leaves the typed content recoverable via Retry, or restorable to the composer via Delete. Secondary: U3 groundwork — chunks are reduced off-main and the main actor sees at most ~14 updates/s regardless of token rate.

## Behavior contract

- Given an idle `ChatRuntime` for chat C with synced history H, when `send(parts:)` is called with text "fix the bug", then a user message with a fresh client-generated id (`UUID().uuidString.lowercased()`) and a `{"type":"text","text":"fix the bug"}` part is appended to `messages` immediately, `status == .submitted`, exactly one GRDB write occurs (insert with `sync_state = 'pending_send'`, `position` = max existing position + 1), and the POST `/api/chat` body is `{"sessionId": ..., "chatId": ..., "messages": H + [user]}` with every prior part — including `.unknown` parts — re-encoded verbatim (no `context`, `id`, `trigger`, or `messageId` fields).
- Given the POST returned 200 with the `v1` header, when the `start` chunk arrives, then the user row is updated `pending_send → synced` (the second and last write before finish), `status == .streaming`, and an immediate flush publishes the first snapshot without waiting for the 75 ms tick.
- Given chunks arrive faster than 75 ms apart, when the turn streams, then `ChatRuntime.messages` is mutated at most once per flush interval (plus the immediate flushes on first-chunk-after-connect, `finish`, and `error`), only the last array element is replaced per flush, and **zero** GRDB writes occur between the `start`-chunk write and the finish write (the write-point invariant from 05 section 6.1/6.3).
- Given `finish` then EOF arrive cleanly, when the turn ends, then a final immediate flush runs, the assistant message is upserted `synced`, turn registries are discarded, and `status == .ready`.
- Given the send is the first message of a fresh session (the chat is the session's only chat and `messages` was empty before the send), when the send starts, then `optimisticChatTitle` is set to the trimmed text truncated at 80 chars with a `...` suffix when longer (in-memory only — never written to the GRDB `chat` row), `POST /api/generate-title` fires in parallel with body `{"message": "<trimmed text>"}`, and a 200 `{"title": "<non-empty>"}` response triggers `PATCH /api/sessions/{sessionId}` with `{"title": "<generated>"}`. A generate-title or PATCH failure is swallowed silently (the optimistic title stands). A non-first send performs none of these calls, and the parallel title work never delays the chat POST.
- Given the POST fails before any chunk (URLError or 5xx), when the failure is mapped, then the optimistic message stays rendered flagged as failed (`failedSendMessageIds` contains its id), the GRDB row is updated to `failed_send`, `status == .error(...)`, and the optimistic chat title (if set this send) is cleared.
- Given a failed message, when `retryFailedMessage(messageId:)` is called, then the identical body re-POSTs with the **same** message id (server insert-only persistence makes this idempotent) and the happy path resumes; when `deleteFailedMessage(messageId:)` is called instead, then the GRDB row and the in-memory message are removed and the original `[OutgoingMessagePart]` is returned so the composer restores the typed text — typed content is never lost.
- Given the POST returns 409 ("Another workflow is already running for this chat"), when the conflict is handled, then the user message stays `failed_send` flagged with the attach reason (UI copy "Agent is still working" is owned by M7-06), the runtime immediately calls `ChatStreamClient.resume(chatId:)` and applies the replay to a **fresh** `ChatTurnState` seeded with the synced history (rebuild, never append — M7-02's idempotence invariant), and `canSend == false` while the attached run streams.
- Given the POST returns 400 with `"Session is archived"`, then `isSessionArchived == true` (disables the composer in M7-06) and the failed-send handling above still applies.
- Given a clean finish where the final step (parts after the last `step-start`) contains tool parts with `providerExecuted != true` and **all** of them are terminal (`output-available` non-preliminary, `output-error`, or `approval-responded`), when quiescence is evaluated, then the runtime re-POSTs `/api/chat` with the full history ending in that assistant message — at most 5 consecutive times without a new user send; the 6th attempt is blocked, `autoResubmitBlocked == true`, and `chat_auto_resubmit_blocked` is logged.
- Given a clean finish with a `tool-ask_user_question` part in `input-available`, then no resubmit happens; when `addToolOutput(toolCallId:toolName:output:)` is later called with the answers payload, then the tool part mutates to `output-available`, the assistant message upserts to GRDB `synced`, a fire-and-forget `POST /api/sessions/{sessionId}/chats/{chatId}/messages` with `{"message": <assistant message>}` runs (a 409 response is dropped silently), and auto-resubmit then evaluates true and re-POSTs.
- Given `userStopped == true` (set by `stop()`, cleared by the next `send`), then `effectiveStatus == .ready` regardless of any other input; given local status idle and `serverSaysStreaming == true` (fed by `updateServerStreaming(_:)` from the chats poll), then `effectiveStatus == .streaming` and `canSend == false` — the full 05 section 5.6 blend, in that precedence order.
- Given `stop()` is called mid-stream, then the M7-03 stop semantics run (fire-and-forget stop POST with the snapshot, `userStopped` set, instant local cancel) and the runtime upserts the in-flight assistant snapshot to GRDB as `synced` (the server persists the same snapshot from the stop body).
- Given a streaming runtime for chat C, when the user navigates away and back, then `registry.runtime(forChatId: C, sessionId: S)` returns the **same instance**, still accumulating; when `releaseIdleRuntimes()` fires (memory warning or scene background), then only runtimes whose `effectiveStatus` is not `.submitted`/`.streaming` are evicted, and the next `runtime(forChatId:)` call constructs a fresh instance hydrated via `setMessages(_:)` from GRDB by its caller.

## Product and design spec

This slice is engine-only; M7-06 owns pixels, copy, and the composer. The engine must expose exactly the state the UI specs need, so the UI slice is a pure rendering exercise:

- **Entry point:** `ChatStore` (M7-06) obtains the runtime via `ChatRuntimeRegistry.runtime(forChatId:sessionId:)` inside AppShell's `navigationDestination` (03 section 10.5) and binds to its `@Observable` properties.
- **States exposed:** `messages` (full transcript including the in-flight last message), `status` (`.ready/.submitted/.streaming/.error(String)`), `effectiveStatus` (the 5.6 blend driving the send/stop button and the `status.stream.*` copy keys from `docs/plans/ios-app/07-observability.md` section 12.2), `serverSaysStreaming`, `failedSendMessageIds: Set<String>` (drives the failed badge with Retry/Delete actions), `isSessionArchived` (disables the composer with the "Session is archived" banner), `autoResubmitBlocked` (drives a banner), `optimisticChatTitle` (chat header overlay), `pendingQuestion` (the `tool-ask_user_question` input payload when paused — drives the M7-06 question wizard).
- **Error/empty/loading behavior:** every failure surfaces through `status == .error(message)` plus the structured flags above; the engine never presents UI and never localizes — copy keys are owned by `docs/plans/ios-app/01-product-and-ux.md`.
- **Accessibility/permissions:** none in this slice (no views, no prompts).

## In scope

- `ChatRuntime`, `ChatRuntimeRegistry`, and the `ChatStreamReducer` engine actor wiring M7-03's connection to M7-02's reducer with 75 ms coalesced latest-value flushes (immediate on first chunk, `finish`, `error`).
- The full send flow per 05 sections 5.1–5.2: minimal POST body, stable client ids, full-history echo-back, optimistic insert, `pending_send → synced` on `start`.
- The 05 section 5.3 rollback matrix: failed-send flagging with Retry/Delete (Delete returns the parts for composer restoration), 409 attach-to-active-run via a single GET resume onto a fresh seeded `ChatTurnState`, archived-session flag, structural 409 prevention via `canSend`.
- `effectiveStatus` blend + `updateServerStreaming(_:)` + `userStopped` interaction; the runtime-side `stop()` write point.
- Auto-resubmit per `shouldAutoSubmit` with the 5-run guard, and the `addToolOutput` round trip (local mutation, GRDB upsert, belt-and-braces messages POST, re-POST).
- First-message title flow: in-memory 80-char optimistic chat title, parallel `POST /api/generate-title`, session PATCH, failure-silent semantics, clear-on-send-failure.
- Registry lifetime rules: survive navigation while streaming; evict idle on memory warning and scene background (wiring in AppShell).
- GRDB write-point coverage via the `TranscriptWriting` seam, including the no-writes-between-boundaries invariant test.

## Regression risks and concerns

- **Duplicate sends / lost idempotency:** Retry must reuse the original message id and byte-identical body — generating a fresh id on retry would duplicate the user message server-side. File 3 asserts id stability.
- **Write amplification:** any code path that writes GRDB per chunk or per flush silently destroys battery and the section 7 budget. The recording-fake invariant in file 1 is the guard; reviewers reject any new `TranscriptWriting` call site not in the 05 section 6.3 table.
- **409 attach appending onto partial state:** applying the GET replay onto existing in-memory state duplicates every part (the web's documented jank). The attach path must always seed a fresh `ChatTurnState` from synced history — file 3 byte-compares the result.
- **Auto-resubmit loops:** a server/client disagreement on tool terminality could ping-pong POSTs forever; the 5-run guard plus `chat_auto_resubmit_blocked` is the circuit breaker. Never raise the limit to "fix" a loop — diagnose the terminality bug.
- **Registry leaks vs over-eviction:** evicting a streaming runtime kills local accumulation mid-turn (content reappears only after M7-05 resume); never evicting leaks one runtime per visited chat. The eviction predicate is `effectiveStatus`-based and tested both ways in file 7.
- **Main-actor contention:** `ChatRuntime` is `@MainActor`, but chunk handling must stay in the `ChatStreamReducer` actor — a careless `await runtime.something()` per chunk reintroduces per-token main-thread hops. The flush-count assertion in file 2 catches it.
- **Title clobbering:** writing the optimistic title to the GRDB `chat` row would fight the next poll's server truth; it stays in-memory (`optimisticChatTitle`) by design. A failed generate-title must never surface an error — the web swallows it.
- **Seam drift with M6-04/M7-05:** `TranscriptWriting` is the shared boundary; renaming or bypassing it in M7-05 (`partial_stream`) would fork persistence behavior. The protocol lives in StreamEngine precisely so both slices compile against one contract.
