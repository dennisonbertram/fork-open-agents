## Why this matters

This slice is the first time a user sees the product's center of gravity — the agent transcript — on iOS. M6-01/M6-04 made transcripts durable in GRDB and M6-02 made sessions tappable, but tapping a session today dead-ends. M6-05 turns `SessionsRoute.chat` into a real screen: cached messages render instantly from GRDB (cache-first, P9), assistant prose renders as real Markdown blocks (apple/swift-markdown into per-block SwiftUI views, the §5.2 architecture M7's streaming renderer will reuse unchanged), code renders through CodeUI's `CodeBlockView` with off-main Highlightr highlighting and the two token-tied themes, and reasoning parts render collapsed. It also ships the chat shell states every later milestone assumes exist: the archived banner with a working Unarchive action, the offline cached banner, and the empty-chat suggestion chips. M6-06 (tool rows), M7 (streaming), and M8 (composer) all bolt onto the `ChatScreen`/`MessageRow`/`MessageBlock` structure fixed here — getting block identity and parse-once caching right now is what keeps streaming from relayouting the transcript later (P2 groundwork).

## User/operator path protected

P9 + P5 (`docs/plans/ios-app/06-testing-strategy.md` §2): a signed-in user opens a session from the inbox and a transcript containing text (rich Markdown), code blocks, and reasoning parts renders correctly **offline from the GRDB cache**, with an explicit staleness banner — never a blank screen, never a crash on any persisted part type. Secondary invariant: message/code/reasoning content never appears in any log at any level (`07-observability.md` §7.3).

## Behavior contract

- Given a chat whose messages are cached in GRDB (seeded by M6-04) and no network, When the user opens `SessionsRoute.chat(sessionId:chatId:)`, Then the full transcript renders from cache before any network call resolves, the amber banner "You're offline — showing saved messages." appears pinned under the nav bar, and `ChatStore.freshness == .offline(since: <lastRefreshedAt>)`.
- Given the same chat with network available, When the screen appears, Then cached rows render first, the M6-04 snapshot refetch runs, GRDB is updated, and the UI updates only via the `ValueObservation` stream (stale-while-revalidate; no spinner when cache exists).
- Given a chat with no cached messages and no network, Then the §4.0 offline-empty surface renders: "You're offline. This screen needs a connection." + button "Retry".
- Given a chat with no cached messages and network available, Then skeleton message rows (`redacted(reason: .placeholder)`) render until the snapshot lands.
- Given an assistant message whose text part contains headings, lists, a GFM table, a blockquote, links, an image, and fenced code, Then it renders per §5.5/§5.7: headings h1–h3 map to `.title3`/`.headline`/`.subheadline` semibold; lists indent 24 pt per level; the table is a bordered grid (0.5 pt `CodeBorder` hairlines, header row `.semibold`, cell padding `OASpacing.sm`) that scrolls horizontally inside its container when wider than the measure (the transcript itself never scrolls horizontally); the blockquote shows a 3 pt `AccentPrimary` leading bar with `.secondary` text; links tint `AccentPrimary`, open in `SFSafariViewController`, and long-press offers "Copy Link"; the image async-loads at max height 280 pt and tapping opens a full-screen viewer with share.
- Given a fenced code block of more than 40 lines, Then it renders collapsed to ~14 lines with footer "Expand · {N} lines"; tapping expands it. Given 40 lines or fewer, it renders fully. Code never wraps — it scrolls horizontally, preserving indentation.
- Given any code block, When the user taps the copy button, Then the raw code lands on the pasteboard and the button swaps to a checkmark (`contentTransition(.symbolEffect(.replace))`, `.snappy(duration: 0.2)`) reverting after 1.5 s. No haptic.
- Given a code fence with an unknown or missing language info string, Then the block renders as plain monospaced text with no highlight and no crash; `ui_render_fallback` logs at notice with `surface=highlight`.
- Given a `reasoning` part, Then it renders as a collapsed disclosure row labeled "Reasoning"; tap toggles expansion (`.snappy(duration: 0.2)`) showing the reasoning text in `.secondary` `Type.message`. Collapsed is the default on every fresh render.
- Given a user message, Then it renders right-aligned in a `BubbleUser` bubble (`OARadius.bubble`, `.continuous`); assistant text renders bubble-less on `systemBackground` capped at the 672 pt measure.
- Given a message containing tool, `data-*`, or unknown part types, Then each renders as a neutral interim placeholder row (part `type` string in `Type.toolRow` + `.secondary`) — never dropped, never a crash. (M6-06 replaces these with real renderers.)
- Given the session row's status is archived, Then a banner "This chat is archived." with button "Unarchive to resume" renders; When the user taps it, Then the button shows a labeled spinner "Unarchiving…", the M3-02 sessions facade unarchive call runs, and on success the banner clears via the session observation. On failure the banner stays and an inline error "Couldn't unarchive. Try again." appears with the button re-enabled; `ui_error_presented` logs with the mapped `error_kind`.
- Given a chat with zero messages (and not archived), Then the empty state renders the three suggestion chips — "Fix a failing test", "Explain this repo", "Start from a GitHub issue" — as opaque `secondarySystemBackground` chips (`OARadius.chip`); tapping invokes the injected `onSuggestionTap(String)` closure (a no-op until M8-01 wires the composer).
- Given the transcript opens, Then it is anchored at the bottom (latest message visible) via `.defaultScrollAnchor(.bottom)`; scrolling up is free — no pill, no follow logic (that is M7-06).
- Given identical message JSON across two GRDB observation emissions, Then no re-parse occurs (parse-once cache keyed by message id + part index + content hash) and row identity is stable (no visible relayout).

## Product and design spec

- Entry point: inbox row tap (M6-02) pushes `SessionsRoute.chat(sessionId:chatId:)`; AppShell's `navigationDestination` (M5-02) constructs `ChatScreen(store:)`. Deep link `openagents://sessions/{sessionId}/chats/{chatId}` lands here too (router shipped in M5-02).
- Chrome (read-only subset of SCR-12): back button; nav title = session title from the cached session row (static text this milestone — the SCR-13 tap-through is M8-04). **No composer, no workspace status row, no toolbar Code button, no share/ellipsis menus** — those are M8-01/M9-01/M8-04/M10-03.
- Layout: transcript is a `ScrollView` + `LazyVStack` of `MessageRow`s, one row per message, `.defaultScrollAnchor(.bottom)`, text column ≤ 672 pt and centered beyond (iPad regular). All surfaces opaque per the §3.5 glass map (no `.glassEffect` anywhere in this slice).
- States (per §4.0 and SCR-12): loading = cached render or skeleton rows; empty = suggestion chips; offline-with-cache = amber `StatusWarning` banner "You're offline — showing saved messages."; offline-no-cache = "You're offline. This screen needs a connection." + "Retry"; archived = banner + "Unarchive to resume"; refresh error with cache = keep transcript, show the standard inline error card for the failed refresh only.
- Copy (exact): banner texts and chip labels as quoted in the Behavior contract; collapse footer "Expand · {N} lines"; unarchive failure "Couldn't unarchive. Try again.".
- Accessibility (§7.2): each message row is one element (`.accessibilityElement(children: .combine)`) labeled "You said, …" / "Assistant said, …" + timestamp; code blocks labeled "{Language} code block, {N} lines" with action "Copy code"; reasoning rows labeled "Reasoning, collapsed"/"Reasoning, expanded" with a toggle action; banners are static text reachable in order; chips are buttons with their full label. Dynamic Type to AX5 — no fixed heights on text-bearing views; the ax3 snapshot variant is required.
- Motion: only the §3.8 entries used here — reasoning/code expand `.snappy(duration: 0.2)`, copy checkmark swap, skeleton→content `.opacity` crossfade. No haptics in this slice (§3.7 lists none for these events).
- Permissions: none. Dark mode: both Highlightr themes are custom and token-tied (§3.6); never a stock highlight.js theme.

Typed error kinds: no new `error_kind` values — unarchive/refresh failures map through the existing §6 taxonomy (`network_offline`, `http_unauthorized`, `http_not_found`, `http_server_error`, `decode_failed`, `server_reported`).

Correlation: `session_id` + `chat_id` on every event above; `request_id` rides the underlying `api_*` events.

Redaction (binding, §7.2/§7.3): message text, markdown source, code content, reasoning text, link URLs, and image URLs are message content — **never interpolated into any log at any level**, including `debug` and the fallback events (which carry only enum-ish `reason` strings and counts such as `blocks`/`lines`). Pasteboard writes are not logged. The checklist's grep proof is attached to the PR.

User-visible status: freshness is always explicit — the offline banner with relative time, skeletons only when no cache exists, archived state with a working action, copy confirmation via the checkmark swap (P5: status = glyph + word + color, never color alone).

Debug recipes:

- Live-tail the chat shell: `xcrun simctl spawn booted log stream --style compact --predicate 'subsystem == "com.openagents.ios" AND category == "ui"' | grep -E 'screen=chat|ui_render_fallback'`.
- Post-hoc offline-path check: `xcrun simctl spawn booted log show --last 30m --style compact --predicate 'subsystem == "com.openagents.ios" AND (category == "ui" OR category == "db")' | grep -E 'ui_screen_appeared|db_sync_applied|ui_error_presented'`.

## Regression risks and concerns

- **Block identity drift breaks M7**: streaming (M7-06) relies on completed blocks never relayouting. If `MessageBlock` ids are unstable (e.g. derived from object identity or random UUIDs), every observation emission rebuilds the transcript. The identity-stability test in file 1 and the parse-cache test in file 5 pin this.
- **Main-thread parsing/highlighting**: swift-markdown and Highlightr are CPU-heavy; both must stay on the sanctioned `@concurrent`/actor paths (`03-architecture.md` §12.3). A regression here shows up as scroll hitches in M7's perf budget — keep `ChatStore` mapping off the hot path and never call `SyntaxHighlighter` synchronously from a view body.
- **Snapshot nondeterminism**: async highlight or live image loading inside a snapshot produces flaky PNGs. The `highlighted:` injection seam and stubbed images are mandatory; CI runs `SNAPSHOT_TESTING_RECORD=never`.
- **Grep-lint conflicts**: the theme CSS files contain hex values, which the M5-01 lint forbids outside DesignSystem. The ci.sh exemption must be scoped to `ios/Packages/CodeUI/Sources/CodeUI/Resources/*.css` only — a broad exemption would gut the token discipline.
- **Content leakage into logs**: markdown/code/reasoning text flowing through render-fallback or error paths is the likeliest §7.3 violation; the fallback events carry enum reasons only, enforced by the grep proof.
- **Interim placeholder scope creep**: `UnsupportedPartView` must stay a dumb label — any tool-row styling added here collides with M6-06's renderers and its snapshots.
- **Highlightr strict-concurrency**: a pre-Swift-6 SDK; if `@preconcurrency import` is needed, confine Highlightr entirely inside the `SyntaxHighlighter` actor (no Highlightr types in public API) so the waiver never spreads.
- **M6-04 API drift**: if the shipped cache/receipt/model names differ from this plan, adapt to what shipped (discovery step) — do not fork a second transcript-read path.

## Deploy or migration impact

None server-side: zero `apps/web` changes, no DB migration, no env vars, no OpenAPI regeneration. iOS-side: two third-party dependency pins (swift-markdown new; Highlightr first-resolve) recorded in `docs/plans/ios-app/03-architecture.md` §2.3 — both land behind the existing `ios-ci.yml` gate; no entitlement, Info.plist, signing, or App Store impact. Committed snapshot PNGs grow the repo by an expected low-tens of images (within the §6.5 budget). Rollback is a plain revert; the GRDB schema is untouched. Doc edits (`03-architecture.md`, `07-observability.md`) ride the same PR so plan and code cannot drift.
