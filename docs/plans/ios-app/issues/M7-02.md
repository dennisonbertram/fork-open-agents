## Why this matters

The reducer is the single point where every byte the server streams becomes the transcript users read. The server's resume contract replays every chunk from index 0 (`05-streaming-chat-engine.md` §2.1), so the only thing standing between a flaky cellular connection and a transcript full of duplicated text is a reducer whose output is a pure, deterministic function of (initial history, chunk sequence). This issue builds that function — `ChatTurnState.apply` — as a value type with no I/O, no clocks, and no main-actor dependency, then locks its behavior to true server bytes with byte-compared golden files for all 14 recorded fixtures. Every later slice (M7-04 runtime, M7-05 resume, M7-06 UI) composes around this reducer without re-testing chunk semantics; every future streaming bug becomes a one-fixture regression here.

## User/operator path protected

U3/U4 core (testing-strategy P3/P4/P5): a user watching an agent turn — live, after a reconnect replay, or after rebuilding from persisted history — sees exactly one copy of every text block, reasoning block, tool row, and data chip, in arrival order, with no lost or duplicated content, no matter how many times the same chunk sequence was applied to a fresh state. Concretely: fixture replay through `ChatTurnState` produces a byte-stable transcript, and the rebuild path (fresh state seeded with history, full replay applied) produces the identical bytes.

## Behavior contract

- Given the decoded chunks of `01-plain-text-turn.sse.txt` and an empty initial history, When each chunk is applied in arrival order, Then `CanonicalJSON.encode(state.messages)` byte-equals the committed `01-plain-text-turn.expected.json`, `sawStart == true`, `sawFinish == true`, and `lastErrorText == nil`.
- Given `messages` ending with an assistant message with id `m-1` (continuation rule, §4.1), When `start` with `messageId == "m-1"` applies, Then no new message is appended and subsequent parts append to that same message; Given the last message is `user`-role, When `start` with `messageId == "m-2"` applies, Then a new assistant message with id `m-2` is appended; When `start` carries no `messageId`, Then the new assistant message gets the deterministic placeholder id `pending-assistant` (goldens must be stable — no random ids in the reducer, ever).
- Given a text block registered under id `text-1` and a tool part registered under `call_1` during step 1, When `finish-step` applies, Then `activeTextPartIndex` and `activeReasoningPartIndex` are cleared but `toolPartIndex` retains `call_1`, and a later `tool-output-available` for `call_1` (fixture 03's next-step output) updates the existing part in place — never appends a second part.
- Given a `data-commit` part with id `aBcD1234eFgH5678:commit` appended at parts index k with `{"status":"pending"}`, When a second `data-commit` chunk with the same id applies (rule D, §4.2), Then `parts.count` is unchanged, the part at index k carries the resolved payload, and its array position is still k.
- Given fixture `12-workspace-status-transient.sse.txt`, When all chunks apply, Then the final messages contain zero parts of type `data-workspace-status` and `apply` returned a non-nil `TransientDataPart` once per transient chunk (count asserted > 0 and equal to the fixture's transient-chunk count).
- Given a `text-delta` for an unregistered id `text-9` (lenient rule, §4.2 — the AI SDK throws here; we must not), When applied, Then a new text part is synthesized with the delta as its content and registered under `text-9`; no error, no crash, no dropped delta.
- Given fixture `08-error-mid-stream.sse.txt`, When the in-band `error` chunk applies, Then `lastErrorText` equals its `errorText`, no message part contains that text, and remaining chunks still apply normally.
- Given a chunk decoded as `.unknown(type: "future-thing")` (fixture 14), When applied, Then `messages` is unmutated and `unknownChunkCount` increments; Given a `data-new-feature` chunk (unknown name but valid `data-*` family), Then it is appended/replaced as a data part per rule D — unknown data parts are kept, never dropped (round-trip safety, §1.6).
- Given a tool part in `input-available`, When `tool-approval-request` applies, Then state is `approval-requested` with `approval.id == approvalId`; When `applyApprovalResponse(approvalId:approved:reason:)` is called, Then state is `approval-responded`; When `tool-output-denied` applies, Then state is `output-denied` (terminal). No approval UI is built — states only (§1.5).
- Given fixture `06-task-subagent-preliminary.sse.txt`, When repeated `tool-output-available` chunks with `preliminary: true` apply, Then each replaces the previous output on the same part (exactly one part per `toolCallId`), and the final non-preliminary output clears `preliminary`.
- Given `message-metadata` `{"a":{"x":1},"b":1}` followed by `{"a":{"y":2}}`, When both apply, Then `metadata` deep-merges to `{"a":{"x":1,"y":2},"b":1}` (objects merge recursively; scalars/arrays replace).
- Given fixture `04-multi-step-long-turn.sse.txt`, When applied (a) to a fresh state, (b) to a second independent fresh state, and (c) via the rebuild path — fresh state seeded with computation (a)'s final messages minus the in-flight assistant message, full chunk list applied — Then all three canonical JSON outputs are byte-equal (the §2.1 resume invariant at reducer level).
- Given every committed `.expected.json`, When decoded through the message model and re-encoded with `CanonicalJSON`, Then output byte-equals the file (history echo-back fidelity for §5.1, including unknown parts).
- Given `OPEN_AGENTS_RECORD_GOLDENS=1` in the environment (error/record mode), When the golden suite runs, Then each test rewrites its `.expected.json` in the source `Fixtures/` directory and fails with a "golden recorded — review the diff and re-run without record mode" message, so a recording run can never pass CI (CI never sets the variable).

## Product and design spec

No user-facing screen ships in this slice; the deliverable is library behavior inside `ios/Packages/StreamEngine` that later UI consumes. The "design" being specified is the transcript data contract: parts append in arrival order and the parts array is the render order (never sorted, §4.3); part identities are stable (text/reasoning block id, `toolCallId`, `(data name, id)`) so M7-06's `ForEach` never recreates rows mid-stream; `data-workspace-status` reaches the UI only through the transient callback value (it drives a status banner and is never part of the transcript); the in-band `error` chunk becomes banner state (`lastErrorText`), never message content. States, loading, accessibility, copy, and permissions: none here — owned by M7-06 and `01-product-and-ux.md`. Inventing any UI in this slice is a defect.

New source files (one concern per file, per repo file-organization rules):

```swift
// ios/Packages/StreamEngine/Sources/StreamEngine/ChatTurnState.swift
public struct TransientDataPart: Equatable, Sendable {
  public let name: String   // chunk type minus the "data-" prefix, e.g. "workspace-status"
  public let id: String?
  public let data: JSONValue
}

struct DataPartKey: Hashable, Sendable { let name: String; let id: String }

public struct ChatTurnState: Sendable {
  public private(set) var messages: [UIMessage]
  var activeTextPartIndex: [String: Int]       // text block id → part index in messages.last
  var activeReasoningPartIndex: [String: Int]
  var toolPartIndex: [String: Int]             // toolCallId → part index; survives finish-step
  var partialToolInput: [String: String]       // toolCallId → accumulated raw input JSON text
  var dataPartIndex: [DataPartKey: Int]        // (name, id) → part index, replace-by-id
  public private(set) var sawStart: Bool
  public private(set) var sawFinish: Bool
  public private(set) var lastErrorText: String?
  public private(set) var unknownChunkCount: Int

  public init(messages: [UIMessage] = [])
  @discardableResult
  public mutating func apply(_ chunk: UIMessageChunk) -> TransientDataPart?  // the only entry point
  public mutating func applyApprovalResponse(approvalId: String, approved: Bool, reason: String?)
}
```

- `ChatTurnState.swift` — state, `apply` dispatcher, continuation rule, `start`/`start-step`/`finish-step`/`finish`/`error`/`abort`/`.unknown` handling.
- `ChatTurnState+TextReasoning.swift` — `text-*`/`reasoning-*` handlers including the lenient unregistered-delta rule and the `finish` sweep marking `streaming` parts `done`.
- `ChatTurnState+ToolParts.swift` — the §1.5 state machine: `tool-input-start/delta/available/error`, `tool-approval-request`, `tool-output-available` (preliminary and final), `tool-output-error`, `tool-output-denied`, `dynamic: true` → `dynamic-tool` part type, raw-input accumulation in `partialToolInput` (never JSON-parse per delta), upsert-if-missing on `tool-input-available`.
- `ChatTurnState+DataParts.swift` — `data-*` handling: `transient == true` → return `TransientDataPart`, no part mutation; otherwise rule D replace-by-id via `dataPartIndex`; `source-url`/`source-document`/`file` part appends.
- `JSONValue+DeepMerge.swift` — `JSONValue.deepMerging(_:)` used by `start`/`message-metadata`/`finish` metadata merges (objects recurse, everything else replaces).

The chunk → mutation behavior is `05-streaming-chat-engine.md` §4.2's table, implemented row-for-row, with §4.3's six ordering rules. This server always sends `finishReason: "stop"` — never branch on it.

Deliberate refinements of the 05 §4.1 sketch (record them back into `docs/plans/ios-app/05-streaming-chat-engine.md` §4.1 in this PR): `apply` returns `TransientDataPart?` (the sketch's "transient-data callback" — a return value keeps the reducer pure and the fixture-12 count trivially assertable), plus `unknownChunkCount` (the §4.2 "skip metric" as state, logged later by M7-04's engine) and `applyApprovalResponse` (the §1.5 "local approval response" row; wired by M7-04).

New test files (all Swift Testing, `ios/Packages/StreamEngine/Tests/StreamEngineTests/`): see "Tests to add first". New committed fixtures: one `NN-<scenario>.expected.json` per `.sse.txt` (14 files, generated via record mode then hand-reviewed — they are assertions, not snapshots) and any `.history.json` the catalog still lacks (fixture 05's answered-continuation history at minimum, if M7-01 did not commit it). `CanonicalJSON` = `JSONEncoder` with `outputFormatting = [.sortedKeys]` (compact, deterministic, diffable). Record mode resolves the source `Fixtures/` directory via `#filePath` from the test-support file (`Bundle.module` is a copy and must never be written).

Engine actor, flush timer, persistence, networking, and observability event emission are explicitly not integrated here (M7-03/M7-04).

## Observability and user feedback

- Named module: `StreamEngine` (`ios/Packages/StreamEngine`). The reducer itself is intentionally silent — `ChatTurnState.apply` performs no logging, no `Date()`, no I/O (purity is what makes goldens byte-stable). Enforcement: the checklist grep over `ChatTurnState*.swift` returns nothing; any logging found in review is a defect.
- Structured-event handoff instead: the reducer exposes the data that M7-03/M7-04 log under the `stream` category of `docs/plans/ios-app/07-observability.md` §4.3 — `unknownChunkCount` feeds the skipped-chunk count on `stream_finished` (notice: `events_total`, `chat_id`, `request_id`, `workflow_run_id`) and per-chunk `stream_event` (debug: `part_type`, `bytes`); `lastErrorText` feeds `stream_error_part` (error, `error_kind=stream_server_error_part`, `error_text` redacted and truncated to 200 chars). This slice must not emit those events itself and must not invent new event names or `error_kind` values.
- Correlation IDs: none live inside the pure reducer. `request_id`/`chat_id`/`workflow_run_id` attach at the connection (M7-03) and engine (M7-04) layers; golden-test failure messages carry the fixture name (`"Golden mismatch for 04-multi-step-long-turn"`) as the test-time correlation key.
- Redaction rules: fixtures are the only content the reducer's tests touch and they are sanitized at capture time (M7-01, `06-testing-strategy.md` §5.5 checklist — no tokens, no real ids, synthetic prompts). Record mode writes only into the repo's `Fixtures/` directory, never user data, never `Bundle.module`. Message/prompt content never reaches OSLog from this code because this code never logs (07-observability §7.3 holds trivially).
- Debug recipes:
  - Reproduce a reported transcript-duplication bug deterministically: `swift test --package-path ios/Packages/StreamEngine --filter "ReplayIdempotenceTests"`.
  - Inspect a golden mismatch: `OPEN_AGENTS_RECORD_GOLDENS=1 swift test --package-path ios/Packages/StreamEngine --filter "ReducerGoldenTests"` then `git diff -- ios/Packages/StreamEngine/Tests/StreamEngineTests/Fixtures/` — the diff is the exact behavior change; never commit it without review.
  - Audit part-type distribution of a golden: `jq '.[].parts[].type' ios/Packages/StreamEngine/Tests/StreamEngineTests/Fixtures/04-multi-step-long-turn.expected.json | sort | uniq -c`.
  - Confirm transient data never persisted: `grep -c "data-workspace-status" ios/Packages/StreamEngine/Tests/StreamEngineTests/Fixtures/*.expected.json` prints `0` for every file.
- Evidence for the PR: red and green `swift test` transcripts, the golden-review notes (one line per fixture stating what was checked), and the purity-grep output.

## Regression risks and concerns

- Goldens encode bugs as truth: a wrong implementation recorded into `.expected.json` becomes a permanent assertion. Mitigation: the mandatory per-fixture hand-review checklist (todo list) before the fixture commit, reviewed again in the PR.
- Determinism leaks: any `UUID()`, `Date()`, unordered-dictionary iteration, or locale-dependent encoding inside `apply` or `CanonicalJSON` makes goldens flaky. Mitigation: the purity grep, `.sortedKeys`, the deterministic `pending-assistant` placeholder, and the two-independent-states test which fails on first nondeterminism.
- Registry-lifecycle mistakes are silent duplicators: clearing `toolPartIndex` at `finish-step` (or not clearing text registries) reproduces the web's resume "jank" later, in M7-05, far from the cause. Mitigation: explicit unit cases for both directions plus fixture 03's cross-step output.
- Model-name drift against M6-04: if this issue hardcodes `UIMessage` while M6-04 shipped `AgentUIMessage`, nothing compiles — acceptable; the danger is a local shadow type that diverges from the persisted model and breaks round-trip. Mitigation: the prerequisite check pins the real names; the reducer must import the M6-04 model, never declare its own message type.
- Record-mode misuse: a CI or agent run with `OPEN_AGENTS_RECORD_GOLDENS=1` silently rewriting goldens. Mitigation: record mode fails every test it records, and CI never sets the variable (same posture as snapshot `record: .never`).
- Mutation-table omissions surface as unknown-chunk skips: forgetting a row (e.g. `tool-input-error`) may pass most goldens while corrupting one. Mitigation: the catalog spans all 26 shapes across fixtures 01–14; fixture 14 plus `unknownChunkCount` assertions distinguish "handled" from "skipped".
- Scope creep into M7-04: adding flush timing, actors, or persistence here would make goldens timing-dependent. Mitigation: `ChatTurnState` stays a value type; any `actor` keyword in this PR's source diff is a review rejection.
