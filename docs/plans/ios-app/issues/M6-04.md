## Why this matters

Every later chat milestone stands on this slice. M6-05/M6-06 render transcripts from GRDB before the network answers (offline-readable, instant cold start); M7-02's reducer and M7-04's send flow consume the same `UIMessage`/`UIMessagePart` models and the same `chatMessage` cache; and `POST /api/chat` requires the **full message history echoed back verbatim** on every turn (`docs/plans/ios-app/05-streaming-chat-engine.md` section 5.1). If our models drop, rename, or retype a single field — including part types this app has never seen — the echo-back silently corrupts server history, because the server has no Zod validation on that body. This issue builds the hand-rolled history layer with structural fidelity guarantees: decode anything, persist exactly what arrived, re-encode byte-equal (under canonicalization), and never throw on unknown shapes. It also lands the two small client-state behaviors the chat shell needs on day one: read receipts (so unread badges clear like the web) and per-chat composer drafts.

Naming normalization (binding for this issue and its consumers; record disagreements here, do not re-decide):
- Package: the chat data layer lives in `ios/Packages/StreamEngine` (`docs/plans/ios-app/03-architecture.md` owns the package graph; `05-streaming-chat-engine.md` calls it "ChatEngine" — superseded).
- Types: `UIMessage` / `UIMessagePart` per `05-streaming-chat-engine.md` section 1.6 (`03-architecture.md` section 3.1 calls them `AgentUIMessage`/`AgentMessagePart` — superseded; M7 issues consume the `UIMessage` names).
- GRDB: table `chatMessage`, columns `messageJson`/`syncState` (camelCase per `03-architecture.md` section 9.3; `05-streaming-chat-engine.md` section 6.2 spells them `chat_message`/`sync_state`). The `syncState` **column values** stay snake_case strings: `synced`, `pending_send`, `failed_send`, `partial_stream`. Do not confuse the per-message `syncState` column with M6-01's `syncState` freshness-ledger **table** — they are different things.

## User/operator path protected

History echo-back fidelity: what we persist is exactly what we can POST back in `messages`. Concretely, for any chat the server returns from `GET /api/sessions/{sessionId}/chats/{chatId}`, decoding to `[UIMessage]`, persisting to GRDB, reading back, and re-encoding produces canonically byte-equal JSON — including part types, part fields, and metadata keys this build has never seen. Catalog path: P9 (`docs/plans/ios-app/06-testing-strategy.md` section 2) — offline or degraded network shows cached transcripts, never a blank crash — plus the upstream half of P5 (every persisted part type decodes and survives) that M6-05/M6-06 render and M7-04 echoes back on send.

## Behavior contract

- Given `StubURLProtocol` serves `ios/Fixtures/json/chat-snapshot-tools.json` for `GET /api/sessions/ses_fixture/chats/chat_fixture`, when `ChatHistoryClient.fetchSnapshot(sessionId:chatId:)` is awaited, then it returns a `ChatRefreshResponse` whose `isStreaming` matches the fixture, whose `chat.id`/`chat.modelId` match, and whose `messages` decode every part in the fixture (text, reasoning, step-start, `tool-bash`, `tool-read`) with none dropped.
- Given any of the four committed history fixtures, when the `messages` array is decoded to `[UIMessage]` and re-encoded through `CanonicalJSON`, then the output equals the canonical encoding of the same raw JSON decoded as `JSONValue` — the echo-back fidelity invariant.
- Given a message containing `{"type":"future-part","blob":{"x":1}}` and a `data-new-feature` part, when it is decoded, then both become `.unknown`/`.data` parts retaining their complete raw payloads, decoding does not throw, and re-encoding reproduces them at the same array positions.
- Given a `text` part carrying an unrecognized sibling key (e.g. `"annotations":[...]`), when it is decoded and re-encoded, then the unrecognized key survives (the `extra` remainder rule below).
- Given a recognized part whose typed decode fails (e.g. a `tool-bash` part missing `toolCallId`), when the message is decoded, then that part falls back to `.unknown` with the raw object retained — history decode never throws.
- Given GRDB holds rows `[u1: synced, u2: pending_send, u3: failed_send]` for a chat and the server snapshot returns messages `[u1, a1]`, when `TranscriptCache.applySnapshot(chatId:messages:)` runs, then the resulting rows are `u1(pos 0, synced), a1(pos 1, synced), u2(pos 2, pending_send), u3(pos 3, failed_send)` — server truth replaces synced rows, the outbox survives, and positions are renumbered with outbox rows after server rows in their previous relative order.
- Given a `pending_send` row whose id IS in the server snapshot, when `applySnapshot` runs, then the local row is replaced by the server copy as `synced` (the send was accepted while we were away).
- Given `partial_stream` rows exist for a chat, when `applySnapshot` runs, then they are deleted (always replaced by refetch, `05-streaming-chat-engine.md` section 6.3).
- Given the chat screen opens, when `ReadReceiptReporter.chatOpened(sessionId:chatId:)` runs, then `POST /api/sessions/{sessionId}/chats/{chatId}/read` fires unconditionally and the local `chat.hasUnread` flag flips to false in GRDB.
- Given the app foregrounds twice within 3 seconds for the same chat, when `appForegrounded(sessionId:chatId:)` runs both times, then the receipt POSTs at most once (3 s throttle, per-chat); a different chatId is throttled independently. Mirrors the web (`docs/plans/ios-app/research/11-web-client-consumption-patterns.md`: route entry forced, focus throttled 3 s).
- Given the receipt POST fails (offline, 404), when the reporter runs, then no error surfaces to the caller — receipts are best-effort; the failure is logged at notice and retried only by the next trigger.
- Given a draft "fix the login bug" saved for chat C, when `DraftStore.load(chatId: C)` runs after relaunch, then it returns the text; `save(chatId:text:"")` deletes the row; `clear(chatId:)` deletes the row (called on successful send by M8-01).
- Given the device is offline, when `fetchSnapshot` throws the M3-01 offline `APIError`, then cached rows from `TranscriptCache.observeMessages(chatId:)` keep rendering — the cache is never wiped by a failed fetch.

## Product and design spec

No end-user pixels ship in this slice; it is the data layer under SCR-12 (chat). The user-visible consequences it enables:

- Entry point (for consumers): M6-05's `ChatScreen` calls `observeMessages` for instant cached render, then `fetchSnapshot` + `applySnapshot` to reconcile; M8-01's composer calls `DraftStore`; M6-05 wires `ReadReceiptReporter` to `.task` (open) and `scenePhase == .active` (foreground), firing only while the scene is active.
- States: cached-then-fresh (no spinner when rows exist), offline (cached rows + staleness handled by M6-05's banner), empty (no rows, no outbox), and outbox rows carrying `pending_send`/`failed_send` for M7-04's failed-send badges.
- Unread: opening a chat clears its unread dot locally at once (GRDB update) and server-side via the receipt POST; the sessions poll (M6-02) reconciles aggregates.
- Accessibility/copy/permissions: not applicable here (owned by M6-05/M6-06).

`TranscriptCache` API (consumed by M6-05 for reads and M7-04 for streaming-time write points; this issue owns the semantics and tests):

- `applySnapshot(chatId: String, messages: [UIMessage]) async throws` — one transaction implementing the `05-streaming-chat-engine.md` section 6.3 snapshot-replace row: (a) read surviving outbox rows (`syncState` IN (`pending_send`,`failed_send`)) whose ids are NOT in the server set, ordered by `position`, into memory; (b) delete ALL rows for the chat (this removes `synced`, `partial_stream`, and superseded outbox rows, and sidesteps the `UNIQUE(chatId, position)` collision); (c) insert server messages as `synced` with `position` 0..n-1 and `messageJson` = `CanonicalJSON`-stable encode of the decoded `UIMessage`; (d) re-insert survivors with positions n, n+1, … in their previous relative order. Emits `db_sync_applied`.
- `observeMessages(chatId: String) -> AsyncSequence<[CachedChatMessage]>` — `ValueObservation` ordered by `position`, `.removeDuplicates()`. `CachedChatMessage` = `{ message: UIMessage, syncState: MessageSyncState, position: Int }`; `MessageSyncState` is the lenient RawRepresentable struct over the four snake_case values.
- `upsert(chatId: String, message: UIMessage, syncState: MessageSyncState) async throws` — insert at `max(position)+1` when new, else update `messageJson` + `syncState` in place (position unchanged).
- `updateSyncState(chatId: String, messageId: String, to: MessageSyncState) async throws`
- `delete(chatId: String, messageIds: [String]) async throws`
- `pendingOutbox(chatId: String) async throws -> [CachedChatMessage]`

`ChatCache` gains `markReadLocally(chatId: String) async throws` — one transaction: set `chat.hasUnread = false` for the row, then recompute the owning `session.hasUnread` as the OR of its remaining chats' flags.

Part-model fidelity sketch (the load-bearing pattern; copy the shape, not necessarily the exact code):

```swift
public enum UIMessagePart: Codable, Equatable, Sendable {
  case text(TextPart)                  // "text": text, state?, providerMetadata?
  case reasoning(ReasoningPart)        // "reasoning": same fields, rendered collapsed
  case stepStart(StepStartPart)        // "step-start": extra-only
  case file(FilePart)                  // "file": mediaType, filename?, url
  case sourceUrl(SourceUrlPart)        // "source-url": sourceId, url, title?
  case sourceDocument(SourceDocumentPart) // "source-document": sourceId, mediaType, title, filename?
  case tool(ToolPart)                  // "tool-<NAME>": toolCallId, state, input?, rawInput?,
                                       //   output?, errorText?, preliminary?, providerExecuted?,
                                       //   callProviderMetadata?, approval?, title?
  case dynamicTool(DynamicToolPart)    // "dynamic-tool": ToolPart fields + toolName
  case data(DataPart)                  // "data-<name>": id?, data: JSONValue
  case unknown(UnknownPart)            // raw type + complete raw object (JSONValue)

  public init(from decoder: Decoder) throws {
    // 1. Decode the WHOLE object into [String: JSONValue] first.
    // 2. Read "type"; dispatch per the discriminator order above.
    // 3. Lift typed fields out of the dictionary; store the remainder in `extra`.
    // 4. Any failure in steps 2-3 for a recognized type => .unknown(raw object). Never throw.
  }
  public func encode(to encoder: Encoder) throws {
    // Re-emit "type" from the case (tool: "tool-\(toolName)", data: "data-\(name)",
    // unknown: its stored raw type), write typed fields, then merge `extra`
    // (typed fields win on key collision). Dynamic fields (input, output, rawInput,
    // data, providerMetadata, approval, metadata) are stored and re-emitted as
    // JSONValue — never re-typed, never dropped.
  }
}
```

`ToolPart.state` is a lenient RawRepresentable struct with statics for `input-streaming`, `input-available`, `output-available`, `output-error`, `output-denied`, `approval-requested`, `approval-responded`; unknown state strings decode fine. `data-workspace-status` never appears in persisted history (`05-streaming-chat-engine.md` section 1.6) but decodes generically as `DataPart(name: "workspace-status")` if it ever does.

Boundaries honored: no SSE, no chunks, no reducer, no send flow (M7-01/02/04); no `POST .../messages` persistAssistantMessage (M7/M8-03); no UI (M6-05/M6-06); no schema tables beyond the one-column `v1` amendment (M6-01 owns the migrator); read-receipt transport is the M3-02 generated facade, not a new endpoint.

## Regression risks and concerns

- Fidelity is the whole game: a typed decode that drops unknown sibling keys or re-types `input`/`output`/`data` corrupts the echo-back that M7-04 will POST. The extra-remainder + unknown-fallback rules and the canonical round-trip tests are the structural defense; reviewers must reject any `struct`-only decode of dynamic payloads.
- `JSONValue` number representation (`Double`) could differ from raw bytes (`1` vs `1.0`); the tests canonicalize both sides through `JSONValue`, and the future POST body goes through the same encoder, so the comparison and the wire stay self-consistent. Do not "fix" a mismatch by comparing against raw fixture bytes directly.
- `UNIQUE(chatId, position)` makes naive renumbering collide mid-transaction; the delete-all-then-reinsert order in `applySnapshot` is mandatory. A failed transaction must leave prior rows intact (GRDB transactions guarantee this — never write outside `writer.write`).
- Amending migration `v1` after M6-01 shipped to dev devices relies on DEBUG `eraseDatabaseOnSchemaChange`; if a TestFlight build exists before this lands (it should not, per the milestone order), switch to a `v2` migration instead and say so in the PR.
- Read-receipt over-firing (no throttle, or firing while backgrounded) would spam the server and skew unread semantics; under-firing leaves stale badges. The per-chat clock-injected tests pin the policy; M6-05 must only call the reporter while the scene is active.
- `ChatHistoryClient` accidentally routed through the streaming `URLSession` would hold 600 s idle timeouts on a class-F call; the test asserting normal-session usage is impractical, so the PR review checks the session choice explicitly (named here so reviewers look).
- M6-01/M6-04 overlap (TranscriptCache/DraftStore stubs): if M6-01 already implemented parts of these stores, extend rather than duplicate — the discovery checklist item exists for exactly this; divergent duplicate stores would be a defect.
