## Why this matters

The iOS app generates its Swift API client from `apps/web/openapi.json`. Today that spec covers 6 paths / 10 operations — none of them sessions or chats, which are the very first surfaces the app renders (sessions inbox, chat tabs, transcripts, share sheet). Until the 9 sessions/chats paths below are in the spec, the iOS milestone M3-02 ("Domain models + facades: sessions, chats, ...") has nothing to generate against and would have to hand-roll types that silently drift from the server. Documenting these paths from the same Zod schemas the routes validate with makes drift mechanically impossible (the `openapi:check` gate and `apps/web/lib/api/openapi-spec.test.ts` both rebuild the document and compare), and the black-box contract tests pin the live HTTP behavior the spec claims.

## User/operator path protected

- Spec-documented sessions/chats operations match the live route shapes byte-for-byte: an iOS client generated from `apps/web/openapi.json` can list sessions, create a session, manage chats, persist/delete messages, fork, mark read, and manage share links without a single decode failure.
- Existing web clients are untouched: every sessions/chats route keeps its exact status codes and error strings after the manual-validation-to-Zod swap (the colocated `route.test.ts` suites are the guard).
- Both committed artifacts (`apps/web/openapi.json`, `apps/web/lib/api/openapi-types.ts`) regenerate in the same PR, keeping `openapi:check`, the spec unit test, and `bun --bun run ci` green.

## Behavior contract

Happy path:

- Given the builder in `apps/web/lib/api/openapi-spec.ts` after this change, when `buildOpenApiDocument()` runs, then the document contains the 9 Batch B paths with exactly these 17 operationIds: `listSessions`, `createSession`, `getSession`, `updateSession`, `deleteSession`, `listChats`, `createChat`, `getChat`, `updateChat`, `deleteChat`, `persistAssistantMessage`, `deleteMessageCascade`, `forkChat`, `markChatRead`, `getChatShare`, `createChatShare`, `deleteChatShare` — each with a documented 401 and `{ error: string }` (`ErrorResponse` `$ref`) on every non-2xx.
- Given a running server with test auth, when the contract suite POSTs `/api/sessions` with `{}` (no repo), then it gets 200 `{ session, chat }`, the session appears in `GET /api/sessions`, and the full chats CRUD/messages/fork/read/share lifecycle round-trips with the documented shapes.
- Given `POST /api/sessions/{sessionId}/chats` with a client-supplied `{ "id": "<uuid>" }`, when the same body is POSTed twice, then both responses are 200 with the same `chat.id` (idempotent create), and a third POST reusing that id under a different session returns 409 `{ "error": "Chat ID conflict" }`.

Error paths:

- Given `PATCH /api/sessions/{sessionId}` with `{ "runtimeMode": "bogus" }`, when the route validates with the extracted Zod schema, then the response is still 400 `{ "error": "Invalid runtime mode" }` — the legacy message, byte-identical.
- Given `POST /api/sessions` with `{ "repoOwner": "bad owner!" }`, then 400 `{ "error": "Invalid repository owner" }`; with `{ "sandboxType": "modal" }`, then 400 `{ "error": "Invalid sandbox type" }`.
- Given `DELETE /api/sessions/{sessionId}/chats/{chatId}` on the only chat in a session, then 400 `{ "error": "Cannot delete the only chat in a session" }`.
- Given any of the 17 operations without a session cookie/bearer, then 401 `{ "error": "Not authenticated" }`; on another user's session, then 403; on an unknown id, then 404 (semantics come from `apps/web/app/api/sessions/_lib/session-context.ts` and must not change).

Edge cases:

- Given `POST /api/sessions/{sessionId}/chats` with a malformed (non-JSON) body, then the route still creates a chat with a server-generated id (today's behavior: the body is optional; parse failure means "no requested id"). The spec documents the request body as `required: false`. Do not "fix" this to a 400.
- Given `GET /api/sessions?status=archived`, then the response additionally carries `archivedCount` and `pagination: { limit, offset, hasMore, nextOffset }` — `SessionListResponse` declares `archivedCount` and `pagination` as optional fields so one schema covers all three `status` variants.
- Given `POST .../messages` re-sent with the same assistant message id, then 200 `{ "success": true, "status": "updated" }` (idempotent upsert); the `status` enum (`"inserted" | "updated"`) is in the spec.
- Given `DELETE .../messages/{messageId}` targeting an assistant message, then 400 `{ "error": "Only user messages can be deleted" }`; while a run is streaming, then 409.
- `createSession` returns 200, not 201 — document 200; changing the live status code is out of scope.

## Product and design spec

No user-facing UI changes. The "product" of this slice is operator/developer-facing:

- Entry points: `apps/web/openapi.json` (consumed by the iOS codegen in `ios/Packages/OpenAgentsAPI`, milestone M2-02) and `apps/web/lib/api/openapi-types.ts` (consumed by the existing typed web client `apps/web/lib/api/client.ts`).
- Primary flow: a contributor edits `apps/web/lib/api/openapi-spec.ts`, regenerates both artifacts, and the drift gates prove spec == code.
- Error/empty/loading behavior: route validation errors keep their exact current copy (the strings listed in the behavior contract); no new states are introduced.
- Permissions: every operation requires an authenticated session; ownership gating (401/403/404) is already enforced by `requireAuthenticatedUser`/`requireOwnedSession`/`requireOwnedSessionChat` in `apps/web/app/api/sessions/_lib/session-context.ts` and is only documented, never modified.
- Accessibility and copy: not applicable (no UI).

## Observability and user feedback

This slice changes a published contract and request validation on production auth-gated routes; it adds no new runtime services, so the named observability surface is the gate evidence plus the preserved error envelope:

- Module responsible: `apps/web/lib/api/openapi-spec.ts` (contract) and the six sessions/chats route handlers (validation). No new structured event emitters are added; the routes' existing `console.error("Failed to create session:", error)`-style logs are preserved verbatim.
- Error envelope: every documented non-2xx is `ErrorResponse` `{ error: string }`. These routes carry no `errorKind` field today; do not introduce one in this slice (the iOS error taxonomy maps these as `server_reported` per `docs/plans/ios-app/07-observability.md` section 6). The validation swap must keep each typed error string byte-identical so client-side string matching (web and iOS `ConflictKind` matching on `"Chat ID conflict"`, `"Cannot delete the only chat in a session"`) keeps working.
- Correlation IDs: `sessionId`, `chatId`, `messageId` travel in the URL path and appear in server request logs; contract-test failures print the request path and status via `bun:test` assertions. No `requestId` echo exists on these routes and none is added here.
- Redaction rules: `apps/web/openapi.json` is a committed, publicly-served artifact — schema descriptions and examples must never contain real user ids, session ids, tokens, or message content. The contract test must not log response message bodies on success (assert shapes, not dump payloads); the fixture session is created by the shared test-auth user and deleted in `afterAll`.
- User-visible status: none changes. Operator evidence for the PR: the `openapi:check` success line, the spec-test pass, and the contract-suite pass output.
- Debug recipes:
  - Spec drift: `bun run --cwd apps/web openapi:check` (non-zero exit + diff hint when `openapi-spec.ts` changed without regeneration).
  - Coverage check: `bun -e 'const d=JSON.parse(await Bun.file("apps/web/openapi.json").text()); console.log(Object.keys(d.paths).filter(p=>p.startsWith("/api/sessions")))'` — must list all 9 Batch B paths.
  - Hygiene check: `grep -c '"additionalProperties": false' apps/web/openapi.json` → `0`.
  - Live-shape check during an incident: `CONTRACT_BASE_URL=http://localhost:3000 bun test apps/web/tests/contract/sessions-chats-crud.test.ts`.

## Regression risks and concerns

- Validation-message drift: swapping manual checks for Zod can change 400 bodies. Mitigation: exact legacy messages attached to each schema check, first-issue mapping, and the unmodified existing `route.test.ts` suites as the gate. Each existing test sends exactly one invalid field, so issue ordering cannot change which message surfaces.
- Silent behavior "fixes": `createChat` tolerating malformed JSON, `createSession` returning 200 (not 201), and the idempotent share/message upserts are load-bearing; the contract suite pins all three.
- Spec/route divergence: response schemas are hand-declared in `openapi-spec.ts`, not derived from route return types — a typo (e.g. marking `prNumber` non-nullable) ships a wrong contract that compiles fine on the server. Mitigation: mirror the cited row types in `apps/web/lib/db/schema.ts` / `apps/web/lib/db/sessions.ts`, and the contract tests assert presence/nullability of the summary fields.
- Registry name collisions: `Session` or `Chat` may collide with names another in-flight batch registers; the M1-01 registry throws on conflicting definitions — coordinate via rebase and regenerate.
- Merge conflicts on `openapi.json`: every M1 batch rewrites the artifact wholesale. Never hand-merge; rebase, then rerun `openapi:generate` + `openapi:types`.
- `UIMessage` looseness is deliberate — do not let a well-meaning reviewer tighten it; tightening breaks ChatKit's ownership of the part system and would make Swift codegen model 26 chunk shapes it must not own.
