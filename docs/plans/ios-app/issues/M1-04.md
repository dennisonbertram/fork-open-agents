## Why this matters

The iOS "ship code" surface — Files browser, file viewer, Diff tab, Commit sheet, PR sheet, and Merge dialog — is generated Swift code built from `apps/web/openapi.json`. Today the committed spec covers only 6 paths / 10 operations and none of the files, diff, or PR-readiness routes. Until this batch lands, the iOS client for those screens cannot be generated at all, and any hand-guessing of shapes would silently break the moment the server changes. This issue adds the 12 Batch D operations from `docs/plans/ios-app/02-api-contract-and-networking.md` section 2.3 to the spec, registers their response shapes under the stable `components.schemas` names from section 2.2, and pins them with drift gates and contract tests so the iOS codegen surface can never silently diverge from the live routes.

## User/operator path protected

The diff/PR-readiness contracts behind the iOS ship-code screens are spec-covered and drift-gated: an iOS user opens a session's Diff tab, reviews `DiffFile` entries, discards a file, asks for an AI commit message and PR draft, watches merge readiness (checks summary + `CheckRun` rows), and taps "Fix failing checks" — every one of those payload shapes is now documented in `apps/web/openapi.json`, verified by `apps/web/scripts/check-openapi.ts`, the spec unit test, and black-box contract tests. Existing web behavior on these routes is unchanged.

## Behavior contract

- Given `buildOpenApiDocument()` after this change, when the document is built, then `paths` contains exactly these 12 new operations (operationIds in parentheses): `GET /api/sessions/{sessionId}/files` (`listSessionFiles`), `GET /api/sessions/{sessionId}/files/content` (`getSessionFileContent`), `GET /api/sessions/{sessionId}/diff` (`getSessionDiff`), `GET /api/sessions/{sessionId}/diff/cached` (`getCachedSessionDiff`), `POST /api/sessions/{sessionId}/git/discard` (`discardChanges`), `POST /api/sessions/{sessionId}/git/pr/generate` (`generatePrContent`), `POST /api/sessions/{sessionId}/git/pr/close` (`closePullRequest`), `GET /api/sessions/{sessionId}/git/pr/readiness` (`getMergeReadiness`), `GET /api/sessions/{sessionId}/git/deployment-url` (`getDeploymentUrl`), `POST /api/sessions/{sessionId}/generate-commit-message` (`generateCommitMessage`), `POST /api/sessions/{sessionId}/checks/fix` (`fixFailingChecks`), `POST /api/generate-pr` (`generatePr`).
- Given the committed `apps/web/openapi.json` after regeneration, when inspected, then `components.schemas` contains `FilesResponse`, `FileEntry`, `FileContentResponse`, `DiffResponse`, `DiffFile`, `DiffSummary`, `CachedDiffResponse`, `DiscardResult`, `GeneratePrContentResult`, `ClosePullRequestResult`, `MergeReadinessResponse`, `CheckRun`, `PrDeploymentResponse`, `GenerateCommitMessageResponse`, `FixChecksResponse`, `FixCheckSnippet`, and `GeneratePrResponse`, and `DiffResponse.properties.files.items` is `{"$ref": "#/components/schemas/DiffFile"}` (named Swift types, not anonymous inline payloads).
- Given any of the 12 operations, when the spec unit test runs, then each has a unique `operationId` and a documented `401` response, and no schema in the document contains `"additionalProperties": false` (M1-01 hygiene applies to the new entries automatically because they go through the same `j()`/`ref()` helpers).
- Given a request to `POST /api/sessions/{sessionId}/checks/fix` with `{"checkRuns": []}`, when the route validates with the new `fixChecksRequestSchema`, then it still returns `400 {"error":"No check runs provided"}`; with 11 check runs it still returns `400 {"error":"Too many check runs (max 10)"}` — identical status codes and messages to today's manual validation.
- Given a request to `POST /api/generate-pr` with no `sessionId`, when the route runs, then it still returns `400 {"error":"Session ID is required"}` and the existing staged validation order (sessionId check before session lookup, branch checks after sandbox check) is untouched — this route's manual validation is deliberately preserved (see In scope for the documented deviation).
- Given an owned session whose sandbox is paused, when the client calls `GET /api/sessions/{sessionId}/diff`, then the documented `409 {"error":"Sandbox is unavailable. Please resume sandbox."}` envelope appears in the spec for every sandbox-touching operation in this batch, because the iOS `ConflictKind.sandboxUnavailable` mapping depends on that exact string.
- Given a session with no cached diff, when the client calls `GET /api/sessions/{sessionId}/diff/cached`, then the spec documents `404` with the `ErrorResponse` envelope (live message: `No cached diff available`), and the 200 shape is `{ data: DiffResponse, cachedAt (format: date-time), isStale: boolean }`.
- Given `GET /api/sessions/{sessionId}/diff/patch` or the dev-server logs route, when the spec is built, then they are absent: raw-body (`text/x-diff`, `text/plain`) endpoints stay excluded per `docs/plans/ios-app/02-api-contract-and-networking.md` section 0.4.
- Given `bun run --cwd apps/web openapi:check` after committing both regenerated artifacts, when it runs, then it exits 0 and prints the in-sync message.

## Product and design spec

This is a server contract slice with no end-user UI change. The "product" is the contract artifact pair and the developer flow around it:

- Entry point: `apps/web/lib/api/openapi-spec.ts` (`buildOpenApiDocument()`) is the single source of truth; `apps/web/openapi.json` and `apps/web/lib/api/openapi-types.ts` are committed, regenerated outputs. Never hand-edit `openapi.json`.
- Primary flow: edit the builder → `bun run --cwd apps/web openapi:generate` → `bun run --cwd apps/web openapi:types` → `bun run --cwd apps/web openapi:check` → commit all three files together (section 2.4 procedure).
- States: in-sync (both gates green) or drift (gate fails with an actionable message telling the developer to regenerate). There is no partial state — the checker string-compares the whole document.
- Error/empty behavior: every operation documents its error statuses from the section 1.7/1.8 tables, all using the `ErrorResponse` (`{ error: string }`) envelope registered in M1-01. The 409 sandbox-unavailable envelope is documented on `listSessionFiles`, `getSessionFileContent`, `getSessionDiff`, `discardChanges`, and `generatePrContent` because the iOS Resume affordance keys off it.
- Permissions/copy/accessibility: not applicable (no UI). Downstream iOS copy for these states is owned by the epic's M4+ issues.

New/changed source files:

- `apps/web/lib/github/http-schemas.ts` (new): `checkRunSchema` (mirror `CheckRun` in `apps/web/lib/github/pulls.ts`: `{ id: z.number(), name: z.string(), state: z.enum(["passed","pending","failed"]), status: z.string().nullable(), conclusion: z.string().nullable(), detailsUrl: z.string().nullable() }`), `fixChecksRequestSchema` (`z.object({ checkRuns: z.array(checkRunSchema).min(1, "No check runs provided").max(10, "Too many check runs (max 10)") })`), and `generatePrRequestSchema` (`z.object({ sessionId: z.string().min(1), sessionTitle: z.string(), baseBranch: z.string().min(1), branchName: z.string().min(1), createBranchOnly: z.boolean().optional() })`).
- `apps/web/app/api/sessions/[sessionId]/checks/fix/route.ts`: replace the manual `Array.isArray`/length checks with `fixChecksRequestSchema.safeParse`, returning the schema's message in the existing `{ error }` envelope. Status codes and messages must not change.
- `apps/web/app/api/generate-pr/route.ts`: NOT rewired (see In scope). `generatePrRequestSchema` documents the contract and is unit-tested against the route's accepted payloads.
- `apps/web/lib/api/openapi-spec.ts`: import `discardChangesRequestSchema`, `generatePrContentRequestSchema`, `deploymentUrlQuerySchema` from `apps/web/lib/git/http-schemas.ts` and the new schemas from `apps/web/lib/github/http-schemas.ts`; define response Zod schemas for the table above; add the 12 path entries; register names via the M1-01 `ref(...)` registry. Container schemas (`DiffResponse` → `DiffFile`/`DiffSummary`, `CachedDiffResponse` → `DiffResponse`, `MergeReadinessResponse` → `CheckRun`, `FixChecksResponse` → `FixCheckSnippet`) must emit nested `$ref`s in the committed JSON — compose those container JSON schemas with `ref(...)` for the nested parts (or reuse whatever nested-ref helper M1-01 landed); the acceptance check is on the artifact, not the mechanism.
- Query parameters: `getSessionFileContent` declares `{ name: "path", in: "query", required: true, schema: { type: "string" } }`; `getDeploymentUrl` declares optional `prNumber` (integer) and `branch` (string) matching `deploymentUrlQuerySchema`. All 12 operations reuse the existing `sessionIdParam` path parameter except `generatePr` (sessionId travels in the body).
- Timestamps: `cachedAt` uses `z.iso.datetime()` (Blocker 3 convention from M1-01).

Data model, auth, agent/sandbox/workflow surfaces, and config: unchanged. No DB migration. Compatibility: additive spec change; web client untouched; the iOS generated client (epic milestone M3+) consumes the new operations.

## Observability and user feedback

This slice is contract documentation plus one behavior-preserving validation rewire; it adds no new runtime events, and that is deliberate — the routes' existing logging (for example the `[generate-pr]` console lines in `apps/web/app/api/generate-pr/route.ts`) is untouched. The observable evidence is the gate output and the documented error vocabulary:

- Named module: `apps/web/lib/api/openapi-spec.ts` is the contract source; its gates are `apps/web/scripts/check-openapi.ts` (prints the in-sync confirmation or an actionable drift error and exits 1) and `apps/web/lib/api/openapi-spec.test.ts` (deep-equality, unique operationIds, documented 401s).
- Typed error vocabulary the spec must document verbatim, because the iOS `APIError` mapper (`docs/plans/ios-app/07-observability.md` section 6 and plan 02 section 4.2) string-matches them: `Sandbox is unavailable. Please resume sandbox.` (409 → `ConflictKind.sandboxUnavailable`), `No cached diff available` (404), `File is too large to preview` (413), `No check runs provided` / `Too many check runs (max 10)` (400), `Session ID is required` (400), `Access denied` (403 BotID signature). These live in the operations' response `description` fields and the `ErrorResponse` envelope.
- Correlation IDs: none added server-side here; the iOS client sends `x-request-id: ios-<uuid>` per plan 02 section 4.1, and contract tests print status plus body on failure, which is the incident evidence for this surface.
- Redaction: the spec and its examples must contain no real tokens, session ids, repo names, or file contents — schema shapes only. `getSessionFileContent` keeps its documented `Cache-Control: no-store` note so clients never disk-cache user file contents.

  - `jq '.components.schemas | keys' apps/web/openapi.json` — confirm the 17 registered names.

## Regression risks and concerns

- The checks/fix rewire tightens item-level validation: a malformed `CheckRun` (for example `id` as a string) previously slipped past the array/length checks and now 400s. The real web client (`apps/web/lib/...` merge-dialog flow) always sends well-formed runs, but the route's first-issue Zod message will differ from the legacy text for that previously-unvalidated case — acceptable, called out in the PR.
- Do not rewire `POST /api/generate-pr`: flipping its staged validation to Zod-first changes observable status ordering (400 vs 404). The deviation is explicit in In scope.
- Schema-name collisions: the M1-01 registry throws on conflicting definitions for the same name. If M1-02/M1-03 merged first and already registered an overlapping name (none expected for this batch), reconcile to a single shared Zod schema rather than renaming.
- Nested `$ref` assembly is the most error-prone step; the `DiffResponse.properties.files.items.$ref` test assertion plus the `grep -c` acceptance check catch a silent inline-duplication regression.
- Forgetting to regenerate either artifact fails `openapi:check` or the spec unit test — never hand-edit `apps/web/openapi.json` to silence them.
- Merge-order risk with sibling batches: each batch adds disjoint paths, but `openapi.json` regenerates wholesale, so expect artifact-level merge conflicts; resolve by re-running the section 2.4 procedure on the merged builder, never by hand-merging JSON.

## Deploy or migration impact

No database migration and no schema.ts change. Runtime behavior change is limited to the checks/fix validation rewire (same statuses/messages on the documented paths). The spec artifacts are build-time only; preview and production deploys are unaffected beyond shipping the updated committed files. No new env vars. Safe to ship independently once M1-01 is on `develop`.
