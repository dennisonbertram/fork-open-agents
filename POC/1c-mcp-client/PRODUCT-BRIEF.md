# Product Brief: First-Class MCP Client

> Status: Proof-of-concept complete (eval-backed). This brief argues whether to productize it.

## TL;DR
Let any agent session mount arbitrary Model Context Protocol (MCP) servers — databases, internal tooling, the filesystem, third-party services — per repo and per session, auto-discover their tools, and expose them to the agent as ordinary namespaced tools (`mcp__<server>__<tool>`). It serves teams whose real work depends on systems beyond GitHub: query the staging DB, hit the internal API, read the design-system registry. The core bet: the agent becomes dramatically more useful when users can plug in *their* tools instead of waiting for us to build first-party integrations for each one. Recommendation: build it — feasibility is strong and the merge path is free — but gate it hard on the sandbox-execution and security decisions, and ship behind the approval gate (POC 1b).

## The gap today
Today the agent's tool surface is fixed by us: built-in tools (`read`, `bash`, …) plus the curated Composio SaaS integrations. There's no way for a user to say "also give the agent access to my Postgres staging DB" or "let it call our internal deploy API" or "mount this team's MCP server." If a team's workflow depends on a system we haven't integrated, the agent simply can't reach it — the user falls back to copy-pasting query results into the chat by hand, or doing that step themselves. Meanwhile the entire MCP ecosystem (Claude Desktop, Cursor, the official filesystem/everything servers, and a growing catalog of database/SaaS/internal servers) is something the agent can't tap, even though the AI SDK already in the repo ships a production MCP client. We're leaving a large, standards-based capability on the table.

## What we'd build
A per-session/per-repo MCP client that mounts a user-configured set of servers (stdio command+args, or Streamable HTTP / legacy SSE URLs), connects, discovers each server's tools, and merges them into the agent's `ToolSet` — namespaced `mcp__<server>__<tool>` so they never collide with built-ins or Composio's `COMPOSIO_*`. The POC proved the full round trip with no mocks against **two real MCP servers**: a custom stdio `math` server (`add`, `echo`) and the official `@modelcontextprotocol/server-filesystem`, asserting connect→list→call→guard→close, exact results (`add(2,3)==5`, real file contents read back), and clean teardown — all passing. Critically, the AI SDK v6 MCP client (`@ai-sdk/mcp`, backing `experimental_createMCPClient`) returns objects that *are* AI-SDK `Tool`s, so they drop into the **exact same `requestedTools` merge path Composio already uses** in `chat.ts` / `open-agent.ts` — zero new merge machinery. Productizing means: an `mcpSelection` jsonb column on `chats` (mirroring `composioSelection`), a per-repo `repository_mcp_settings` defaults table (mirroring `repository_composio_settings`), a `resolveMcpToolsForChat(...)` resolver, and a server-selection UI — plus the consequential decision of *where* stdio servers run.

## How users experience it
### Where it lives (exposure)
- **Settings → Integrations → MCP Servers (per repo):** the management surface. "Add server" with fields for transport (stdio command+args / HTTP URL), name, `env`/`headers` for secrets (stored encrypted, never model-visible), and per-server tool allow/deny lists.
- **Per-session tool picker:** a chat-level chip/panel ("Tools: math, fs") to enable/disable configured servers for the current session, mirroring how Composio toolkits are selected.
- **Repo-level defaults:** an org/repo admin sets an approved server catalog so sessions inherit safe defaults (the `repository_mcp_settings` analog).

### Sample UI
- **Server list (Settings):** rows of configured servers, each showing name, transport badge (stdio / HTTP), connection status (a live "16 tools discovered" / "couldn't connect" indicator), and a tool-count chip. Expanding a row reveals the discovered tool list with checkboxes for allow/deny.
- **Add-server form:** transport selector → conditional fields (command + args + env for stdio; URL + headers for HTTP); a "Test connection" button that runs the MCP `initialize` handshake and shows discovered tools before saving.
- **In-chat tool-call card:** when the agent calls `mcp__fs__read_text_file`, the card shows a server badge ("fs"), the tool name, and the args/result — visually distinct from built-in and Composio tools so users know it's reaching an external system.
- **Tool-budget warning:** because two servers already yield 16 tools (the filesystem server alone is 14), the UI surfaces a "this session has N tools mounted — large tool sets slow responses and raise cost" warning with a one-click "trim to allow-list."
- **States:** connecting, ready (N tools), partial ("2 of 3 servers mounted — `db` failed: connection refused"), failed, and disabled. Per-server failure is attributed, not a blanket session error.

### UX walkthrough
1. A team admin opens Settings → MCP Servers for their repo and adds an HTTP server pointing at their internal "staging-db" MCP server, with a `Authorization: Bearer …` header stored encrypted. "Test connection" shows 5 discovered tools; they allow-list just `query` and `describe_table`. They save it as a repo default.
2. A developer starts a session on that repo. The tool picker shows "staging-db" available; they enable it.
3. Developer: "Why are signups failing today? Check the staging users table."
4. The agent calls `mcp__staging-db__describe_table(users)`, then `mcp__staging-db__query(...)`. Each renders as a card with the "staging-db" badge; the parked-approval gate (1b) fires before the write-capable variant, but read queries pass.
5. The agent reads the returned rows, correlates with a recent migration, and explains the failure — citing real data it pulled itself, no copy-paste.
6. After the turn, the session tears down the MCP transports (proven clean in the POC's `close` step).

## Value to the user
**Job-to-be-done:** "Give the agent access to the *rest* of my stack — my database, my internal tools, my files — so it can do end-to-end work, not just the GitHub-shaped slice." Scenarios:
- **Debug with real data:** "This query is slow in prod." The agent mounts the team's DB MCP server, runs `EXPLAIN`, sees the missing index, writes the migration, and opens the PR — all in one session instead of the user shuttling query output back and forth.
- **Bring-your-own-tool, no waiting on us:** a team has an internal "feature-flags" MCP server; they mount it and the agent can flip a flag as part of a change, without us ever building a first-party feature-flag integration.
- **Local context:** mounting the filesystem server scoped to a data dir lets the agent read fixtures, logs, or generated artifacts the repo references but doesn't contain.

## Value to the product
This is the **extensibility flywheel**: instead of our roadmap being the bottleneck on what the agent can reach, users and the open MCP ecosystem extend it themselves. It's a strong differentiator and ecosystem-alignment play — MCP is becoming the standard tool-interop layer, and being a first-class MCP host puts open-agents on the same plane as Claude Desktop and Cursor while keeping the cloud-sandbox + PR-flow advantage. It drives expansion and retention for teams (every internal server they mount deepens lock-in and session value) and complements, rather than competes with, Composio (curated SaaS) by covering the long tail of custom/internal/standards-based tools. Strategically it reframes open-agents from "an agent with our integrations" to "an agent that speaks to your whole stack."

## The case FOR (strong)
1. **The integration is nearly free, and proven.** The AI SDK v6 already in the repo ships a production MCP client whose output *is* the agent's `ToolSet`; MCP tools reuse the exact `requestedTools` merge path Composio uses — no new merge machinery. The POC ran a real, mock-free round trip against a custom server and the official filesystem server, all checks passing.
2. **It removes us as the bottleneck on agent reach.** Every team's stack is different; first-party integrations can't scale to the long tail. MCP lets users plug in their own systems and tap the whole open ecosystem immediately.
3. **It rides existing patterns end to end.** Config mirrors `composioSelection` (a jsonb column + per-repo defaults table), secrets reuse the encrypted-credential pattern, namespacing (`mcp__…`) provably avoids collisions, and observability events slot in beside the existing `composio.*` events.
4. **Standards alignment future-proofs us.** Betting on MCP rather than bespoke adapters means new servers built by anyone work with us for free, and we stay interoperable as the protocol stabilizes.
5. **It composes with the other two POCs into a coherent autonomy story:** mount your tools (1c), guard the dangerous ones (1b), and let the agent see results (1a).

## The case AGAINST (strong)
1. **The "where do stdio servers run" decision is a serious security fork, and it's unsolved.** stdio MCP servers spawn child processes from user-configured commands. Running arbitrary commands in the Next.js web process is a flat-out RCE/exfiltration risk (the POC explicitly refused to do this beyond the trusted eval). The right answer — run them inside the per-session sandbox with resource/time limits — is real, unbuilt work; HTTP servers dodge local spawning but introduce SSRF/egress concerns instead. There is no free, safe path here.
2. **Untrusted, model-visible content is a prompt-injection vector by design.** Third-party MCP servers control tool *descriptions* and *results*, both of which the model reads. Namespacing prevents name collisions, not malicious content. We inherit every prompt-injection risk of third-party tooling, and the blast radius now includes whatever those servers (DBs, internal APIs) can touch.
3. **Tool-count bloat degrades the whole agent.** Two servers already mounted 16 tools; mounting several balloons the tool list and system-prompt token cost, slowing and degrading *every* turn, including non-MCP work. This forces mandatory allow/deny lists and caps — more product surface and more ways for users to misconfigure.
4. **It overlaps with Composio and may confuse the model.** We'd have two parallel external-tool systems (Composio + MCP). Users have to understand which to use; the agent has two tool-provenance namespaces; and we maintain two resolver/config/UI stacks. A simpler path is to lean harder on Composio and only add MCP for the specific gaps it can't cover.
5. **`managed_runtime` mode filters MCP tools out by default, so the headline value may not reach the default surface.** Today managed runtime restricts to a fixed allowlist via `pickTools`; MCP tools won't appear there unless we deliberately extend it — a policy decision with its own safety weight. And the client-side validation gap (AI SDK passes MCP args through unchecked; only the server validates) means we're trusting third-party servers as the validation boundary.

## Effort, dependencies & risk
- **Feasibility verdict (from POC):** Strongly feasible, low *integration* risk — zero new merge machinery, real round trip proven against two servers, clean lifecycle. The risk is concentrated in security/execution-placement, not plumbing.
- **Build size:** Medium. `mcpSelection` column + `repository_mcp_settings` defaults table + `resolveMcpToolsForChat` resolver + server-management UI + tool allow/deny + observability events — plus the sandbox-execution implementation, which is the real cost center.
- **Cross-POC dependencies:** Should ship behind **POC 1b** (gate MCP write/external actions). Sandbox execution of stdio servers depends on `packages/sandbox` (`exec`, `domain(port)`) being able to host child processes with limits.
- **Top risks & mitigations:** (a) RCE from stdio spawning → run stdio servers *inside* the per-session sandbox with resource/time limits, never in the web process; prefer HTTP servers where possible. (b) Prompt injection → apply the same hardening used for web/Composio content; treat third-party server output as untrusted. (c) Tool bloat → mandatory per-server allow/deny lists (like Composio's `blockedToolkitSlugs`) + a session tool cap, surfaced in UI. (d) Per-server failure → mount healthy servers, attribute the failed one as an observability event, never fail the whole turn. (e) SSRF/egress for HTTP servers → egress policy/allowlist. (f) Version coupling → track `@ai-sdk/mcp` as it sheds `experimental_` aliases.

## The decision
**The question to answer:** Do we want users to extend the agent's reach with arbitrary MCP servers now — accepting that we must solve sandbox execution and third-party-content security to do it safely — or keep the tool surface curated (built-ins + Composio) and add MCP only once those guardrails exist? **Greenlight trigger:** a validated design for running stdio MCP servers inside the per-session sandbox with enforced resource/time limits, plus an allow/deny + tool-cap policy, plus the approval gate (1b) in place. **Success looks like:** teams mounting their own servers and using them in a meaningful share of sessions, MCP-tool calls correlated with longer/deeper sessions and higher task-completion, no security incidents traced to mounted servers, and median session tool-count kept under control by allow-lists. **Suggested default: build later — but next.** The capability and merge path are proven and the strategic value is high, but it should *follow* the approval gate (1b) and a concrete sandbox-execution + security design. Don't ship it ungated; do schedule it as the immediate follow-on, starting with HTTP/remote servers (which dodge the RCE fork) before enabling sandbox-hosted stdio servers.
