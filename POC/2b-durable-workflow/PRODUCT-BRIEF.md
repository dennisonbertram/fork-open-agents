# Product Brief: Durable Workflow Runtime (the Reliability Keystone)

> Status: Proof-of-concept complete (eval-backed). This brief argues whether to productize it.

## TL;DR
This is the infrastructure that makes a long, parked, scheduled, or event-woken agent run survive a process crash, a deploy, or a sandbox teardown — completed steps replay instead of re-executing, suspended runs cost no compute, and resume is deterministic. The POC proved every durability property from first principles across a *real* hard crash (`exit(137)`, two separate OS processes joined only by an on-disk store): 19/19 assertions, with a non-idempotent side effect firing exactly once across the crash boundary. It is the keystone: 2a (cron), 2c (event-driven), 1b (approval park), and long-running agents in general are all blocked on it. Recommendation: build first; adopt the Vercel Workflow DevKit backed by a self-hostable Postgres World on the existing Neon DB.

## The gap today
The repo's agent loop already uses the Vercel Workflow DevKit (`"use workflow"` / `"use step"`), but durability is **World-dependent**: it's real on the Vercel-managed World, while the local World executes steps synchronously and is not a crash-durability proof, and the managed World is `iad1`-only today. The practical consequence is that the product cannot *honestly promise* that a run survives teardown — and the agent's whole runtime is a per-session microVM sandbox that *will* be torn down. Who feels the pain: any user whose run is long (a 50-step refactor that dies at step 40 today restarts at step 0, re-running tool side effects and re-billing model calls), any run that must pause for human approval (1b), and every run that should be triggered while no human is watching (2a, 2c). It also hurts the operator: there is no durable record to reason about *why* a run stalled, and the current client-reconnect path is a best-effort `claimActiveStream`/`clearActiveStream` dance rather than a persisted, resumable stream.

## What we'd build
A durable execution layer the whole platform runs on: agent runs become checkpointed workflows where each step's result is persisted, a crash loses nothing, suspended runs (sleep timers, approval gates, event waits) consume no compute, failed steps retry with backoff, and resume replays the log to the frontier deterministically. The POC validated the exact contract: `ctx.step(key, fn, retry?)` checkpoints results (replay-not-rerun), `ctx.sleep(key, ms)` persists an on-disk deadline (not a `setTimeout`), `ctx.waitForEvent(key, token)` persists an undelivered waiter that an HTTP endpoint resolves via `deliverEvent(token, payload)`, and retries carry crash-safe attempt counts with exponential backoff. The recommended production path is the DevKit's `@workflow/world-postgres` pointed at the existing Neon database — same agent code, durability on our own infrastructure, no new vendor.

## How users experience it
### Where it lives (exposure)
This is infrastructure; its "exposure" is mostly the *reliability users perceive* plus an operator/observability surface:
- **Users:** a **run status** on every session/chat that is now trustworthy — "Running (step 12 of ~)", "Paused — awaiting your approval", "Sleeping until Mon 9:00", "Resumed after interruption" — and a chat stream that survives a reload/redeploy and reconnects where it left off.
- **Operators:** a **Runs** admin view backed by the persisted `workflowRuns` table — every run with status, current step, attempt counts, suspend reason, and timings.
- **Developers:** the existing `chat.ts` workflow stays structurally the same; the new affordances are `sleep()`, typed `createHook<T>({ token })`, and `withRetry` available inside the workflow body.

### Sample UI
**Operator observability UX:** a **Runs dashboard** listing every workflow run with a status pill (Running / Suspended-sleep / Suspended-event / Retrying / Completed / Failed), the current/last step key, attempt count when >1, suspend reason (e.g. "awaiting approval token", "sleeping until 2026-06-01T09:00Z"), and start/finish timestamps. Drilling into a run shows a **step timeline**: each step with its checkpoint status (completed/replayed/failed-attempt-N), so an operator can see exactly where a run is parked and why — the durable log made visible. **User-perceived reliability UX:** the chat header status chip becomes honest and specific ("Paused — your approval needed", "Sleeping — resumes Mon 9:00 AM", "Reconnected — resuming"), and a reloaded page reattaches to the persisted stream instead of showing a dead or duplicated transcript. States to design: actively-streaming, suspended-on-sleep (with wake time), suspended-on-approval, retrying-after-failure (with attempt N/M), resumed-after-crash, and terminal completed/failed.

### UX walkthrough
1. A user kicks off a long refactor; the chat shows "Running (step 1…)".
2. Midway, the platform redeploys / the sandbox is recycled. **Before:** the run would silently die or restart from zero. **After:** the run is checkpointed; the status chip shows "Reconnected — resuming," and streaming continues from the last completed step — no duplicated commits, no re-billed model calls.
3. The agent hits a step requiring approval; the run *suspends durably* and the chip shows "Paused — your approval needed." It costs no compute while parked, even for days.
4. The user approves hours later from another device; an endpoint delivers the approval token, the run resumes past the gate.
5. A flaky external step fails twice; the operator dashboard shows "Retrying (attempt 3/3)" with backoff, then the step succeeds and the run completes.
6. An operator investigating a stuck run opens the step timeline and sees precisely which step is suspended and on what token — diagnosis in seconds, from durable state.

## Value to the user
**Job-to-be-done:** "Trust the agent to finish what it started — even across interruptions, pauses, and waits." Scenarios:
- **The long refactor that survives a deploy** — a 50-step change that previously had to complete inside one function's lifetime now resumes at step 40 after any interruption, with side effects done exactly once.
- **The pause that actually holds** — an agent parked on "approve this destructive migration?" stays parked for days at zero cost and resumes correctly when the human gets to it (this is the durability 1b explicitly deferred).
- **The stream that reconnects** — a user closes their laptop mid-run; reopening reattaches to the live stream rather than showing a broken or restarted transcript.

## Value to the product
This is the **reliability foundation the rest of the roadmap stands on** — its single biggest strategic value is that it *unblocks 2a, 2c, and 1b at once*, turning three blocked features into shippable ones. It moves open-agents from "best-effort runs inside one serverless lifetime" to "durable agent execution," which is a credibility line for any serious or paying user: long runs, scheduled runs, and approval-gated runs are exactly the workloads that justify upgrading. It's also a **margin** lever — suspended runs consuming no compute means parked/scheduled work isn't billed idle time — and a **lock-in-avoidance** story we can tell honestly: the DevKit's World abstraction runs the same code on dev (local), managed (Vercel), or self-hosted (Postgres on our own Neon), so adopting it does *not* trap us in a vendor, whereas the external-queue alternatives (Upstash, Inngest) are cloud-only. Strategically, durability is invisible when it works and catastrophic when it doesn't; owning it well is table stakes for being trusted with someone's repo.

## The case FOR (strong)
1. **It's the keystone — highest leverage on the board.** One build unblocks 2a (cron), 2c (event-driven), 1b (approval park), and long-running agents generally. Nothing else has that multiplier.
2. **The durability contract is proven, not assumed.** The POC reproduced replay-not-rerun, durable sleep, event-suspend, and retry/backoff from first principles across a real `exit(137)` crash and two processes sharing only an on-disk store — a non-idempotent side effect fired exactly once (19/19). We now *understand* the contract we'd depend on, with a known-good ~600-line fallback engine if the DevKit beta disappoints.
3. **It's a low-disruption adoption, not a rewrite.** The repo is already on the DevKit; `chat.ts`'s `"use workflow"`/`"use step"` functions already match the validated contract. The change is pinning `@workflow/world-postgres` at Neon and swapping the approval pause for a durable hook — no structural rewrite of the agent loop.
4. **It avoids vendor lock-in instead of adding it.** The World abstraction keeps the same code portable across local/managed/self-hosted; choosing Upstash or Inngest would mean an HTTP-step rewrite *and* a cloud-only dependency — more lock-in for capabilities the DevKit already has.
5. **It pays for itself in correctness and cost.** Exactly-the-frontier resume means no duplicated tool side effects and no re-billed model calls on a crash; zero-compute suspends mean parked runs don't burn money.

## The case AGAINST (strong)
1. **It's load-bearing infrastructure on a beta.** The DevKit is pinned at `^4.2.0-beta.72` while docs are v5, and `world-postgres` maturity is unverified against our actual Neon setup. Betting the platform's reliability story on beta directive semantics is real risk — even with the fallback engine as insurance.
2. **No direct user-facing feature ships from it alone.** A leadership reviewer can reasonably ask "what does the user *get*?" and the honest answer is "nothing visible by itself — it unblocks other things." That makes it easy to deprioritize against features with a screenshot.
3. **At-least-once is not exactly-once.** A crash *between* a side effect and its checkpoint write can re-run that step. Every step with external side effects (commits, PRs, payments) must be made idempotent or idempotency-keyed — a discipline tax across the codebase, not a one-time fix.
4. **Determinism contract is a sharp edge.** Replay requires steps requested in stable order returning serializable results; any un-stepped side effect or non-deterministic control flow in the workflow body desyncs replay. This constrains how all future agent code is written and is easy to violate accidentally.
5. **The prototype isn't the product.** The POC's SQLite engine has no concurrent-worker locking, leasing, or visibility timeouts; the real World (or a Postgres rewrite) must supply those, and stream resumption under the DevKit was not exercised by this POC and needs its own verification against the current reconnect UX.

## Effort, dependencies & risk
**Feasibility verdict (from POC): the durability model is proven and the adoption path is native** — the repo already runs on the DevKit. **Build size:** medium — pin and configure `@workflow/world-postgres` against Neon (`POSTGRES_URL`), verify locally on the Local World first, swap the approval pause for a typed `createHook`, expose `sleep()`/event-resume seams for 2a/2c, and replace the best-effort reconnect dance with persisted resumable streams — plus the operator Runs dashboard and honest user-facing status. **Cross-POC dependencies:** this is the *dependency* — 2a, 2c, and 1b all wait on it; it depends on nothing else. **Recommendation:** adopt the Vercel Workflow DevKit + `@workflow/world-postgres` on Neon; do **not** add Upstash/Inngest. **Top risks + mitigations:** (a) beta instability → validate `world-postgres` against real Neon before committing the agent loop; keep the POC's `engine.ts`/`store.ts` as a controlled fallback executor; (b) at-least-once re-runs → make side-effecting steps idempotent / idempotency-keyed (commits, PRs); (c) determinism desync → keep step boundaries pure, key steps explicitly, no un-stepped side effects in the workflow body; (d) prototype gaps (locking/leasing) → rely on the World's production guarantees, not the SQLite prototype; (e) stream resumption → verify DevKit resumable streams against the current reconnect UX before claiming it.

## The decision
**The crisp question:** Do we adopt a durable execution runtime now — specifically the DevKit on a self-hosted Postgres World — as the foundation the proactive-agent roadmap stands on? **Recommended trigger to greenlight:** immediately; this gates the rest of Wave 2, so every quarter it waits, 2a/2c/1b wait too. **Success metrics:** run-survival rate across deploys/teardowns (target ≥99.9% resume-without-loss); zero duplicated side effects on resume in a soak test; suspended-run compute cost ≈ 0; operator mean-time-to-diagnose a stuck run (via the step timeline) dropping sharply; successful `world-postgres`-on-Neon validation. **Suggested default: BUILD — and build it FIRST.** Rationale: it is the highest-leverage item on the board (one build, three-plus unblocks), the durability contract is already proven from first principles, adoption is native rather than a rewrite, and it avoids rather than adds vendor lock-in. The only honest hesitation — beta risk and no standalone screenshot — is outweighed by the fact that 2a, 2c, and 1b cannot ship reliably without it, and is hedged by the known-good fallback engine.
