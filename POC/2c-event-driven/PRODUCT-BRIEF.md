# Product Brief: Event-Driven Agents (Wake on Event X)

> Status: Proof-of-concept complete (eval-backed). This brief argues whether to productize it.

## TL;DR
Event-driven agents let a user say "when X happens, run this agent" — where X is a GitHub issue opened, a failed deploy, a Sentry alert, an inbound email, or any registered source — turning open-agents into a reactive automation surface, not just a chat box. The POC proved a source-agnostic pipeline (verify → normalize → match rules → dispatch) across five real sources with three distinct signature schemes plus a bearer escape hatch, passing 53/53 assertions including fan-out, redelivery dedup, bad-signature rejection, and no-regression on the existing GitHub PR-close behavior. It generalizes today's GitHub-only ingestion additively, not as a rewrite. The open dependency is durability (POC 2b) for the woken run to survive teardown. Recommendation: build, sequenced after 2b.

## The gap today
The product already ingests GitHub webhooks (`/api/github/webhook`: HMAC-verify, parse by `x-github-event`, dispatch), and there's a *partial* generalization in `lib/background-agents/` — but it is **GitHub-only and repo-centric**: the single normalizer only understands GitHub payloads, every normalized event *requires* a repo, and the only verifier is GitHub's signature scheme. So an agent can react to a GitHub PR but cannot react to the failed deploy that PR caused, the Sentry error it triggered, or the customer email reporting it. Who feels the pain: teams who want their repo agent wired into their actual incident loop (deploy fails → agent investigates → opens a fix PR), support-adjacent flows (bug-report email → agent triages and files an issue), and anyone whose meaningful triggers live outside GitHub. A single hard-coded verifier would silently reject three of four real external sources — the gap isn't cosmetic, it's structural.

## What we'd build
An "on event X, wake an agent" capability: operators register event sources (GitHub, Vercel deploys, Sentry, AgentMail/email, or a generic bearer source) with their signing secrets, and users define **trigger rules** — "when source=vercel-deploy and type=deployment.error, run an agent against repo Y with this prompt template." The platform verifies each inbound payload with that source's real scheme, normalizes it to a canonical `AgentEvent { source, type, externalId, repo?, actor?, subject, body, metadata }`, matches it against enabled rules (with `{{field}}` prompt templating), dedups on an idempotency key, and dispatches the run. The POC proved the mechanism end-to-end: a per-source verifier+normalizer registry (GitHub `sha256=`, AgentMail bare-hex SHA256, Vercel SHA1, Sentry SHA256 under a different header, generic bearer), a payload-shape-agnostic rule engine, and the existing GitHub PR-close behavior reproduced as *one data-defined rule* to prove generalization is additive, not a regression.

## How users experience it
### Where it lives (exposure)
- A new **Triggers** section in settings/nav, listing trigger rules with enable/disable switches.
- A **"New trigger"** builder: pick a source, an event type (with wildcards like `source.*`), optional match conditions (field equals/in/prefix/contains), a target repo (optional — email/Sentry events have none), and a prompt template with `{{field}}` interpolation.
- An operator **Event Sources** admin screen to register a source kind, paste/rotate its signing secret, and copy the webhook URL to paste into GitHub/Vercel/Sentry/AgentMail.
- A per-source **delivery log** showing recent inbound events, verify pass/fail, which rules matched, and the dispatched run.

### Sample UI
The **Triggers list** shows each rule: name, "When [source] [type] [match summary]", "→ run agent on [repo]", last-fired timestamp, and an enable switch. The **rule builder** is a When/Then form: a *When* block (source dropdown → type dropdown/wildcard → optional condition rows: field path · matcher · value) and a *Then* block (target repo picker, prompt template editor with an insert-field menu showing available `{{subject}}`, `{{actor}}`, `{{metadata.x}}` keys, and a live preview rendered from a sample payload). The **Event Sources** screen lists registered sources with a kind badge, the webhook URL, a "rotate secret" action, and a **verification-health** indicator (verify-failure rate per source — critical, since a rotated/misconfigured secret looks identical to an attacker: both 401). The **delivery log** renders each inbound event as a row: source, type, externalId, verify result (green/red), matched rule(s), and the dispatched run link — with redelivered-duplicate rows clearly marked "deduped (0 new runs)." States to design: verified+matched+dispatched, verified+no-rule (no-op), verify-failed (rejected), and fan-out (one event → multiple matched rules → multiple runs).

### UX walkthrough
1. Operator opens **Event Sources**, registers a `vercel-deploy` source, pastes the signing secret, copies the webhook URL into the Vercel project's webhook settings.
2. User opens **Triggers → New trigger**: *When* source `vercel-deploy`, type `deployment.error`; *Then* run an agent on `acme/storefront` with prompt "A deploy just failed: {{subject}}. Investigate the build error in {{metadata.commitSha}} and open a fix PR."
3. The builder's live preview renders the prompt against a sample failed-deploy payload; the user saves; the rule appears enabled.
4. A real deploy fails. Vercel POSTs the (SHA1-signed) payload; the pipeline verifies it, normalizes it to an `AgentEvent` (deriving the repo from commit meta), matches the rule, renders the prompt, dedups, and dispatches one run.
5. The user sees a new session appear with the agent already investigating; the delivery log shows the event verified and matched.
6. Vercel redelivers the same event (webhooks retry); the log shows "deduped (0 new runs)" — the agent doesn't double-fire.

## Value to the user
**Job-to-be-done:** "Have an agent react to what's already happening in my stack, automatically." Scenarios:
- **Deploy failure → auto-investigation** — a failed Vercel deploy wakes an agent that reads the build error and opens a fix PR before anyone pages the on-call.
- **Bug-report email → triage** — an inbound support email matching "Bug" fans out to both a support-triage rule and a bug-report rule, producing a labeled issue and a first-pass reproduction attempt (the POC proved this exact fan-out).
- **Sentry alert → context-gathering** — a new Sentry issue wakes an agent that correlates the stack trace to recent commits and posts findings, turning a 2am alert into a head start.

## Value to the product
This is the capability that plugs open-agents into a team's **actual operational loop** rather than sitting beside it — the move from "a place I go to code with an agent" to "an agent embedded in my CI/incident/support pipeline." Strategically it's a powerful **integration and lock-in** surface: every registered source (Vercel, Sentry, GitHub, email) is an embedded webhook the team won't casually unwind, and each trigger rule is accumulated automation value that raises switching cost. It's an **expansion** story (more sources, more rules, more triggered runs — natural metering) and a strong **differentiation** play: competitors mostly react to GitHub; "react to your deploys, your errors, and your inbox, with a repo-aware agent that opens PRs" is a wider and more defensible footprint. It also composes with 2a — scheduled *and* event-driven coverage together is the full "standing agents" pitch.

## The case FOR (strong)
1. **Proven across real heterogeneity.** 53/53 assertions with each fixture signed by its *true* scheme — three different HMAC algorithms plus a bearer — verifying and rejecting both ways. The hard part (per-source auth differences that a single verifier would silently fail) is solved and demonstrated.
2. **Additive, not a rewrite.** The canonical `AgentEvent` cleanly subsumes the existing GitHub-only model (repo becomes optional), and the original PR-close behavior is reproduced as one data-defined rule with identical `prStatus` derivation — generalization with a proven no-regression.
3. **The right correctness guards are already in.** Redelivery dedup via idempotency key (proven by re-POSTing), fan-out to the correct rule set, no-rule → no dispatch, raw-body verification discipline — the webhook foot-guns are handled, not deferred.
4. **It reuses the production dispatch seam.** The `RunAgent` seam wires to the same `dispatchBackgroundTriggerEvent → start(runBackgroundAgentWorkflow)` path GitHub already uses; only two small tables and one route handler are net-new.
5. **It's the highest-surface-area growth lever in Wave 2.** Each new source is a new reason a team embeds the product deeper into their stack — compounding integration value the competition mostly lacks.

## The case AGAINST (strong)
1. **It's blocked on 2b, same as 2a.** The POC dispatches a run *intent* and stops; for the woken run to survive sandbox teardown a crash between "intent created" and "run started" must not lose the wake-up. Without 2b's durable queue, event-driven agents will occasionally drop the very events that justify the feature.
2. **Unattended agents reacting to external events is a real safety surface.** An agent that auto-opens PRs on every deploy failure or Sentry alert can amplify an incident (noise during an outage), act on spoofed-but-verified-by-misconfig events, or loop. Needs rate limits, spend caps, and dry-run/review-only modes — product work beyond the POC.
3. **Operator burden is non-trivial.** Every source needs its secret stored and rotated, and a misconfigured secret is indistinguishable from an attack (both 401). Without strong verification-failure observability, teams will hit silent, hard-to-debug breakage — and that operator surface is ongoing cost, not a one-time setup.
4. **Provider payload/signature drift.** Vercel's SHA1 and Sentry's header were taken from docs and flagged as "confirm against a live delivery"; normalizers can break when providers change shapes. This is permanent maintenance across N external integrations, each able to break independently.
5. **Scope creep risk.** "Any source" invites an unbounded integration backlog. Each source is marketing-attractive but carries verify/normalize/maintenance weight; without discipline the surface sprawls faster than it's maintained.

## Effort, dependencies & risk
**Feasibility verdict (from POC): feasible and low-risk** — the canonical model subsumes the existing one, the verifier registry handles heterogeneous auth with no pipeline special-casing, and PR-close becomes data, so generalization is additive. **Build size:** small-to-medium — two `pgTable`s (`eventSources`: kind/secretRef/config; `triggerRules`: the rule shape with jsonb match + prompt template), move `sources/*` + `rule-engine.ts` + `dispatcher.ts` into `apps/web/lib/event-agents/`, fold existing `github-events.ts` into `sources/github.ts`, add `/api/events/[source]` (with `/api/github/webhook` kept as a thin alias so the existing GitHub App URL keeps working) — plus the net-new Triggers/Event-Sources/delivery-log UI. **Cross-POC dependencies:** hard dependency on **POC 2b** for the woken run to survive teardown (dispatch must enqueue into the durable queue; the idempotency key is the reconciliation hook 2b needs); composes with **2a** (shared `RunAgent` seam and dispatch path) for the full standing-agents story. **Top risks + mitigations:** (a) durability → ship after 2b, enqueue via the durable workflow; (b) dedup store → back the idempotency key with a unique index / TTL'd store so dedup holds across instances and stays bounded; (c) secret provisioning → first-class rotation UX + per-source verification-failure-rate observability; (d) signature/normalizer drift → confirm Vercel/Sentry schemes against live deliveries, fail closed (return `[]`) and emit an observability event so drift is visible; (e) safety → rate limits, spend caps, and a review-only/dry-run mode for unattended runs.

## The decision
**The crisp question:** Do we generalize event ingestion into a source-agnostic "wake an agent on event X" product — and gate it on durable execution? **Recommended trigger to greenlight:** POC 2b's durable runtime is adopted (so woken runs survive teardown); start with GitHub + one high-value external source (Vercel deploys *or* Sentry) rather than all five at once. **Success metrics:** # of active trigger rules per team; triggered-run land rate (target ≥99% on 2b); per-source verification-failure rate (health, not just volume); triggered PRs/issues that get acted on; # of distinct sources registered per account (integration depth). **Suggested default: BUILD — but LATER (after 2b), and START NARROW.** Rationale: it's proven, additive, and the strongest integration/lock-in lever in Wave 2, but it shares 2a's hard durability dependency and adds an ongoing operator + provider-maintenance surface. Build it once 2b is real, launch with GitHub plus one external source behind solid verification-health observability and unattended-run guardrails, and expand sources by demonstrated demand rather than by catalog.
