# POC 3b — Sandbox ↔ Local State Handoff

**"Continue this in my editor"** (and the reverse, "Resume in sandbox").

Export a sandbox's complete git state — branch, full commit-graph delta, **and
the uncommitted working state (staged + unstaged + untracked, with file modes
and binary bytes)** — as a single portable artifact, plus a one-command local
checkout. Then re-hydrate a fresh sandbox clone from a local branch the same
way.

## Goal

A developer running an agent in a cloud sandbox hits a point where they want to
finish in their local editor. They click **"Continue locally"**. They should get
their branch, their commits, **and their exact in-progress edits** — including
files they staged, files they only modified, brand-new scratch files they never
`git add`-ed, files they deleted, executable scripts, and binary assets — landed
byte-for-byte on their machine. And vice-versa: pick local work back up in a
fresh sandbox.

The hard part is **not** the commits (git already transports those well). It is
the uncommitted/untracked fidelity. A naive `git diff` or `git stash` silently
drops untracked files and conflates the staged-vs-unstaged split. Eliminating
that blind spot is the point of this POC.

## What was built

```
POC/3b-sandbox-local-handoff/
├── scripts/
│   ├── export-state.sh       # runs "in the sandbox": capture -> portable bundle
│   ├── import-state.sh        # runs in the target: bundle -> byte-exact rehydrate
│   └── continue-locally.sh    # one-command: fresh clone + import (the UI action)
├── src/
│   ├── exec-seam.ts           # stand-in for Sandbox.exec(command, cwd, timeoutMs)
│   ├── fidelity.ts            # byte-exact fingerprint + compare
│   └── eval.ts                # builds realistic mixed state, proves both directions
└── evidence/                  # status dumps + sha256 manifests (generated by eval)
```

Every operation in the two core scripts is a plain `git` command string, so the
whole handoff maps 1:1 onto the sandbox execution seam
(`packages/sandbox/interface.ts` → `exec(command, cwd, timeoutMs)`).

## The git mechanism chosen — and why

**Transport: a single `git bundle`.** A bundle is git's canonical offline,
single-file transport for commit history. It is self-verifying, supports thin
delta bundles (`<base>..<tip>`) for cheap "2 commits ahead" exports, and a fresh
clone can `git fetch <bundle>` directly. We bundle the branch tip plus three
bookkeeping refs (below). A `.meta` sidecar records the branch name and the two
state-tree SHAs so import is self-describing.

**Uncommitted capture: two extra trees, written with plumbing.** This is the
crux. We capture the working state as two git *trees*, then wrap them in commits
so the bundle carries their objects:

| Ref | Tree contents | Captures |
| --- | --- | --- |
| `refs/handoff/head` | (the HEAD commit) | branch tip + history |
| `refs/handoff/index` | `git write-tree` of the live index | **staged** snapshot |
| `refs/handoff/worktree` | `git add -A` into an **external throwaway index**, then `git write-tree` | **staged + unstaged + untracked**, with exec bits and binary bytes |

From three trees the importer reconstructs the exact split:

- `HEAD → index tree` = the staged changes (`git diff --cached`)
- `index tree → worktree tree` = the unstaged changes (`git diff`)
- files in the worktree tree absent from HEAD = untracked + staged-new
- files tracked at HEAD but absent from the worktree tree = working-tree
  deletions

**Why not the obvious alternatives:**

- **`git stash create` / `git stash`** — rejected. Plain `git stash create` does
  **not** capture untracked files at all (verified: a brand-new `new.txt` never
  appears in the stash commit). `git stash -u` exists but bundles untracked into
  an opaque parent commit and still does not cleanly preserve the
  staged-vs-unstaged distinction on restore. It is built for local round-trips,
  not transport fidelity.
- **`git diff` / `git format-patch`** — rejected as the primary mechanism. A
  textual patch loses untracked files entirely, mangles binary files unless
  `--binary` is forced, is fragile across line-ending/CRLF normalization, and
  does not carry commit history. format-patch is commit-only.
- **Raw tarball of the worktree** — rejected. Loses the git index, so the
  staged-vs-unstaged split is gone, and it cannot dedupe against history.

The chosen approach reuses git's own content-addressed object store for
**byte-exact** transfer of every file (text or binary), preserves file modes via
`checkout-index`, and is expressible entirely as `exec`-able git commands.

### Restore order (import-state.sh)

1. `git fetch <bundle> refs/handoff/*` — pull objects/refs into the target.
2. `git checkout -B <branch> <head>; git reset --hard <head>; git clean -fdq` —
   clean baseline at the captured commit.
3. Materialize the **full worktree tree** to disk through a throwaway index with
   `git checkout-index -a -f` (restores exact bytes **and** modes, incl. the
   exec bit; binary files come back byte-identical).
4. Delete paths tracked at HEAD but absent from the worktree tree (the unstaged
   deletions).
5. `git read-tree <index tree>` — point the real index at the staged snapshot.

After step 5: `git diff --cached` == the original staged diff, `git diff` == the
original unstaged diff, untracked files are present, deletions are reflected.

## How it was tested + evidence

`bun run eval` builds a realistic **mixed** state in a throwaway repo and proves
byte-exact fidelity in **both** directions. The seeded state contains every
subtlety simultaneously:

- a `feature` branch **2 commits ahead** of `main`
- a **staged** modification (`tracked.txt`) ...
- ... with a further **unstaged** modification on top (git status `MM`)
- a brand-new **untracked** file (`scratch-notes.txt`)
- a **staged-new** file (`staged-new.txt`, status `A.`)
- a **deleted** tracked file (`to-delete.txt`, unstaged deletion `.D`)
- an **executable-mode** file modified (`run.sh`, mode `100755`)
- a small **binary** file modified (`logo.bin`)

It then exports → transfers the bundle → imports into a **separate fresh clone**
and asserts the two trees are identical across seven independent fingerprints:
`branch`, `head`, reachable commit `graph`, `git status -uall --porcelain=v2`,
`git diff --cached` (staged), `git diff` (unstaged), and a **sha256 manifest of
every on-disk file with its mode**.

## Integration plan

**Execution seam.** Both scripts are sequences of `git` command strings. In
production they run via `Sandbox.exec(command, cwd, timeoutMs)`
(`packages/sandbox/interface.ts`; concrete impl
`packages/sandbox/vercel/sandbox.ts`). The repo already centralizes git helpers
in `packages/sandbox/git.ts` (`getCurrentBranch`, `getHeadSha`, `getStagedDiff`,
`getFileModes`, `detectBinaryFiles`) — the export routine slots in next to those
as `exportHandoffBundle(sandbox)` returning the bundle bytes (read via
`sandbox.readFileBuffer`), and `importHandoffBundle(sandbox, bundle)` for the
reverse. Note `git.ts` today reads changed files individually and base64-encodes
binaries by hand; the bundle approach supersedes that with git's own
content-addressed transfer and removes the per-file binary special-casing.

**Persistence / session fields.** The relevant columns already exist on
`sessions` in `apps/web/lib/db/schema.ts`: `repoOwner`, `repoName`, `branch`,
`cloneUrl`, and the `sandboxState` JSON blob. A "Continue locally" action:

1. Calls `exportHandoffBundle` inside the live sandbox (sequence of `exec` git
   commands), reads the resulting `.bundle` + `.meta`.
2. Stores/streams the bundle (e.g. blob storage; or `snapshotUrl`-style field),
   and hands the user `continue-locally.sh <bundle> <cloneUrl> <dest>` where
   `cloneUrl` = `sessions.cloneUrl` and the branch comes from `sessions.branch`.

**Where the UI/CLI hangs it.**

- *Continue locally*: a button on the session/diff view. Backend produces the
  bundle; the CLI (or a downloadable script) runs `continue-locally.sh`, which
  is the exact `git clone` + `import-state.sh` flow proven here.
- *Resume in sandbox*: the reverse path — a local CLI runs `export-state.sh` on
  the user's working tree, uploads the bundle, and the orchestrator provisions a
  fresh sandbox clone of `cloneUrl` and runs `import-state.sh` via `exec`,
  updating `sessions.branch` / `sandboxState` to the rehydrated state.

## Feasibility verdict

**Feasible and proven.** Full-fidelity sandbox↔local handoff, including the
uncommitted/untracked blind spot, works with stock git plumbing and nothing else
— no daemon, no custom protocol. The transfer is byte-exact in both directions
on a realistic mixed state, and every step is an `exec`-able git command that
fits the existing sandbox seam and session schema. Ship it.

## Blind spots eliminated

- **Untracked files** — captured (plain `git stash create` drops them; verified).
- **Staged vs. unstaged split** — preserved exactly via two separate trees;
  `git diff --cached` and `git diff` both reproduce identically, including the
  `MM` case (a file both staged and further modified).
- **Staged-new files** (`A.`) — present in the index tree, restored staged.
- **Working-tree deletions** (`.D`) — reproduced by diffing HEAD against the
  worktree tree.
- **Executable bit** — preserved (`checkout-index` writes mode `100755`;
  manifest confirms `755`).
- **Binary files** — byte-identical (content-addressed blobs; sha256 manifest
  match), no patch/encoding mangling.
- **Commit-graph delta** — full reachable history transferred via the bundle;
  thin `<base>..<tip>` bundles supported for ahead-of-main exports.

## Remaining risks

- **Huge working trees** — `git add -A` into a throwaway index plus a bundle
  scales with worktree size; multi-GB trees mean large bundles and slow
  `checkout-index`. Mitigation: delta bundles against the base ref, and a size
  guard before export.
- **`.gitignore`'d build artifacts** — `git add -A` respects `.gitignore`, so
  `node_modules`/`dist` are intentionally excluded. This is usually correct, but
  if a user relies on an ignored-but-important file it will not transfer. A
  `--include-ignored` opt-in could be added (with loud warnings).
- **Secrets in uncommitted files** — uncommitted `.env`/credential files that
  are *not* gitignored **will** be captured and transported in the bundle. The
  bundle must be treated as sensitive (encrypted at rest, scoped access). Worth
  a pre-export scan/warning for secret-looking untracked files.
- **Git LFS** — pointer files transfer fine, but LFS-backed blob *contents* are
  not in the bundle; LFS objects need a separate fetch/transfer step.
- **Submodules** — only the gitlink (commit SHA) transfers; submodule working
  trees and their own uncommitted state are out of scope for this POC.
- **Symlinks / special files** — symlinks are handled by git as mode `120000`
  blobs (fine); device files, sockets, and FIFOs are not git-tracked and are not
  transferred.
- **Path/line-ending normalization** — assumes consistent `core.autocrlf` /
  `core.fileMode` between sandbox and local. The eval forces `core.fileMode
  true` on clones; production should pin these so mode/EOL fidelity holds across
  OSes (notably Windows locals).
